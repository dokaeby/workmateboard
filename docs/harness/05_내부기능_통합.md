# 05. 내부 기능 통합 — calendar-agent / skillRadar / Codex 제공자

기존 `calendar-agent`, `skillRadar` 프로젝트의 기능을 하네스 내부 워크플로로 이식한 내용.

## 1. 모델 제공자와 debug/release 라우팅

- `ModelConfig.provider`: `openai_compat`(기본) | `codex`
- `CompositeLLM`이 provider별 클라이언트로 디스패치
- `CodexResponsesLLM`: `~/.codex/auth.json`의 ChatGPT 구독 OAuth 토큰 사용.
  `chatgpt.com/backend-api/codex/responses`에 SSE 스트리밍 필수(`stream:true`).
  액세스 토큰 만료 시 `auth.openai.com/oauth/token`으로 refresh 후 auth.json 갱신.
- `Settings.mode`:
  - `debug` — 모든 역할/티어가 `default_model`(gemini-3.5-flash-lite)로 강제
  - `release` — default 티어는 gemini, important 티어는 `important_model`(codex, `gpt-5.6-sol`)
- 역할별 오버라이드 `role_models`는 양쪽 모드에서 유지.
- `configure_logging(settings)`이 mode별 로거 레벨을 설정한다 —
  app/cli 시작 시 호출. `debug`=DEBUG, `release`=INFO (DEBUG 출력 숨김).
  토큰·API 키·push endpoint 등 비밀값은 어느 레벨에서도 로깅하지 않는다
  (push 실패 로그는 endpoint 원문 대신 SHA256 지문 12자만 기록).

## 2. calendar-agent 이식 (`gmail_calendar` v0.2.0)

멀티채널 공통 소스 컨텍스트: `source_provider` ∈ `gmail|slack|telegram`,
`source_id`, `thread_id`, `source_url`, `message_text`.

단계: `extract(LLM) → validate(결정적) → conflict_check(Calendar 검색) →
register(멱등) → notify`

- Slack: `POST /api/v1/webhooks/slack` — `X-Slack-Signature` HMAC 검증,
  5분 타임스탬프 윈도우, `url_verification` 챌린지, 채널 allowlist
- Telegram: `POST /api/v1/webhooks/telegram` — secret-token 헤더 검증, 봇 메시지 무시
- 수신함: `message_extractions` 테이블, `(provider, source_id)` 멱등,
  `processing_status` pending/processed/failed + 재시도 백오프(최대 5회)
- 워커(`_automation_loop`, `JOBMATE_WORKER_INTERVAL_SECONDS`):
  pending 메시지 → run 생성·동기 실행, due `notification_jobs` 발송,
  `gmail_calendar` 자동화 활성 시 주기적 Gmail 폴링, KST 06시 이후 radar 일일 수집
- `scheduled_events`: provider-aware event_key, status, version
- Calendar 충돌/자기중복은 `CalendarClient.search_events` 사전 검색으로 판별.
  타임아웃 후 불확실 쓰기는 marker 검색으로 복구(이벤트 재생성 없음).
- 알림 실패해도 캘린더 링크 보존, 사전 알림은 `notification_jobs`에 예약.

신규 엔드포인트: `/webhooks/slack`, `/webhooks/telegram`, `/messages`,
`/messages/{provider}/{id}/retry`, `/listeners/status`, `/events`,
`/events/{id}/review`, `/notification-jobs`, `/gmail-calendar/poll`(어댑터 필요)

- **needs_review 검토 흐름**: `gmail_validate`가 검증 실패 후보를
  `scheduled_events(status="needs_review")`로 영속화. 대시보드 Calendar 뷰 상단에
  "검토 필요" 카드(제목/시작/종료 수정 입력 + 승인·등록/거부)를 표시.
  `POST /api/v1/events/{id}/review` — `reject`는 `rejected` 전이,
  `approve`는 수정값 병합 → `validate_event` 재검증 → 통과 시
  `find_by_marker("review:{id}")` 중복 확인 후 `create_event` →
  `registered` + `calendar_event_id` 저장. 재검증 실패 시 422 + 사유 갱신,
  캘린더 어댑터 없으면 503.

## 3. skillRadar 이식 (`skill_radar` v0.1.0)

단계: `collect → dedupe → summarize(LLM, default 티어) → rank → approve(사람) → publish`

- `radar_collect`: `queries.json`의 플랫폼별 GitHub Search 쿼리,
  `GitHubClient` 프로토콜(GitHubAPI 실구현 + FakeGitHub). README는
  `Accept: application/vnd.github.raw`로 fetch, base64 폴백.
- `radar_dedupe`: `full_name` 중복, fork, archived 제외.
- `radar_summarize`: `RepoSummary`(en/zh/ko 요약, taxonomy+confidence,
  summary_status). content_hash 캐시로 재호출 방지, 실패 시 메타데이터 폴백.
  LLM 실패는 audit 기록 후 계속 진행.
- `radar_rank`: stars + 일일 증가량 + 라이선스 + taxonomy 신뢰도 점수.
- `radar_publish`: 승인 전 reject면 스냅샷 미작성. `radar_snapshots`/
  `radar_items`에 일별 플랫폼 스냅샷 저장(같은 날 재실행 시 갱신).

엔드포인트: `GET /radar/trending?platform&date&lang`, `GET /radar/dates`,
`POST /radar/refresh {platforms, force}` (플랫폼당 run 생성)

Web Push: `GET /push/vapid-key`, `POST /push/subscribe|unsubscribe`,
`GET /sw.js` — gmail_calendar notify 단계에서 `webpush` 어댑터가
저장된 구독 전체로 발송(VAPID_PRIVATE_KEY 필요, 404/410 구독 자동 삭제).
푸시 클릭(`notificationclick`)은 payload의 `url`로 이동 — gmail 유래
알림은 `https://mail.google.com/mail/u/0/#all/{message_id}` 원문 링크가
들어간다(`sensors/gmail_url.build_gmail_url` + `is_safe_source_url` 검증).
알림 예약 발송(`_process_due_notification_jobs`)도 gmail 이벤트면 동일
링크를 source_url로 전달한다.

토큰 JSON 경로를 설정하면 `_default_adapters`가 실구현을 주입한다.
토큰 발급은 `jobmate google-auth gmail|calendar` —
`--credentials <credentials.json>`(calendar-agent와 같은 OAuth client
파일) 또는 `--client-id/--client-secret` 지정, loopback + state 검증,
refresh token을 0600 권한으로 저장. 토큰 파일은 calendar-agent의
`token_gmail.json`/`token_calendar.json`(google-auth Credentials
형식)과 호환되므로 그대로 재사용 가능. 헤더는 RFC2047/mojibake 복원,
Calendar 검색은 nextPageToken 전체 페이지 순회(calendar-agent 포팅).
Calendar 멱등 마커는 `extendedProperties.private.jobmate_marker`에 기록.

## 5. 상용 전환(Django) 시 이관 대상

- `api/app.py`의 엔드포인트/워커 → Django views + Celery/RQ 태스크
- `store/db.py` → Django ORM/PostgreSQL (스키마는 그대로 이관 가능)
- LangGraph 체크포인터 → PostgresSaver
- 워크플로/함수/센서는 프레임워크 비의존이라 그대로 재사용

## 6. Vercel 배포 / PostgreSQL

- `app.py`(루트)가 Vercel Python entrypoint — `src/`를 sys.path에 추가 후
  `jobmate.api.serverless:app`(`create_app()` 인스턴스)을 노출.
- DB: `Store`는 인자가 `postgres://`/`postgresql://` DSN이면 psycopg3 +
  `SCHEMA_PG`로 PostgreSQL을, 아니면 SQLite 파일을 사용.
  `JOBMATE_DATABASE_URL` 또는 Vercel Postgres의 `POSTGRES_URL`/
  `POSTGRES_PRISMA_URL`(자동 인식)이 있으면 PG 사용. PG DSN이 없으면
  `JOBMATE_DB_PATH` SQLite, Vercel에서는 `/tmp/jobmate.db`(인스턴스 임시 —
  WARNING 로그 발생, 영속성 없음).
  SQL은 `?`→`%s`, `INSERT OR IGNORE`→`ON CONFLICT DO NOTHING`으로 번역되는
  단일 코드베이스.
- 서버리스에서는 lifespan의 자동화 스레드를 띄우지 않음(`VERCEL` env 감지).
  대신 `GET|POST /api/v1/cron/tick`이 `_automation_loop` 1사이클을 실행 —
  `vercel.json`의 cron이 주기 호출. `CRON_SECRET` env가 있으면
  `Authorization: Bearer <CRON_SECRET>` 검증(Vercel Cron이 자동 부착).
- 주의: Vercel Hobby 플랜 cron은 하루 1회 제한 — 분 단위 폴링이 필요하면
  외부 스케줄러(GitHub Actions 등)로 tick을 호출하거나 Pro 플랜 필요.
- Google 토큰: 로컬은 `JOBMATE_{GMAIL,CALENDAR}_TOKEN_PATH` 파일.
  Vercel처럼 파일이 없는 환경은 `JOBMATE_{GMAIL,CALENDAR}_TOKEN_JSON` env에
  토큰 JSON 전체를 넣으면 부팅 시 임시 파일(0600)로 materialize해 어댑터에
  주입한다. 토큰 경로만 설정되고 파일이 없으면 해당 어댑터는 생성되지 않고
  WARNING 로그를 남긴다(앱 크래시 없음).

## 7. 이메일 3줄 요약 카드 (`/api/v1/email/check`)

- 외부 스케줄러(cron-job.org 등)가 30분마다 `POST /api/v1/email/check` 호출.
  본문 `{"limit": 5, "query": "in:inbox"}` — limit 최대 20.
- `adapters["gmail"]`(GoogleGmail)로 최근 메일을 읽고 메시지별 LLM 3줄 요약을
  생성해 `email_summaries` 테이블에 upsert. 결과는 `GET /api/v1/email/summaries`
  로 조회하며 Gmail Checker 뷰가 우선 표시(없으면 message_extractions 폴백).
- 인증: `CRON_SECRET`/`JOBMATE_CRON_SECRET` 설정 시 `Authorization: Bearer` 또는
  `?secret=` 파라미터 필요. 미설정이면 오픈(로컬 개발용).
- Gmail API 오류 시 502 + `{"ok": false, "error": ...}` 반환.

## 8. LangSmith 관측성

- `langsmith>=0.15` 명시 의존성. `LANGSMITH_API_KEY` env가 있고
  `JOBMATE_LANGSMITH_TRACING`(기본 true)이면 `configure_langsmith()`가
  `LANGCHAIN_TRACING_V2`/`LANGCHAIN_API_KEY`/`LANGCHAIN_PROJECT`
  (`JOBMATE_LANGSMITH_PROJECT`, 기본 `jobmate`)를 설정 — app/cli 시작 시 호출.
- LangGraph 워크플로 실행은 langsmith 내장 연동으로 자동 트레이스.
- `CompositeLLM.complete`는 tracing env 감지 시 `langsmith.traceable`
  (`run_type="llm"`, name `jobmate.llm.complete`)로 래핑되어 OpenAI-compat/
  Codex 모든 LLM 호출이 별도 run으로 기록됨. 키 없으면 래핑하지 않음.

## 9. Agent-Office 뷰 (`dev_review` 스테이지 시각화)

- 대시보드 사이드바 "Agent Command" 메뉴(뷰 키 `office`): `dev_review`
  workflow의 run을 선택해 단계 스테이지를 3D 보드 노드로 표시한다.
- 노드 상태는 `stage_runs.status`(`pending`/`running`/`succeeded`/`failed`/
  `skipped`)에서 매핑하고, run 단위 상태(`queued`/`running`/
  `waiting_approval`/`waiting_review`/`needs_human`/`completed`/`failed`/
  `rejected`/`budget_exhausted`/`cancelled`)는 ORCH(오케스트레이터) 노드
  테두리와 활성 run 선택에 사용한다. 실행 중 스테이지에는 진행 애니메이션,
  attempt>1에는 재시도 표시(×N)를 붙인다.
- 데이터는 기존 runs API를 재사용한다 — `GET /api/v1/runs?workflow=dev_review&limit=50`
  (`workflow` 쿼리 파라미터로 workflow_key 필터, 미지정 시 전체 workflow 대상
  기본 limit=50 동작 유지)으로 dev_review run 목록을 고르고
  `GET /api/v1/runs/{id}`로 stages(전체 stage_runs)·토큰 사용량·
  이벤트 로그를 주기 폴링한다. run 상태가 바뀌면 선택 중인 상세 패널도
  다시 렌더링한다.
- `waiting_approval` run에서 승인 단계(사람 승인) 노드를 선택하면
  승인/거절 버튼을 표시 — `POST /api/v1/runs/{id}/approve`
  `{decision: "approve"|"reject"}` 호출. run이 waiting_approval을 벗어나면
  버튼은 자동으로 숨겨지고, 클릭 즉시 비활성화해 더블클릭 중복 발사를 막는다.
- 노드 클릭 시 우측 상세 패널에 스테이지 설명·상태·소요시간·토큰 합계와
  해당 run의 이벤트 로그를 표시한다. 헤더에는 진행률·총 토큰·경과 시간을
  요약한다(토큰은 모든 시도 attempt를 합산).
- 별도 코딩 job 큐/워커/SSE는 없다 — 코딩 에이전트 기능은 제거됐고,
  dev_review run 실행은 API 서버의 run 실행 경로(`_automation_loop`/tick 또는
  동기 `jobmate run`)가 담당한다.
- **모드 전환**: Agent-Office 뷰 상단에 `워크플로 | 세션` 탭과
  `3D 보드 | 스프라이트 사무실` 토글이 있다.
  - 스프라이트 사무실: `claude-3d-frog-office`(MIT) 포팅 아이소메트릭
    캔버스 — `src/jobmate/api/static/office/`의 JS/CSS/webp. 최초 선택 시
    lazy 로드. `jobmate-bridge.js`가 `officeState`를 people 계약으로 변환
    (stage running→working, waiting_approval→decision, 그 외→rest).
  - 세션 탭: 스프라이트 엔진을 재사용하되 provider를
    `GET /api/v1/agent-sessions`로 교체 — 로컬 `jobmate agent-bridge`가
    push한 Claude/Codex/Gemini/Devin 세션이 캐릭터로 표시된다.

### 9.1 에이전트 세션 (`agent_sessions` + `agent-bridge`)

- `agent_sessions` 테이블: tool/session_key UNIQUE, status
  (`working`/`decision`/`rest`/`ended`), doing/ask 요약(≤80자),
  project/title, machine, tokens_in/tokens_out(누적, MAX 갱신),
  last_event_at. 대화 본문은 저장하지 않는다.
- `POST /api/v1/agent-sessions` — 머신 push 전용. `JOBMATE_API_KEY`가
  설정된 경우 API 키 인증 필수(세션 쿠키만으로는 403). body:
  `{tool, session_key, status, project?, title?, doing?, ask?, event_at?,
  machine?, tokens_in?, tokens_out?, ended_summary?, artifacts?}`.
  `machine`은 브릿지가 보내는 짧은 호스트명, `tokens_*`는 세션 누적
  토큰 카운터(서버는 MAX로만 갱신 — 역행 push는 무시).
- `GET /api/v1/agent-sessions?limit=50&include_ended=&machine=` —
  `ended` 제외(기본), last_event_at 내림차순. `machine` 지정 시 해당
  머신 세션만 정확 일치 필터. 각 항목에 계산 필드가 붙는다:
  - `health`: `ended`(status=ended) / `stale`(working·decision인데
    last_event_at‖updated_at이 300초 초과) / `long_idle`(rest인데
    43200초=12h 초과) / `active`(그 외). Python 계산.
  - `est_cost_usd`: tokens_in/out을 1M 토큰당 가격표로 환산한 USD
    추정치. tool별 오버라이드(codex 저가, claude/gemini 등) + default
    {input:3.0, output:15.0}. 토큰이 둘 다 없으면 null.
    세션별 비용은 로깅하지 않는다.
- `GET /api/v1/agent-sessions/stats?since=YYYY-MM-DD` — 응답
  `{tools: {...}, hourly: [{hour:0..23, working_seconds:int}]}`.
  `since`는 로컬 날짜(기본 오늘, 형식 오류 시 422). `hourly`은
  agent_session_events의 working/decision 이벤트 간격(event_at →
  다음 이벤트 created_at, 로컬 날짜로 클립, 시간 경계 분할 합산)을
  로컬 시간 버킷에 합산한 값.
- `GET /api/v1/agent-sessions/{tool}/{session_key}/history` — 상태 전이
  이벤트 시간순(최대 500).
- `jobmate agent-bridge [--url URL] [--interval 15] [--once]` — 로컬
  수집기. `~/.claude/projects`, `~/.codex/sessions`(jsonl.zst),
  `~/.gemini/antigravity-cli/conversations`(sqlite),
  `~/.local/share/devin/cli`(transcripts+locks)를 스캔해 상태를 계산,
  변경분/60초 하트비트만 push. 모든 push에 `machine`(짧은 호스트명)을
  포함한다. 토큰 누적치는 claude(assistant usage 합산)와
  codex(token_count의 total_token_usage 최신값)에서만 수집하고
  gemini/devin은 null로 둔다 — 스캔 실패는 세션 수집을 깨지 않는다.
  인증은 `JOBMATE_API_KEY` env, 서버 주소는 `--url` 또는 `JOBMATE_URL`
  env(기본 `http://127.0.0.1:8000`). 상태 판정은 파일 mtime+마지막
  이벤트 휴리스틱 — 승인 프롬프트 정밀 감지는 미지원.
- **알림 규칙(`notify_rules`)**: 세션 attention 웹푸시( decision 진입
  또는 ask 설정 전이 시 1회, 10분 레이트리밋)에 적용되는 prefs 필터.
  `automation_state`의 `prefs` 키 JSON 안 `notify_rules` 리스트:
  `[{"tool": str|null, "project": str|null, "statuses": [str]}]`.
  - 비어 있거나 없으면 모든 세션에 푸시(기존 동작).
  - 규칙이 있으면 규칙 중 하나라도 `tool`(null=전체)·`project`
    (null=전체) 일치 AND `statuses`에 세션의 유효 상태가 포함될 때만
    푸시. 유효 상태는 `ask`가 비어 있지 않으면 `"ask"`, 아니면
    `status`(working/decision/rest/ended). 매칭 안 되는 세션은
    조용히 스킵(debug 로그만).
  - `GET/POST /api/v1/settings`로 왕복 가능 — POST body에
    `notify_rules`를 포함하면 검증 후 저장(최대 100개 규칙,
    statuses는 문자열 리스트 필수).

## 9.5 워크플로 변형·스케줄·통계·diff/감사 조회

### 워크플로 템플릿 (`GET /api/v1/workflows`)

`dev_review` 파이프라인의 단계 부분집합 변형 4종이 `WORKFLOWS`에 등록됐다
(`workflows/code_pipelines.py`). 모두 `analysis→implement→auto_checks` 이후
리뷰 단계만 다르며 `implement` stage key는 동일해 diff 미리보기가 공통 동작한다.

| key | 단계 |
|---|---|
| `dev_review` | analysis→implement→auto_checks→security→code_review→qa→approval |
| `bugfix` | analysis→implement→auto_checks→security→approval |
| `refactor` | analysis→implement→auto_checks→code_review→approval |
| `docs_update` | analysis→implement→auto_checks→approval |
| `dependency_update` | analysis→implement→auto_checks→security→code_review→approval |
| `gmail_calendar` / `skill_radar` | 기존 워크플로 (변경 없음) |

`GET /api/v1/workflows` 응답 항목: `{key, version, description, stages:[{key,kind,description,agent,function}]}`.
`POST /api/v1/runs`는 `WORKFLOWS`에 등록된 모든 key를 그대로 받는다.

### 에이전트/스테이지 모델 오버라이드 (`JOBMATE_AGENT_MODELS`)

JSON 객체로 agent 키(`analysis|implementer|security|reviewer|qa|extractor`) 또는
stage 키(`analysis|implement|auto_checks|security|code_review|qa|approval` 등)를
모델명에 매핑한다. 예: `{"security":"gpt-5","qa":"claude-sonnet"}`.
`build_registry`가 `agent.model.model`만 교체하고 `ModelConfig`의 나머지
필드(base_url/api_key_env/provider/temperature 등)는 유지한다. 잘못된 JSON은
경고 후 무시.

### Run 통계 (`GET /api/v1/runs/stats?workflow=&days=30`)

`runs`+`stage_runs` 조인 집계(SQLite/PostgreSQL 공용 SQL). 응답:
`{workflow, days, runs, succeeded, failed, running, waiting_approval,
avg_duration_s, total_tokens_in, total_tokens_out, stage_failures, daily}`.
- `succeeded`=completed, `failed`=failed/rejected/budget_exhausted/needs_human/cancelled,
  `running`=queued+running, `waiting_approval`=waiting_approval (나머지 상태는 runs에만 포함)
- `avg_duration_s`: 종료 상태 run의 `updated_at-created_at` 평균(초), 없으면 null
- `stage_failures`: run×stage별 최신 attempt가 failed인 건수를 stage_key별 집계
- `daily`: 윈도우 전 일자(UTC) `{date,runs,tokens}` — runs는 created_at 일자,
  tokens는 stage_runs.started_at 일자 기준 in+out 합

### Approval diff 미리보기 (`GET /api/v1/runs/{run_id}/diff`)

implement 단계의 succeeded stage_run 출력을 최신 시도 순으로 합쳐
`ChangeProposal.diff`(unified diff)를 파일 단위로 분해한다.
응답 `{files:[{path,status,additions,deletions,diff}], summary}` —
status는 added/deleted/renamed/modified. implement 산출물이 없으면
`files: []`. run이 없으면 404.

### Run 감사 로그 (`GET /api/v1/runs/{run_id}/audit`)

`audit_events`를 run_id로 조회해 최신순 최대 200건 반환 —
`[{id, actor, action, object_ref, detail, created_at}]` (detail은 본문/토큰 없는
메타데이터만). `run_detail`의 `audit` 필드와 동일 데이터의 역순 뷰.

### 주기적 workflow 실행 (`/api/v1/schedules`)

`workflow_schedules` 테이블(SQLite/PostgreSQL 양쪽 스키마):
`id, workflow, input(JSON), interval_minutes, enabled, last_run_at, next_run_at, created_at`.

- `GET /api/v1/schedules` — 전체 목록 (input은 파싱된 객체, enabled는 bool)
- `POST /api/v1/schedules` — `{workflow, input?, interval_minutes}`.
  workflow는 `WORKFLOWS` 등록 key만 허용(아니면 404), `interval_minutes>=5`
  (미만 시 422). `next_run_at = now + interval`로 생성, 201 + 스케줄 객체.
- `POST /api/v1/schedules/{id}/toggle` — `{enabled: bool}`.
  활성화 시 `next_run_at`을 `now + interval`로 재계산. 없으면 404.
- `DELETE /api/v1/schedules/{id}` — 삭제, 없으면 404.

발사 경로: `_automation_loop`와 `/api/v1/cron/tick`이 매 사이클
`_process_due_schedules`를 호출 — `enabled=1 AND next_run_at<=now`인
스케줄마다 run을 생성(`store.create_run` → 일반 run과 동일하게 `/runs`에 표시)
하고 `last_run_at`/`next_run_at`을 갱신한다. run audit에 `scheduled_run`
이벤트(object_ref=schedule id)가 남는다. input의 `task`가 없으면
`"scheduled <workflow>"`를 사용한다. 스케줄 CRUD·발사 모두 `audit_events`에
기록되며, 스케줄 입력은 run input으로 그대로 전달된다(비밀값 입력 금지).

### 승인 메타데이터

`approvals` 테이블에 `created_at` 컬럼 추가(양쪽 스키마 + 기존 DB는
`_ensure_columns` 마이그레이션). `GET /api/v1/runs/{id}`의 approvals 항목에
`created_at`이 포함된다(구 행은 `decided_at`으로 폴백). 승인 "대기" 시작
시각은 approval stage의 `stage_runs.started_at`(RUNNING 유지) 또는
`/audit`의 `waiting_approval` 이벤트로 확인한다.

## 10. 대시보드 설정 (`/api/v1/settings`)

- 헤더 ⚙ 버튼 → 설정 다이얼로그. `automation_state` 테이블 `prefs` 키에 JSON 저장.
- 항목: `gmail_check_minutes`(30/60 — `_maybe_poll_gmail` 폴링 간격에 적용,
  email/check 외부 cron 주기는 cron-job.org/Vercel cron에서 별도 설정),
  `radar_interval`(daily/weekly — `_maybe_daily_radar`가 마지막 수집 후
  7일 미만이면 스킵),
  `notify_rules`(에이전트 세션 어텐션 푸시 필터 — §9.1 참조).
- GET/POST `/api/v1/settings` — 검증 실패 시 422.
- POST 시 `_sync_cronjob`이 cron-job.org 실제 스케줄도 갱신
  (`adapters/cronjob.py`, `PATCH /jobs/{id}`):
  - `JOBMATE_CRONJOB_JOB_ID` — 이메일 체크 job. `gmail_check_minutes`
    30→`minutes:[0,30]`, 60→`minutes:[0]` (Asia/Seoul).
  - `JOBMATE_CRONJOB_RADAR_JOB_ID` — 레이더 수집 job. daily→매일 06:00,
    weekly→매주 월요일 06:00.
  - **자동 생성**: job id가 없고 `CRONJOB_ORG_API_KEY` +
    `JOBMATE_PUBLIC_BASE_URL`이 설정돼 있으면 `PUT /jobs`로 job을 생성하고
    반환된 id를 prefs(`cronjob_email_job_id`/`cronjob_radar_job_id`)에 저장.
    이후 설정 변경은 기존 job에 `PATCH`만 수행(중복 생성 없음).
    생성되는 job은 `POST {PUBLIC_BASE_URL}/api/v1/email/check`
    (`{"limit":5}`)와 `POST .../api/v1/radar/refresh`(`{"force":true}`)를
    호출하며, `JOBMATE_API_KEY` 설정 시 `X-API-Key` 헤더를 함께 보낸다.
  - `CRONJOB_ORG_API_KEY`는 콘솔 Settings에서 발급. job id/API 키 미설정 시
    `skipped`, API 실패 시 `error:` 상태 문자열을 응답 `cronjob` 필드로
    반환 — 로컬 저장은 항상 성공, UI가 상태를 표시한다.

## 11. 보안 (`security.py` + API 미들웨어)

- **API 키 인증**: `JOBMATE_API_KEY` 설정 시 `/api/*` 전체에
  `X-API-Key` 또는 `Authorization: Bearer` 요구. 예외: `/api/v1/health`,
  `/api/v1/webhooks/*`(자체 서명 검증). 키와 허용 이메일 목록이 모두 없고
  Vercel이 아닐 때만 인증 비활성(로컬 개발).
  프론트는 localStorage `jobmate_api_key`를 자동 첨부하고 401 시 1회 입력
  프롬프트 후 재시도한다.
- **저장 데이터 암호화**: Fernet(`cryptography`). 키 우선순위
  `JOBMATE_ENCRYPTION_KEY` → `JOBMATE_API_KEY` → `CRON_SECRET` →
  `JOBMATE_CRON_SECRET`. 암호문은 `enc:v1:` 접두사, 키 없으면 평문 저장.
  적용 필드: `push_subscriptions.keys_json`, `email_summaries`의
  `subject`/`sender`/`summary` — store 계층에서 저장 시 암호화·조회 시
  복호화해 API 응답 형태는 동일하다.
- **응답 헤더**: 모든 응답에 `X-Content-Type-Options: nosniff`,
  `X-Frame-Options: DENY`, `Referrer-Policy: no-referrer`,
  `Permissions-Policy`(camera/mic/geo 차단) 부여.
- 참고: TLS 종료는 배포 계층(Vercel 등) 책임. Google OAuth 토큰 파일은
  파일 권한(0600)으로 보호되며 DB 암호화 대상이 아니다.

### 11.1 2026-11-23 보안 수정

- `JOBMATE_ALLOWED_EMAILS`가 설정된 경우에만 비밀번호 가입 시 관리자 API 키를
  요구한다(허용 이메일 입력만으로는 소유권이 검증되지 않음). 미설정 시 공개 가입.
- Google 로그인은 `email_verified=true`가 필요하다. 허용 목록이 설정되면
  목록의 이메일만 로그인 가능. 다른 Google subject가 연결된 기존 계정으로
  로그인할 수 없다. 허용 목록에서 제거한 세션은 즉시 거부한다.
- cron tick은 Vercel 외 환경에서도 설정된 cron secret 또는 API 키를 검증한다.
  Vercel은 전용 cron secret이 필수다.
- Web Push는 HTTPS/443의 FCM, Mozilla, Apple Push, Windows Push 호스트만
  허용한다. 저장 구독도 발송 시 재검증하며 리디렉션을 차단하고 10초 타임아웃을 적용한다.
  실패 로그에는 endpoint가 포함될 수 있는 예외 원문 대신 예외 유형만 남긴다.
- 도구 파일 읽기는 심볼릭 링크를 해석한 실제 경로가 저장소 내부인지 검사한다.
- `deep-translator` 의존성을 제거했다(PYSEC-2022-252). 한국어 번역 폴백은
  기존 HTTPX로 MyMemory API를 호출하고 실패하면 원문을 유지한다.
- Windows의 `chmod(0600)`은 POSIX 권한 보장과 같지 않다. Windows 토큰 파일의
  실제 보호는 NTFS ACL 설정에 달려 있으며 이번 검사에서는 별도 검증하지 않았다.

## 12. 통합 인박스·비용·리포트·메신저·세션 활동 (2026-11-23 추가)

### 12.1 알림 센터 (`inbox_items`)

- 테이블: `id, kind, title, body, link, read, dedupe_key, created_at`
  (SQLite/PostgreSQL 양쪽 스키마). kind ∈
  `notification|session_attention|approval|schedule|report`.
- `notifications` 테이블은 그대로 유지 — `GET /inbox` 호출 시
  `dedupe_key=notif:{id}`로 `inbox_items`에 **지연 미러링**(멱등,
  읽음 상태는 인박스 항목 기준). 나머지 kind는 이벤트 발생 시 직접 insert.
- dedupe: `upsert_inbox_item(dedupe_key=...)` — 같은 키가 있으면
  title/body/link만 갱신하고 created_at·read는 유지. `reset_read=True`면
  미읽음으로 리셋(승인 재대기용).
- 발생 지점: 세션 decision/ask 전이 → `session:{tool}:{session_key}`,
  run waiting_approval 전이 → `approval:{run_id}`, 스케줄 발사/실패 →
  `schedule:{run_id}`/`schedule-fail:{sid}:{ts}`, 리포트 생성 →
  `report:{id}`.
- 엔드포인트:
  - `GET /api/v1/inbox?limit=50&unread_only=` → `[{id,kind,title,body,link,read,created_at}]`
    최신순 (`read`는 bool).
  - `POST /api/v1/inbox/{id}/read`, `POST /api/v1/inbox/read-all`
    (`{ok,updated}`), `GET /api/v1/inbox/unread-count` → `{count}`.
  - 승인 결정(`POST /runs/{id}/approve` 또는 메신저 `승인해`) 시 해당
    `approval:{run_id}` 인박스 항목을 자동 read 처리.

### 12.2 비용 대시보드

- `GET /api/v1/usage/summary?days=30` →
  `{total_cost_usd,total_tokens_in,total_tokens_out,by_model:[{model,cost_usd,tokens}],
  by_day:[{date,cost_usd,tokens}],top_sessions:[{tool,session_key,cost_usd}],
  budget_usd,budget_exceeded}`.
- 비용은 `llm_usage` 행에 `jobmate/pricing.py`의 모델별 가격표
  (1M 토큰당 USD, 패밀리 키워드 매칭: claude/codex/gemini/default)를 적용한
  **추정치**다. `top_sessions`는 `agent_sessions.tokens_*`의
  `est_cost_usd` 상위 10개(토큰 없으면 제외).
- `budget_usd`는 prefs `monthly_budget_usd`(POST /settings로 설정,
  GET /settings에도 반환). `budget_exceeded` = UTC 월초 이후 llm_usage
  추정 비용 > 예산.

### 12.3 자연어 쿼리 (`POST /api/v1/ask`)

- body `{question}`(≤2000자) → `{answer}` (한국어).
- 컨텍스트: run_stats(7d)·agent_session_stats·llm_usage_summary 집계만
  JSON으로 주입(비밀값/원문 없음). `settings.model_for("_ask","default")`
  모델로 `llm.complete` 호출 — MeteredLLM 경유로 사용량 자동 계측.
- 타임아웃 30초. LLM 실패/타임아웃 시 **503** `{"answer":"","error":"llm_unavailable"}`.
- 레이트리밋: 세션 사용자 또는 IP당 UTC 일 20회(인메모리).

### 12.4 리포트 (`jobmate/reports.py` + `reports` 테이블)

- `build_report(store, kind, settings)` — kind `daily`(1일)/`weekly`(7일)
  + `exec_daily`/`exec_weekly` 임원 리포트(§15.8).
  섹션: `period, runs(집계+daily), sessions(tool별), llm(토큰/비용/모델별),
  approvals.pending, radar.new_items, notable_failures(stage_failures 상위)`.
- 엔드포인트:
  - `GET /api/v1/reports?kind=daily|weekly` — 온디맨드 생성(비저장).
  - `GET /api/v1/reports/latest?kind=` — 저장본 우선, 없으면 온디맨드 생성.
  - `POST /api/v1/reports/generate {kind}` — **admin 전용**, 저장 +
    인박스 `report` + 메신저 알림.
- 자동 생성: `_automation_loop`과 `/cron/tick`이 매 사이클
  `_maybe_generate_reports` 호출 — 최신 리포트가 20h(daily)/7d(weekly)
  이상 지났거나 없으면 생성·저장·인박스·메신저 알림. 실패는 warning 로그.

- 첫 가입 사용자는 자동 admin 승격(`_maybe_first_user_admin`).

### 12.6 메신저 커맨드 (`jobmate/messenger.py`)

- `parse_command(text)`: `승인해|approve [run_id]`(최신 waiting_approval),
  `시작|start|run <workflow> <task>`(run 생성), `현황|status`, `도움말|help`.
  인식 못 하는 텍스트는 None → 기존 캘린더 수신함 처리로 진행.
- webhook(`POST /webhooks/slack|telegram`) 서명 검증 후 커맨드면 답장 후
  `{"status":"command"}` 반환(수신함 저장 안 함). 답장은 수신 채널로 —
  Slack은 `JOBMATE_SLACK_WEBHOOK_URL`, Telegram은 수신 `chat_id`로
  `JOBMATE_TELEGRAM_BOT_TOKEN` 사용.
- 발송: `send_slack(webhook_url,text)`, `send_telegram(bot_token,chat_id,text)`
  — httpx timeout 10s, 실패 시 예외 유형만 로그(토큰/URL 원문 금지).
- `notify(text)`: `JOBMATE_SLACK_WEBHOOK_URL` +
  `JOBMATE_TELEGRAM_BOT_TOKEN`/`JOBMATE_TELEGRAM_CHAT_ID` 설정 채널 전체로
  best-effort 발송. waiting_approval 전이와 리포트 생성 시 호출.
- 신규 env: `JOBMATE_SLACK_WEBHOOK_URL`, `JOBMATE_TELEGRAM_BOT_TOKEN`,
  `JOBMATE_TELEGRAM_CHAT_ID`, `JOBMATE_ADMIN_EMAILS` (.env.example 참조).

### 12.7 세션 활동 녹화/리플레이

- `session_activity` 테이블: `id(autoincrement/identity), tool, session_key,
  status, doing, project, recorded_at`. SQLite/PostgreSQL 양쪽.
- `push_agent_session`마다 `record_session_activity` 호출 — status/doing이
  바뀌었거나 마지막 기록 후 60초 경과 시에만 insert(인메모리 아닌 SQL 스로틀),
  insert 시 ~2% 확률로 7일 이전 행 삭제(저비용 보존).
- `GET /api/v1/agent-sessions/{tool}/{session_key}/activity?limit=200` →
  `[{at,status,doing,project}]` 시간순.

### 12.8 헬스 상세·뱃지·위젯

- `GET /api/v1/health/detail` →
  `{api:{uptime_s}, db:{type,path,size_bytes}, bridge:{last_push_at,
  machines:[{machine,last_push_at,sessions}]}, cron:{last_tick_at}, version}`.
  `/health`와 동일하게 인증 예외. `last_tick_at`은 `_automation_loop`/
  `cron/tick` 진입 시 갱신되는 모듈 변수.
- `GET /api/v1/badge/count` → `{count}` = 미읽음 인박스 + waiting_approval run
  (PWA 뱃지).
- prefs 확장: `monthly_budget_usd`(float|null), `dashboard_widgets`
  (`[{id,visible,order}]`, 최대 50) — GET/POST `/settings`로 왕복.

## 13. 사이드바 뷰 집계 API (읽기 전용, `jobmate/insights.py`)

새 대시보드 사이드바 뷰용 GET 엔드포인트 4개. 모두 `/api/*` 인증 미들웨어와
동일하게 세션 사용자 또는 API 키를 요구하며, 상태를 변경하지 않는다.
집계 로직은 `src/jobmate/insights.py`의 순수 함수에 두고 app.py는 얇게 감싼다.
비용 센터 뷰는 기존 `GET /usage/summary`+`GET /agent-sessions`, 시스템
모니터링은 `GET /health/detail`을 재사용하므로 신규 엔드포인트가 없다.

### 13.1 인사이트 (`GET /api/v1/insights?days=30`)

- 응답: `{days, sessions:{by_tool,by_project,total_sessions,
  total_working_seconds}, runs:{total,succeeded,failed,running,
  success_rate,avg_duration_s,by_workflow}, cost:{total_cost_usd,
  llm_tokens_in,llm_tokens_out}, top_failures}`.
- `sessions`는 신규 Store 메서드 `session_work_seconds(since_iso)` 기반 —
  `agent_session_events`를 (tool, session_key) 시간순으로 훑어
  `agent_session_stats`와 동일한 간격 추정(working 이벤트→다음 이벤트,
  최대 1시간 캡, 마지막 working은 현재까지)으로 tool/project별
  `sessions`(윈도우 내 고유 session_key 수)·`working_seconds`·
  `decisions`(tool만)를 계산. project는 이벤트 값→`agent_sessions.project`
  →`"(no project)"` 순. 윈도우 이전 이벤트는 로드하지 않아 경계 구간은
  누락될 수 있다(단순화, 문서화된 한계).
- `runs`는 `store.run_stats` 재사용. `success_rate` =
  succeeded/(succeeded+failed), 종료 run 0이면 null. `by_workflow`는
  workflow별 `run_stats` 재호출. `top_failures`는 stage_failures 상위
  (stage_key,count) 정렬 목록.
- `cost`는 `llm_usage_rows(cutoff)` + `pricing.cost_usd` 합계 —
  `/usage/summary`와 동일한 추정 방식.

### 13.2 자동화 허브 (`GET /api/v1/automation/overview`)

- 응답: `{schedules:[{id,workflow,interval_minutes,enabled,last_run_at,
  next_run_at,input}], notify_rules, cron:{last_tick_at},
  messenger:{slack,telegram}, reports:{last_daily,last_weekly},
  generated_at}`.
- schedules는 `store.list_schedules()` 투영. notify_rules는 prefs 원본.
- `cron.last_tick_at`은 `/health/detail`과 같은 `_last_cron_tick_at()`
  모듈 변수(`_automation_loop`/`cron/tick` 진입 시 갱신).
- `messenger` configured는 env 존재 여부(bool)만 —
  slack=`JOBMATE_SLACK_WEBHOOK_URL`, telegram=`JOBMATE_TELEGRAM_BOT_TOKEN`
  +`JOBMATE_TELEGRAM_CHAT_ID` 모두 설정 시 true. 값 자체는 반환하지 않는다.
- `reports.last_*`는 `store.list_reports` 최신순 첫 daily/weekly의
  created_at.

### 13.3 아카이브 검색 (`GET /api/v1/archive?q=&kind=&limit=50`)

- 3개 소스를 Python 필터로 통합(데이터셋이 작아 DB 방언 차이 회피):
  - `kind="report"`: `list_reports` → title `일일|주간 리포트 YYYY-MM-DD`,
    snippet `kind · 생성 시각`, link `"reports"`.
  - `kind="run"`: `list_runs` → title `workflow: task 앞 60자`,
    snippet `status · created_at`, link `"runs"`.
  - `kind="session"`: `list_agent_sessions(include_ended=True)` 중
    status=ended이고 ended_summary/artifacts가 있는 행 → title
    `tool · project(또는 session_key 앞 12자)`, snippet=ended_summary
    (없으면 artifacts), link `"office"`.
- `q`는 title+snippet 대소문자 무시 부분 문자열. `kind`는
  report|run|session, 빈 값=전체, 그 외 값은 422.
- 응답 `{items:[{kind,id,title,snippet,created_at,link}], query}` —
  created_at 내림차순, limit 최대 200.

### 13.4 개발자 상태 (`GET /api/v1/developer/status`)

- 응답 `{integrations:[{name,configured,note}], auth:{google,password,
  api_key,admin_emails_configured}, generated_at}`.
- integrations: gmail/calendar(어댑터 주입 여부), github_radar
  (`settings.github_token_env`이 가리키는 env, 기본 `GITHUB_TOKEN`), slack/telegram(env 존재),
  llm_default(`settings.llm_api_key_env`, 기본 `GEMINI_API_KEY`가 가리키는 env)/llm_codex
  (codex api key env 또는 `~/.codex/auth.json` 존재), codex_bridge
  (`agent_sessions_bridge_info().last_push_at` 존재).
- auth: google=`GOOGLE_CLIENT_ID` 설정, password=항상 true(내장 기능),
  api_key=`JOBMATE_API_KEY` 설정, admin_emails_configured=
  `JOBMATE_ADMIN_EMAILS` 설정. **모든 값은 bool/짧은 설명만 — 비밀값
  원문·토큰·URL은 절대 반환하지 않는다.**

## 14. 대시보드 확장 기능 (2026-11-23 추가)

모두 세션 인증 필요(공개 share 조회 제외). 신규 테이블:
`playbooks`, `run_comments`, `connectors`, `custom_workflows`, `triggers`,
`trigger_fires`, `share_links`, `dashboard_cards`. `runs`에 `created_by` 컬럼 추가.

### 14.1 플레이북 (`/api/v1/playbooks`)

- `GET` → `{items:[{id,name,workflow,input,created_by,created_at}]}`.
- `POST {name,workflow,input?}` → 201. workflow는 내장+커스텀 모두 허용
  (미등록 시 404). name 공백 불가.
- `DELETE /{id}` → 204.
- `POST /{id}/run` → 202 `{run_id,...}`. `POST /runs`와 동일한 백그라운드
  실행 경로(`_start_run`)를 사용하며 `created_by`에 실행자를 기록한다.

### 14.2 Run 코멘트 (`/api/v1/runs/{run_id}/comments`)

- `GET` → `{items:[{id,run_id,user_id,user_email,body,created_at}]}` (최신순).
- `POST {body}` → 201. run 존재 확인, body trim 후 1~4000자만 허용(그 외 422).
  `user_email`·`user_id`를 함께 저장한다.

### 14.3 커넥터 (`/api/v1/connectors`)

- 타입: `github|jira|notion|linear|webhook|json`.
- `POST {type,name,config,enabled?}` → 201. `config`의 token/secret/password/
  api_key 등 민감 키는 Fernet(`enc:v1:`)로 암호화해 저장한다.
  **응답·목록에는 `config`를 포함하지 않고 `has_token`만 노출한다.**
- `GET` → `{items:[{id,type,name,enabled,has_token,last_fetch_at,last_error,created_at}]}`.
- `DELETE /{id}`, `POST /{id}/toggle {enabled}`.
- `GET /{id}/items?limit=50` → 외부 fetch 후 정규화된
  `{items:[{id,title,url,state,updated_at,author}]}`.
  - 60초 인메모리 캐시(`_CONNECTOR_CACHE`), 실패 시 `last_error` 기록 + 경고 로그.
  - github: `api.github.com` + 선택적 token(Bearer). webhook/json: config.url을
    GET하고 `config.json_path`(dot-path, 기본 배열 루트)로 배열 추출,
    `config.fields`로 출력 필드 매핑 가능. jira/notion/linear은 config.url
    + json_path/fields 규칙을 그대로 사용한다.
  - 외부 호출 성공/실패는 앱 로그에 기록(토큰·URL 민감값 미포함).

### 14.4 커스텀 워크플로 (`/api/v1/workflows/custom`)

- `GET` → `{items:[{name,spec,created_at,updated_at}]}`.
- `POST {name,spec}` → 201. spec는 `WorkflowSpec`로 검증하고 `spec.key==name`이어야 한다.
- `DELETE /{name}`.
- 저장된 spec는 앱 시작 시와 변경 직후 `_sync_custom_workflows()`가 모듈
  `WORKFLOWS` dict에 동기화한다. `build_registry()`가 `WORKFLOWS`를 순회하므로
  `/runs`, 플레이북, 스케줄, 트리거에서 별도 코드 없이 그대로 해석된다
  (프로세스 재시작 후에도 DB에서 복원).

### 14.5 트리거 (`/api/v1/triggers`)

- `match`: `{tool?, project?, state?}` (state ∈ 세션 라이프사이클 상태).
  `action.type`: `run_workflow{workflow,input?}` | `run_playbook{playbook_id}` |
  `report{report_kind=daily|weekly}`.
- `POST {match,action}` → 201(검증 실패 422/404), `GET`, `DELETE /{id}`,
  `POST /{id}/toggle {enabled}`.
- `_automation_loop`/cron tick에서 세션 스냅샷을 주기적으로(≥45s) 비교해
  **상태 전이**를 감지한다. 동일 `(trigger_id, tool, session_key, state, fingerprint)`는
  `trigger_fires`의 UNIQUE 제약으로 1회만 발화(재시작·중복 tick에도 dedupe).
  발화 시 `last_fired_at`/`last_error` 갱신, 성공·실패 앱 로그 기록
  (세션 본문 미로깅).

### 14.6 팀 뷰 (`GET /api/v1/team`)

- `{items:[{id,email,name,role,run_count,last_active_at,session_count}]}`.
  `runs.created_by`(email 또는 user id) 기준 집계 + auth_sessions 활동 병합.
  첫 사용자/`JOBMATE_ADMIN_EMAILS` 기준 effective admin 반영.

### 14.7 감사 뷰 (`GET /api/v1/audit?limit=200`)

- **admin 전용**(비관리자 403). `{items:[{id,created_at,actor,action,target,detail}]}`
  최신순. `audit_events` 테이블 재사용. 로그인 성공/실패·승인/거절·설정 변경·
  playbook/connector/workflow/trigger/card/share 변경·role 변경이 기록된다.
  비밀값은 detail에 넣지 않는다.

### 14.8 내보내기/공유

- `GET /api/v1/export?kind=runs|sessions|usage|reports&format=csv|json&days=30`
  → `text/csv` 또는 `application/json` attachment. 비밀 필드 제외.
- `POST /api/v1/share {kind:run|report|insights, ref_id}` → 201 `{token,url,expires_at}`
  (30일). `GET /api/v1/share/{token}` 및 공개 페이지 `GET /share/{token}`은
  세션 없이 안전한 스냅샷만 반환. 만료 시 410, 미존재 404.

### 14.9 대시보드 카드 (`/api/v1/cards`)

- `GET/POST {title,url,json_path?}/DELETE /{id}/POST /{id}/toggle`.
- `GET /{id}/data` → 서버가 URL을 GET(8s 타임아웃, ~256KB 상한)해 `json_path`
  dot-path로 값을 추출해 `{value}` 반환(빈 path=전체 JSON).
- SSRF 방지: http/https만 허용, localhost·loopback·private/링크로컬 IP 리터럴
  차단(`webutil.is_safe_public_url`). 실패 시 `last_error`+경고 로그.

### 14.10 모바일 요약

- 신규 백엔드 없음 — 기존 `/api/v1/insights`, `/api/v1/automation/overview` 등
  읽기 전용 집계 API로 충분.

## 15. 팀장(lead) 기능 — 역할·프로젝트·리스크·리포트 (2026-11-23 추가)

`jobmate/lead.py` — insights.py와 같은 읽기 전용 집계 모듈(Store 조회 + 순수 함수).
집계 로직은 여기, HTTP 라우트는 `api/app.py`, 리포트 본문은 `reports.py`.

### 15.1 역할 체계 `member|lead|admin`

- `users.role`은 `member|lead|admin` 3단계. 레거시 `'user'`는 읽기 시
  `member`로 정규화(`Store._norm_role`, `_user_json`/`list_users`/`team_activity`),
  쓰기 시에도 `'user'` 별칭을 `member`로 받는다. 알 수 없는 값은 `member`.
- 유효 role 판정(`_effective_role`): 저장 role 우선, `JOBMATE_ADMIN_EMAILS`는
  admin, 신규 `JOBMATE_LEAD_EMAILS`(쉼표)는 lead 부여 — admin env가 lead보다 우선.
- `_lead_user`: 세션 role이 lead/admin, 유효 API 키(머신), 인증 비활성 로컬
  모드일 때 허용. `_admin_user`는 기존과 동일(admin만).
- `PATCH /api/v1/users/{id}/role {role}` — **admin 전용**. 마지막 admin 강등
  시 409 `last_admin`. 변경 시 `store.audit` + `_audit_api`(`user_role`) +
  로그. 첫 가입 사용자 자동 admin 승격은 유지(응답 dict도 동기화).
- `GET /api/v1/auth/me` 응답은 기존 `{user:{id,email,display_name,role}}`
  형태 유지, role은 정규화된 값.

### 15.2 프로젝트 마스터 + 태깅

- `projects` 테이블: `id,name UNIQUE(ci),color,description,goal,target_count,
  created_by,created_at` — SQLite/PG 양쪽 + `lower(name)` 유니크 인덱스.
- `runs.project` 컬럼 추가(`_migrate_run_columns` ALTER). `create_run`은
  `input.project`를 컬럼에도 복사. `agent_sessions.project`는 기존 컬럼 재사용.
- 프로젝트 이름 매칭은 trim + case-insensitive. 미등록 이름도 자유 태그로 허용.
- 엔드포인트(전부 **lead 이상**):
  - `GET/POST /api/v1/projects`, `PATCH|DELETE /api/v1/projects/{id}`
    (name/color/description/goal/target_count). 변경·삭제 시 감사 로그.
  - `PATCH /api/v1/runs/{run_id} {project}` — 태그 설정/해제(`""`/null).
  - `PATCH /api/v1/agent-sessions/{session_key} {project}` — tool 미지정,
    session_key 최신 세션 우선. 변경 시 `agent_session_events`에 전이 1건 기록.

### 15.3 프로젝트 개요/상세

- `GET /api/v1/projects/overview` → `{items:[{id,name,color,description,goal,
  target_count,session_count,active_sessions,run_count,success_rate,
  avg_seconds,total_cost_usd,open_approvals,recent_activity(≤8)}]}`.
  마스터+자유 태그+미태그 `"(기타)"` 버킷을 모두 포함. 비용은 세션
  tokens_in/out 추정(`pricing.price_for_model`).
- `GET /api/v1/projects/{id}/detail` → `{project,sessions,runs,timeline,
  stage_failures,cost_by_day(30d)}`. ref는 프로젝트 id / 이름(ci) /
  `untagged` / `tag:<key>` 허용.

### 15.4 세션 회고

- `GET /api/v1/agent-sessions/{tool}/{session_key}/history` — 기존 `events`
  필드 유지 + `session,timeline[{at,from_state,to_state,text,duration_s}],
  stats{state_counts,decisions,approvals,errors,tokens_in,tokens_out,
  est_cost_usd,total_seconds},files_touched,summary,ended_summary` 추가.
- `GET /api/v1/agent-sessions/{session_key}/history` — tool 미지정 변형
  (session_key 최신 세션으로 해석).
- `summary`는 LLM 없이 stats로부터 조합한 결정적 한국어 문장.

### 15.5 리스크 (`GET /api/v1/risks`, 라이브 계산)

- `{items:[{type,severity,title,detail,ref_kind,ref_id,at}]}` — 심각도→최신순,
  type+ref dedupe, 최대 50건.
- 탐지 유형: `stage_failure`(같은 workflow+stage 7일 내 ≥2 run 실패, ≥3이면
  high), `stale_approval`(waiting_* 4h 초과, 24h 초과 high), `idle_session`
  (health stale/long_idle), `cost_spike`(오늘 비용 >3× 7일 일평균 & >$1,
  llm_usage 기준), `trigger_failure`(triggers.last_error 잔존),
  `budget`(월 누적 > prefs.monthly_budget_usd).

### 15.6 통합 승인 큐 (`GET /api/v1/approvals`)

- `{items:[{kind,id,title,waiting_since,age_seconds,project,status?}]}` —
  run `waiting_approval|waiting_review` + 세션 `decision`/ask 보유 +
  last_error 트리거. 가장 오래 기다린 순.

### 15.7 성과 비교 (`GET /api/v1/perf/compare?workflow=&group_by=`)

- `{workflow,group_by,items:[{group,run_count,success_rate,avg_seconds,
  total_tokens,total_cost_usd,failures_by_stage}],sessions:{items:[{tool,
  session_count,active,ended,avg_work_seconds}]}}`.
- group_by `model`(run 최다 토큰 stage의 model)/`agent`(워크플로 stage→agent
  매핑)/`tool`(created_by 분류: trigger/schedule/radar/user/api-key).

### 15.8 임원 리포트

- `reports.build_report` kind 확장: `exec_daily`(1일)/`exec_weekly`(7일).
  본문: `narrative`(한국어 요약 문단), `highlights[]`, runs/sessions(도구별)/
  llm(비용)/approvals(큐 스냅샷)/risks/notable_failures.
- `GET /api/v1/reports?kind=`, `GET /reports/latest?kind=`,
  `POST /api/v1/reports/generate {kind}`, trigger action `report_kind` 모두
  4종 허용. 인박스/메신저 알림 경로는 기존 `report` kind 그대로 재사용.
- 자동 생성: `_maybe_generate_reports`가 daily/exec_daily(20h)·
  weekly/exec_weekly(7d) 주기로 함께 생성.

### 15.9 편차/주의

- `POST /api/v1/reports`는 기존 엔드포인트 형태(`POST /reports/generate`)를
  그대로 사용 — 신규 경로를 추가하지 않았다.
- `/auth/me`는 프론트 계약 유지를 위해 `{user:{...}}` 래퍼 형태.
- lead 전용 엔드포인트는 `_lead_user`로 보호 — 로컬 개발 모드(인증 비활성)와
  API 키는 admin 상당으로 통과한다.

## 16. 에이전트 플랫폼 확장 (2026-11-24 추가)

### 16.1 네이티브 function calling + 도구 스키마 레지스트리

- `LLMClient.complete()`에 선택적 `tools`/`tool_choice` kwargs 추가.
  반환 계약: `(output, usage)` 유지 — 모델이 tool_calls를 반환하면
  `output == {"tool_calls": [{"id","name","arguments"}], "content": str|None}`
  (arguments는 JSON 문자열 또는 dict, OpenAI 중첩 `function.*` 형태도 정규화).
  `schema` 검증은 tool_calls 턴에서는 바이패스.
- `OpenAICompatLLM`은 chat/completions `tools` 파라미터 전송 + `message.tool_calls`
  파싱. `CodexResponsesLLM`은 Responses API `function_call` output item을
  SSE 이벤트에서 수집. `MeteredLLM`은 kwargs 그대로 전달(사용량 계측 유지).
- `src/jobmate/tools/schemas.py`: `register_tool_schema(name, description, parameters)`
  / `openai_tools()` / `has_schema(name)` — OpenAI tools 형식 레지스트리.
  builtin `read_file`/`run_tests`/`read_diff` 스키마 사전 등록.
- `ToolExecutor(tools, repo_root, extra_tools)`: `extra_tools`는 builtin과 병합,
  **builtin 이름은 절대 덮어쓸 수 없다**. `openai_schemas_for(allowed)`로
  allowlist 필터링된 스키마 조회.
- `engine/runner.py::_run_llm_stage`: `agent.tools`가 비어있지 않으면
  `_tool_loop` 실행 — 최대 `_MAX_TOOL_ROUNDS=5`라운드 + `budget_max_tool_calls`
  상태 카운터(실행된 호출만 집계, denied는 미집계). `ToolDeniedError`/실행 오류는
  `ERROR: …` 문자열로 모델에 반환해 복구 유도. 5라운드 후 tools 없는 최종
  `complete`로 답변 강제. 감사 로그는 `{tool, arg_keys}`만 기록(인자 원문 금지).
  `tools=[]` 에이전트는 기존과 동일한 단일 호출.

### 16.2 프롬프트 인젝션 방어 (`engine/guards.py`)

- `INJECTION_PATTERNS`: EN+KO 13개 정규식(ignore/disregard/forget instructions,
  system prompt, "you are now", developer mode, 이전 지시 무시 등).
- `detect_injection(text) -> list[str]` — 패턴명만 반환(원문 미반환).
- `wrap_untrusted(label, text)` — `<untrusted_source name="…">` 블록 +
  "데이터이지 지시가 아니다" 경고 포함.
- `sanitize_untrusted(text)` — 매칭 라인을 `[filtered]`로 치환.
- `_build_user_prompt`: `task`, `message_text` 및 stage output 내 외부 유래
  문자열(`body/readme/description/text/message/snippet` 키, dict/list 재귀,
  경로별 라벨 `collect.items[2].readme`)을 전부 untrusted 래핑.
  LLM 생성 verdict/decision은 래핑하지 않는다.
- 인젝션 감지 시 `audit(run_id, "system", "injection_detected", stage, {source, patterns})`
  — 원문 로깅 금지.

### 16.3 MCP 연동 (`src/jobmate/mcp/`)

- **서버**: `python -m jobmate.mcp.server` (stdio, FastMCP, `mcp>=1.8,<2` 고정 —
  v2는 FastMCP→MCPServer 개명). 읽기 전용 5종: `list_runs`, `get_run`,
  `list_inbox_items`, `list_scheduled_events`, `run_stats`. Store lazy-init.
- **클라이언트**: `JOBMATE_MCP_SERVERS`(JSON 배열 권장, `name=command args`
  세미콜론 구분 폴백) 또는 `JOBMATE_MCP_SERVER_CMD/NAME/ARGS` 단축키.
  stdio_client + ClientSession, 전용 백그라운드 루프, 실패 시 빈 목록 반환
  (파이프라인 중단 없음). 도구명은 `mcp_<server>_<tool>` 프리픽스.
- `mcp_tool_entries()`가 각 도구를 `register_tool_schema`에 자동 등록 →
  `AgentSpec.tools`에 `mcp_*` 이름을 allowlist하면 function calling으로 사용 가능.
- `workflows/registry_builder.py::_build_tool_executor()`가 MCP 설정 시
  `ToolExecutor(extra_tools=...)`로 주입. MCP 미설정/실패 시 builtin만.

### 16.4 SSE 실시간 스트림 (`GET /api/v1/stream`)

- `text/event-stream`. 초기 `event: snapshot`(최근 run 30) 후
  `Store.activity_since(since_iso)`로 run/stage/session 이벤트를 ~1.5초 간격
  tailing. 테이블별 ISO 워터마크 + 경계 seen-id로 중복 방지, ~15초 heartbeat.
- 인증: 세션 쿠키(동일 출처) 또는 `?api_key=`/`?token=` 쿼리(EventSource는
  헤더 불가 — `security.authorized()`가 쿼리 폴백 지원, `/api/*` 전체에 적용).
  접근 로그는 쿼리스트링 미기록.
- 동시 연결 상한 20, 초과 시 503. `X-Accel-Buffering: no`.
- UI: `index.html`이 EventSource로 `run`/`stage`/`session` 이벤트 수신 시
  디바운스(300ms)로 `refreshRuns`/`updateInboxBadge`/`loadOffice` 등 기존
  갱신 함수 호출. 기존 `setInterval` 폴링은 fallback으로 유지.
- ⚠️ Vercel serverless에서는 버퍼링/타임아웃으로 실시간 보장 안 됨 —
  상시 uvicorn 배포에서 동작.
