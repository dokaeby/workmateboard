# 05. 내부 기능 통합 — calendar-agent / skillRadar / Codex 제공자

기존 `calendar-agent`, `skillRadar` 프로젝트의 기능을 하네스 내부 워크플로로 이식한 내용.

## 1. 모델 제공자와 debug/release 라우팅

- `ModelConfig.provider`: `openai_compat`(기본) | `codex`
- `CompositeLLM`이 provider별 클라이언트로 디스패치
- `CodexResponsesLLM`: `~/.codex/auth.json`의 ChatGPT 구독 OAuth 토큰 사용.
  `chatgpt.com/backend-api/codex/responses`에 SSE 스트리밍 필수(`stream:true`).
  액세스 토큰 만료 시 `auth.openai.com/oauth/token`으로 refresh 후 auth.json 갱신.
- `Settings.mode`:
  - `debug` — 모든 역할/티어가 `default_model`(gemini-3.5-flash-lite)로 강제
  - `release` — default 티어는 gemini, important 티어는 `important_model`(codex, `gpt-5.6-sol`)
- 역할별 오버라이드 `role_models`는 양쪽 모드에서 유지.
- `configure_logging(settings)`이 mode별 로거 레벨을 설정한다 —
  app/cli 시작 시 호출. `debug`=DEBUG, `release`=INFO (DEBUG 출력 숨김).
  토큰·API 키·push endpoint 등 비밀값은 어느 레벨에서도 로깅하지 않는다
  (push 실패 로그는 endpoint 원문 대신 SHA256 지문 12자만 기록).

## 2. calendar-agent 이식 (`gmail_calendar` v0.2.0)

멀티채널 공통 소스 컨텍스트: `source_provider` ∈ `gmail|slack|telegram`,
`source_id`, `thread_id`, `source_url`, `message_text`.

단계: `extract(LLM) → validate(결정적) → conflict_check(Calendar 검색) →
register(멱등) → notify`

- Slack: `POST /api/v1/webhooks/slack` — `X-Slack-Signature` HMAC 검증,
  5분 타임스탬프 윈도우, `url_verification` 챌린지, 채널 allowlist
- Telegram: `POST /api/v1/webhooks/telegram` — secret-token 헤더 검증, 봇 메시지 무시
- 수신함: `message_extractions` 테이블, `(provider, source_id)` 멱등,
  `processing_status` pending/processed/failed + 재시도 백오프(최대 5회)
- 워커(`_automation_loop`, `JOBMATE_WORKER_INTERVAL_SECONDS`):
  pending 메시지 → run 생성·동기 실행, due `notification_jobs` 발송,
  `gmail_calendar` 자동화 활성 시 주기적 Gmail 폴링, KST 06시 이후 radar 일일 수집
- `scheduled_events`: provider-aware event_key, status, version
- Calendar 충돌/자기중복은 `CalendarClient.search_events` 사전 검색으로 판별.
  타임아웃 후 불확실 쓰기는 marker 검색으로 복구(이벤트 재생성 없음).
- 알림 실패해도 캘린더 링크 보존, 사전 알림은 `notification_jobs`에 예약.

신규 엔드포인트: `/webhooks/slack`, `/webhooks/telegram`, `/messages`,
`/messages/{provider}/{id}/retry`, `/listeners/status`, `/events`,
`/events/{id}/review`, `/notification-jobs`, `/gmail-calendar/poll`(어댑터 필요)

- **needs_review 검토 흐름**: `gmail_validate`가 검증 실패 후보를
  `scheduled_events(status="needs_review")`로 영속화. 대시보드 Calendar 뷰 상단에
  "검토 필요" 카드(제목/시작/종료 수정 입력 + 승인·등록/거부)를 표시.
  `POST /api/v1/events/{id}/review` — `reject`는 `rejected` 전이,
  `approve`는 수정값 병합 → `validate_event` 재검증 → 통과 시
  `find_by_marker("review:{id}")` 중복 확인 후 `create_event` →
  `registered` + `calendar_event_id` 저장. 재검증 실패 시 422 + 사유 갱신,
  캘린더 어댑터 없으면 503.

## 3. skillRadar 이식 (`skill_radar` v0.1.0)

단계: `collect → dedupe → summarize(LLM, default 티어) → rank → approve(사람) → publish`

- `radar_collect`: `queries.json`의 플랫폼별 GitHub Search 쿼리,
  `GitHubClient` 프로토콜(GitHubAPI 실구현 + FakeGitHub). README는
  `Accept: application/vnd.github.raw`로 fetch, base64 폴백.
- `radar_dedupe`: `full_name` 중복, fork, archived 제외.
- `radar_summarize`: `RepoSummary`(en/zh/ko 요약, taxonomy+confidence,
  summary_status). content_hash 캐시로 재호출 방지, 실패 시 메타데이터 폴백.
  LLM 실패는 audit 기록 후 계속 진행.
- `radar_rank`: stars + 일일 증가량 + 라이선스 + taxonomy 신뢰도 점수.
- `radar_publish`: 승인 전 reject면 스냅샷 미작성. `radar_snapshots`/
  `radar_items`에 일별 플랫폼 스냅샷 저장(같은 날 재실행 시 갱신).

엔드포인트: `GET /radar/trending?platform&date&lang`, `GET /radar/dates`,
`POST /radar/refresh {platforms, force}` (플랫폼당 run 생성)

Web Push: `GET /push/vapid-key`, `POST /push/subscribe|unsubscribe`,
`GET /sw.js` — gmail_calendar notify 단계에서 `webpush` 어댑터가
저장된 구독 전체로 발송(VAPID_PRIVATE_KEY 필요, 404/410 구독 자동 삭제).
푸시 클릭(`notificationclick`)은 payload의 `url`로 이동 — gmail 유래
알림은 `https://mail.google.com/mail/u/0/#all/{message_id}` 원문 링크가
들어간다(`sensors/gmail_url.build_gmail_url` + `is_safe_source_url` 검증).
알림 예약 발송(`_process_due_notification_jobs`)도 gmail 이벤트면 동일
링크를 source_url로 전달한다.

## 4. 어댑터

| 프로토콜 | 실구현 | fake |
|---|---|---|
| GitHubClient | `radar/github.py: GitHubAPI` | `FakeGitHub` |
| CalendarClient | `adapters/google.py: GoogleCalendar` | `FakeCalendar` |
| GmailClient | `adapters/google.py: GoogleGmail` | `FakeGmail` |
| Notifier | `adapters/local.py: LoggingNotifier` + `adapters/push.py: WebPushNotifier` | `FakeNotifier` |

Google 연동: `JOBMATE_GMAIL_TOKEN_PATH`/`JOBMATE_CALENDAR_TOKEN_PATH`에
토큰 JSON 경로를 설정하면 `_default_adapters`가 실구현을 주입한다.
토큰 발급은 `jobmate google-auth gmail|calendar` —
`--credentials <credentials.json>`(calendar-agent와 같은 OAuth client
파일) 또는 `--client-id/--client-secret` 지정, loopback + state 검증,
refresh token을 0600 권한으로 저장. 토큰 파일은 calendar-agent의
`token_gmail.json`/`token_calendar.json`(google-auth Credentials
형식)과 호환되므로 그대로 재사용 가능. 헤더는 RFC2047/mojibake 복원,
Calendar 검색은 nextPageToken 전체 페이지 순회(calendar-agent 포팅).
Calendar 멱등 마커는 `extendedProperties.private.jobmate_marker`에 기록.

## 5. 상용 전환(Django) 시 이관 대상

- `api/app.py`의 엔드포인트/워커 → Django views + Celery/RQ 태스크
- `store/db.py` → Django ORM/PostgreSQL (스키마는 그대로 이관 가능)
- LangGraph 체크포인터 → PostgresSaver
- 워크플로/함수/센서는 프레임워크 비의존이라 그대로 재사용

## 6. Vercel 배포 / PostgreSQL

- `app.py`(루트)가 Vercel Python entrypoint — `src/`를 sys.path에 추가 후
  `jobmate.api.serverless:app`(`create_app()` 인스턴스)을 노출.
- DB: `Store`는 인자가 `postgres://`/`postgresql://` DSN이면 psycopg3 +
  `SCHEMA_PG`로 PostgreSQL을, 아니면 SQLite 파일을 사용.
  `JOBMATE_DATABASE_URL` 또는 Vercel Postgres의 `POSTGRES_URL`/
  `POSTGRES_PRISMA_URL`(자동 인식)이 있으면 PG 사용. PG DSN이 없으면
  `JOBMATE_DB_PATH` SQLite, Vercel에서는 `/tmp/jobmate.db`(인스턴스 임시 —
  WARNING 로그 발생, 영속성 없음).
  SQL은 `?`→`%s`, `INSERT OR IGNORE`→`ON CONFLICT DO NOTHING`으로 번역되는
  단일 코드베이스.
- 서버리스에서는 lifespan의 자동화 스레드를 띄우지 않음(`VERCEL` env 감지).
  대신 `GET|POST /api/v1/cron/tick`이 `_automation_loop` 1사이클을 실행 —
  `vercel.json`의 cron이 주기 호출. `CRON_SECRET` env가 있으면
  `Authorization: Bearer <CRON_SECRET>` 검증(Vercel Cron이 자동 부착).
- 주의: Vercel Hobby 플랜 cron은 하루 1회 제한 — 분 단위 폴링이 필요하면
  외부 스케줄러(GitHub Actions 등)로 tick을 호출하거나 Pro 플랜 필요.
- Google 토큰: 로컬은 `JOBMATE_{GMAIL,CALENDAR}_TOKEN_PATH` 파일.
  Vercel처럼 파일이 없는 환경은 `JOBMATE_{GMAIL,CALENDAR}_TOKEN_JSON` env에
  토큰 JSON 전체를 넣으면 부팅 시 임시 파일(0600)로 materialize해 어댑터에
  주입한다. 토큰 경로만 설정되고 파일이 없으면 해당 어댑터는 생성되지 않고
  WARNING 로그를 남긴다(앱 크래시 없음).

## 7. 이메일 3줄 요약 카드 (`/api/v1/email/check`)

- 외부 스케줄러(cron-job.org 등)가 30분마다 `POST /api/v1/email/check` 호출.
  본문 `{"limit": 5, "query": "in:inbox"}` — limit 최대 20.
- `adapters["gmail"]`(GoogleGmail)로 최근 메일을 읽고 메시지별 LLM 3줄 요약을
  생성해 `email_summaries` 테이블에 upsert. 결과는 `GET /api/v1/email/summaries`
  로 조회하며 Gmail Checker 뷰가 우선 표시(없으면 message_extractions 폴백).
- 인증: `CRON_SECRET`/`JOBMATE_CRON_SECRET` 설정 시 `Authorization: Bearer` 또는
  `?secret=` 파라미터 필요. 미설정이면 오픈(로컬 개발용).
- Gmail API 오류 시 502 + `{"ok": false, "error": ...}` 반환.

## 8. LangSmith 관측성

- `langsmith>=0.15` 명시 의존성. `LANGSMITH_API_KEY` env가 있고
  `JOBMATE_LANGSMITH_TRACING`(기본 true)이면 `configure_langsmith()`가
  `LANGCHAIN_TRACING_V2`/`LANGCHAIN_API_KEY`/`LANGCHAIN_PROJECT`
  (`JOBMATE_LANGSMITH_PROJECT`, 기본 `jobmate`)를 설정 — app/cli 시작 시 호출.
- LangGraph 워크플로 실행은 langsmith 내장 연동으로 자동 트레이스.
- `CompositeLLM.complete`는 tracing env 감지 시 `langsmith.traceable`
  (`run_type="llm"`, name `jobmate.llm.complete`)로 래핑되어 OpenAI-compat/
  Codex 모든 LLM 호출이 별도 run으로 기록됨. 키 없으면 래핑하지 않음.

## 9. Agent-Office 뷰 (`dev_review` 스테이지 시각화)

- 대시보드 사이드바 "Agent Command" 메뉴(뷰 키 `office`): `dev_review`
  workflow의 run을 선택해 단계 스테이지를 3D 보드 노드로 표시한다.
- 노드 상태는 `stage_runs.status`(`pending`/`running`/`succeeded`/`failed`/
  `skipped`)에서 매핑하고, run 단위 상태(`queued`/`running`/
  `waiting_approval`/`waiting_review`/`needs_human`/`completed`/`failed`/
  `rejected`/`budget_exhausted`/`cancelled`)는 ORCH(오케스트레이터) 노드
  테두리와 활성 run 선택에 사용한다. 실행 중 스테이지에는 진행 애니메이션,
  attempt>1에는 재시도 표시(×N)를 붙인다.
- 데이터는 기존 runs API를 재사용한다 — `GET /api/v1/runs?workflow=dev_review&limit=50`
  (`workflow` 쿼리 파라미터로 workflow_key 필터, 미지정 시 전체 workflow 대상
  기본 limit=50 동작 유지)으로 dev_review run 목록을 고르고
  `GET /api/v1/runs/{id}`로 stages(전체 stage_runs)·토큰 사용량·
  이벤트 로그를 주기 폴링한다. run 상태가 바뀌면 선택 중인 상세 패널도
  다시 렌더링한다.
- `waiting_approval` run에서 승인 단계(사람 승인) 노드를 선택하면
  승인/거절 버튼을 표시 — `POST /api/v1/runs/{id}/approve`
  `{decision: "approve"|"reject"}` 호출. run이 waiting_approval을 벗어나면
  버튼은 자동으로 숨겨지고, 클릭 즉시 비활성화해 더블클릭 중복 발사를 막는다.
- 노드 클릭 시 우측 상세 패널에 스테이지 설명·상태·소요시간·토큰 합계와
  해당 run의 이벤트 로그를 표시한다. 헤더에는 진행률·총 토큰·경과 시간을
  요약한다(토큰은 모든 시도 attempt를 합산).
- 별도 코딩 job 큐/워커/SSE는 없다 — 코딩 에이전트 기능은 제거됐고,
  dev_review run 실행은 API 서버의 run 실행 경로(`_automation_loop`/tick 또는
  동기 `jobmate run`)가 담당한다.

## 10. 대시보드 설정 (`/api/v1/settings`)

- 헤더 ⚙ 버튼 → 설정 다이얼로그. `automation_state` 테이블 `prefs` 키에 JSON 저장.
- 항목: `gmail_check_minutes`(30/60 — `_maybe_poll_gmail` 폴링 간격에 적용,
  email/check 외부 cron 주기는 cron-job.org/Vercel cron에서 별도 설정),
  `radar_interval`(daily/weekly — `_maybe_daily_radar`가 마지막 수집 후
  7일 미만이면 스킵).
- GET/POST `/api/v1/settings` — 검증 실패 시 422.
- POST 시 `_sync_cronjob`이 cron-job.org 실제 스케줄도 갱신
  (`adapters/cronjob.py`, `PATCH /jobs/{id}`):
  - `JOBMATE_CRONJOB_JOB_ID` — 이메일 체크 job. `gmail_check_minutes`
    30→`minutes:[0,30]`, 60→`minutes:[0]` (Asia/Seoul).
  - `JOBMATE_CRONJOB_RADAR_JOB_ID` — 레이더 수집 job. daily→매일 06:00,
    weekly→매주 월요일 06:00.
  - **자동 생성**: job id가 없고 `CRONJOB_ORG_API_KEY` +
    `JOBMATE_PUBLIC_BASE_URL`이 설정돼 있으면 `PUT /jobs`로 job을 생성하고
    반환된 id를 prefs(`cronjob_email_job_id`/`cronjob_radar_job_id`)에 저장.
    이후 설정 변경은 기존 job에 `PATCH`만 수행(중복 생성 없음).
    생성되는 job은 `POST {PUBLIC_BASE_URL}/api/v1/email/check`
    (`{"limit":5}`)와 `POST .../api/v1/radar/refresh`(`{"force":true}`)를
    호출하며, `JOBMATE_API_KEY` 설정 시 `X-API-Key` 헤더를 함께 보낸다.
  - `CRONJOB_ORG_API_KEY`는 콘솔 Settings에서 발급. job id/API 키 미설정 시
    `skipped`, API 실패 시 `error:` 상태 문자열을 응답 `cronjob` 필드로
    반환 — 로컬 저장은 항상 성공, UI가 상태를 표시한다.

## 11. 보안 (`security.py` + API 미들웨어)

- **API 키 인증**: `JOBMATE_API_KEY` 설정 시 `/api/*` 전체에
  `X-API-Key` 또는 `Authorization: Bearer` 요구. 예외: `/api/v1/health`,
  `/api/v1/webhooks/*`(자체 서명 검증). 미설정 시 인증 비활성(로컬 개발).
  프론트는 localStorage `jobmate_api_key`를 자동 첨부하고 401 시 1회 입력
  프롬프트 후 재시도한다.
- **저장 데이터 암호화**: Fernet(`cryptography`). 키 우선순위
  `JOBMATE_ENCRYPTION_KEY` → `JOBMATE_API_KEY` → `CRON_SECRET` →
  `JOBMATE_CRON_SECRET`. 암호문은 `enc:v1:` 접두사, 키 없으면 평문 저장.
  적용 필드: `push_subscriptions.keys_json`, `email_summaries`의
  `subject`/`sender`/`summary` — store 계층에서 저장 시 암호화·조회 시
  복호화해 API 응답 형태는 동일하다.
- **응답 헤더**: 모든 응답에 `X-Content-Type-Options: nosniff`,
  `X-Frame-Options: DENY`, `Referrer-Policy: no-referrer`,
  `Permissions-Policy`(camera/mic/geo 차단) 부여.
- 참고: TLS 종료는 배포 계층(Vercel 등) 책임. Google OAuth 토큰 파일은
  파일 권한(0600)으로 보호되며 DB 암호화 대상이 아니다.
