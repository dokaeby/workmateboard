## 1. 테스트 계층

- 단위: 상태 전이, 일정 parser/validator, 권한, idempotency key, URL 정책
- 통합: Django·PostgreSQL·worker·queue·adapter 상호작용
- UI: 핵심 업무 입력, 실행 상태, Google 연결, 일정 알림 및 클릭 흐름
- 파일럿: 실제 메일 형식과 시간대 다양성을 승인된 테스트 계정으로 확인

## 2. 필수 경계 시나리오

- DST 전환, timezone 누락, 자정 통과, all-day와 반복 일정
- 동일 메일의 재수신, Gmail 수정/삭제, 매우 오래된 메일
- Google scope 철회, API quota, timeout과 성공 응답 유실
- 푸시 권한 거부, 구독 만료, 여러 브라우저 구독, 클릭 중 로그인 만료
- 프롬프트 인젝션이 포함된 메일, HTML/첨부 내 악성 입력
- 사용자가 다른 조직의 event/run ID를 조회하는 시도

## 3. 데이터 정책

테스트 데이터는 합성 메일과 가짜 토큰을 사용한다. 파일럿 계정은 명시적으로 승인된 전용 계정으로 제한한다. 결과 캡처에는 이메일 주소와 일정 세부 정보를 마스킹한다.

## 4. 릴리스 판단

P0 케이스 실패, 일정 중복, 무권한 접근, 승인되지 않은 Calendar 생성이 하나라도 확인되면 릴리스를 차단한다. 푸시 불가 환경에서는 앱 내 알림 fallback을 확인한다. 외부 API 의존 테스트의 미실행은 결과에 명시한다.

## 5. 6계층 센서와 래칫 검증

- **가이드**: 실행에서 template/agent/prompt 버전이 고정되고 trace에 연결되는지 확인한다.
- **센서**: 잘못된 schema, 모호한 시간, 중복 원본, 미허용 권한 입력이 외부 쓰기 전에 차단되는지 확인한다.
- **루프**: 재시도·시간·도구 호출·비용 상한 소진 시 완료로 가장하지 않고 정지하는지 확인한다.
- **메모리**: worker를 중간 종료 후 재시작해 완료 노드 재실행 및 Calendar 중복 없이 재개되는지 확인한다.
- **권한·예산**: Gmail 읽기와 Calendar 쓰기 capability가 서버에서 분리되고 다른 조직/연결로 실행되지 않는지 확인한다.
- **관찰가능성**: 업무 성공 증거와 비용·오류·외부 event ID가 같은 실행 ID로 추적되는지 확인한다.

새 실패는 실패 입력/trace를 고정하고, 근본 원인이 있는 하네스 계층을 수정한 뒤 새 회귀 케이스와 전체 기존 케이스로 재검증한다. 모델 자기평가만으로 테스트 통과를 판정하지 않는다.
