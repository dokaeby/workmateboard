## 1. 운영 점검

- 워커 큐 지연, 실패·재시도·dead-letter 수
- Google OAuth 만료/철회, Gmail API quota 및 polling 지연
- Calendar 생성 성공·중복·불확실 상태
- 푸시 구독 만료, 발송 실패와 앱 내 알림 backlog
- LLM 토큰·비용, Langfuse trace 누락 및 오류
- DB 용량, 백업 성공과 복구 가능성

## 2. 비밀정보와 데이터

OAuth 토큰, 세션 키, API 키, VAPID private key는 비밀 저장소에서 관리하고 주기적으로 교체한다. 관찰 로그에는 메일 본문, 첨부파일, OAuth 토큰, 푸시 endpoint 원문을 포함하지 않는다. 계정 연결 해제 시 토큰을 폐기하고 작업을 중지한다.

## 3. 사고 대응

잘못된 일정 자동 등록이나 조직 간 데이터 노출이 확인되면 자동화를 즉시 비활성화하고 관련 run, message ID, event ID, trace ID를 보존한다. 대상 사용자에게 영향과 복구 방법을 안내한다. Calendar 정정은 권한 있는 담당자가 확인 후 수행하며 감사 이력에 남긴다.

## 4. 사용자 통제

사용자는 Google 연결, 자동 감지, 웹 푸시 구독을 각각 끌 수 있어야 한다. 자동화 비활성화와 OAuth 철회는 진행 중 작업의 추가 Gmail 검색·Calendar 생성을 막는다. 이미 성공한 Calendar 이벤트는 기록을 보존하고 삭제는 별도 사용자 명령으로 처리한다.

## 5. 운영 tripwire와 대응

| 신호 | 대응 |
|---|---|
| 동일 단계 오류가 연속 3회 발생 | 해당 연결의 polling/외부 쓰기를 일시 중지하고 원인 점검 |
| Calendar 생성률 또는 중복률 급변 | 자동 Calendar write 차단, 실패·정상 표본 비교 |
| 실행당 비용이 설정 상한 도달 | 추가 모델 호출 정지, checkpoint와 부분 결과 보존 |
| 새 도메인 또는 scope 밖 도구 요청 | 호출 거부, 보안 로그/경보 생성 |
| 푸시 실패 증가 | Calendar 생성은 유지, push만 재시도하고 앱 내 알림 backlog 확인 |
| 센서 통과율·추출 품질의 유의한 하락 | 자동화 범위를 제한하고 이전 템플릿/프롬프트 버전으로 되돌림 |

알림 기준값은 파일럿 기준선을 측정한 뒤 설정한다. 임계값을 넘었을 때 자동 조치는 외부 쓰기를 안전하게 멈추는 방향으로 제한한다.

## 6. 실패를 영구 개선으로 전환

장애마다 입력 fixture, 실행 ID/trace ID, 영향, 실패 계층, 복구 결과를 남긴다. 동일 실패를 재현하고 가장 적합한 가이드·센서·루프·메모리·권한·관찰 변경을 추가한 다음 재현 케이스와 회귀 검증을 수행한다. 임시 프롬프트 수정만으로 장애를 종료 처리하지 않는다.

## 부록 A. 호스팅 필수 로깅 가이드 (구 docs/harness/06_호스팅_필수_로깅.md)

> 원본: `docs/harness/06_호스팅_필수_로깅.md`. docs/harness/는 폐기되고 본 문서로 통합됨.

jobMate를 Vercel(API) + cron-job.org + PostgreSQL 구성으로 호스팅할 때
**반드시 남겨야 할 로그**의 기준 문서.
기능 작업 시 이 목록을 기준으로 로깅을 추가·유지한다.

### 공통 규칙

- 로거 네임스페이스: `jobmate.*` (`configure_logging`이 handler/레벨 관리,
  `JOBMATE_MODE=debug`→DEBUG, `release`→INFO).
- **절대 로깅 금지**: API 키·토큰·OAuth credential·push endpoint 원문·
  이메일 본문·사용자 메시지 원문. push endpoint는 SHA256 지문 12자만
  (`adapters/push.py::_fingerprint` 패턴 참조).
- 모든 외부 호출 실패는 `logger.warning` 이상 + 에러 유형/HTTP 상태까지만.
  예외는 `logger.exception`으로 스택 보존.
- 로그는 stdout/stderr 한 줄 포맷 — Vercel/Render 등 호스팅 로그 수집기와 호환.
- **레벨 운용**: `JOBMATE_MODE=debug`는 DEBUG까지 전부 출력(스테이지 상세,
  토큰 갱신 성공, push 발송 성공 등 진단용). `release`는
  INFO 이상 — 아래 표의 WARNING/ERROR와 운영 필수 INFO(기동, run 완료,
  폴링 건수, job 생명주기, cronjob 생성/갱신)만 남는다.

### 호스팅 환경별 수집

- **Vercel**: 함수 로그는 invocation 단위. `_automation_loop` 스레드는
  서버리스에서 동작하지 않으므로 Vercel에서는 `/cron/tick` 호출 로그가
  유일한 생존 신호 — tick 수신/실행 결과를 반드시 INFO로 남긴다.
- **Render/Railway/VPS**: stdout이 그대로 로그. 상주 프로세스는 FastAPI 앱
  하나뿐이므로 앱 기동 로그와 `_automation_loop`의 주기 로그가 프로세스
  생존 확인 수단이다(별도 코딩 워커는 제거됨).
- **cron-job.org**: job 실행 이력은 콘솔에서 확인. job이 호출하는 엔드포인트가
  401/5xx를 반환하면 job은 "성공"으로 기록되므로, API 측 401 경고 로그가
  유일한 감지 수단이다.

### 알림(Alert) 권장 기준

- ERROR 이상 로그 → 즉시 알림 (worker 루프 예외, DB 연결 실패, dispatch 실패)
- WARNING 반복(동일 메시지 N회/분) → 알림 (인증 실패 폭주, 폴링 연속 실패)
- run 최종 실패/재시도 소진 → 알림 (run 영구 실패 임박)

### 작업 시 체크리스트

새 기능/수정 작업 시:

1. 새 외부 호출·비동기 작업·재시도 경로를 추가했는가 → 실패/성공 로그 추가
2. 로그에 토큰·이메일 본문·메시지 원문·push endpoint 원문이 없는가
3. 장기 루프/워커에 진행 상황 INFO 로그가 있는가 (무로그 장기 실행 금지)
4. `JOBMATE_MODE=release`에서 DEBUG가 숨겨져도 운영에 필요한 INFO가 남는가
