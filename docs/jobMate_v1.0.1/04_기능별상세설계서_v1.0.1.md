## 2. 업무 템플릿 실행

### 입력

템플릿 ID와 버전, 필수 텍스트/파일 참조, 실행 옵션. API가 권한과 schema를 검증하고 `WorkflowRun`을 만든다.

### 처리

LangGraph가 고정된 그래프를 실행한다. 각 노드는 제한된 도구만 사용하고 JSON schema로 출력을 검증한다. 실패는 해당 노드에 기록하고 정책상 재시도 가능한 오류만 다시 실행한다.

### 검수 기준

- 실행 상세에 노드별 대기·진행·완료·오류 상태가 표시된다.
- 사용자는 본인이 접근 가능한 조직의 결과만 볼 수 있다.
- 승인 단계는 승인자 결정 전 후속 노드를 진행하지 않는다.

## 3. Gmail 일정 자동화

### 검색

사용자 OAuth 연결과 활성화된 일정 자동화 규칙이 있어야 한다. Gmail API로 처리 시점 이후의 메일을 검색한다. 초기 검색 기간과 polling 간격은 운영 설정값으로 두며 사용자에게 연결 상태와 마지막 검색 시각을 표시한다.

### 추출·검증

에이전트 출력 필드: `summary`, `title`, `start_at`, `end_at`, `timezone`, `location`, `attendees`, `source_message_id`, `source_url`, `confidence`. 날짜와 시간대를 정규화하며, 종료가 시작보다 빠르거나 필수 시간이 모호하면 생성하지 않는다. confidence threshold는 파일럿 검증 후 설정한다.

### Calendar 등록

유효한 일정은 Calendar API에 자동 생성한다. 원본 메시지 ID와 계정 ID 조합을 unique 처리 키로 사용한다. 성공 응답의 event ID를 저장한다. API timeout은 생성 실패로 단정하지 않고 Calendar에서 idempotency marker를 조회한 후 재시도한다.

### 푸시·이동

Calendar 저장이 확인되면 즉시 웹 푸시 알림을 큐에 넣는다. 클릭 URL은 `https://mail.google.com/mail/u/{account}/#all/{messageId}` 형식의 원본 메일 링크를 사용한다. 웹 푸시의 `notificationclick`에서 링크를 새 창 또는 기존 창으로 열고, 구독 권한이 없으면 앱 내 알림함에 같은 알림을 남긴다.

### 예외

| 경우 | 처리 |
|---|---|
| 정보가 불명확/신뢰 점수 부족 | `needs_review`로 보류, 자동 등록·푸시 미발송 |
| 이미 처리된 원본 메시지 | 중복 생성을 건너뛰고 기존 이벤트 참조 |
| OAuth 취소/철회 | 감지 중단, 사용자에게 연결 오류 표시 |
| Gmail 일시 오류 | backoff 재시도 후 실패 큐 기록 |
| Calendar 생성 결과 불명 | marker/event 검색 후 중복 없이 복구 |
| Calendar 등록 후 푸시 실패 | 이벤트 유지, 푸시만 재시도, 앱 내 알림 표시 |
| 원본 메일 삭제 또는 접근 권한 없음 | 푸시는 열리지만 Google이 접근 오류를 표시할 수 있음; 앱 알림에 발신자/제목 최소 표시 |

## 4. 접근성·사용성

알림 권한 요청은 맥락과 효용을 설명한 뒤 사용자 동작으로 요청한다. 권한이 거부되어도 Calendar 연동과 일정 자동 등록은 동작하며 앱 내 알림 목록에서 이력을 확인한다. 상태는 색상만으로 표시하지 않는다.

### 1. 모델 제공자와 debug/release 라우팅

- `ModelConfig.provider`: `openai_compat`(기본) | `codex`
- `CompositeLLM`이 provider별 클라이언트로 디스패치
- `CodexResponsesLLM`: `~/.codex/auth.json`의 ChatGPT 구독 OAuth 토큰 사용.
  `chatgpt.com/backend-api/codex/responses`에 SSE 스트리밍 필수(`stream:true`).
  액세스 토큰 만료 시 `auth.openai.com/oauth/token`으로 refresh 후 auth.json 갱신.
- `Settings.mode`:
  - `debug` — 모든 역할/티어가 `default_model`(gemini-3.5-flash-lite)로 강제
  - `release` — default 티어는 gemini, important 티어는 `important_model`(codex, `gpt-5.6-sol`)
- 역할별 오버라이드 `role_models`는 양쪽 모드에서 유지.
- `configure_logging(settings)`이 mode별 로거 레벨을 설정한다 —
  app/cli 시작 시 호출. `debug`=DEBUG, `release`=INFO (DEBUG 출력 숨김).
  토큰·API 키·push endpoint 등 비밀값은 어느 레벨에서도 로깅하지 않는다
  (push 실패 로그는 endpoint 원문 대신 SHA256 지문 12자만 기록).

### 2. calendar-agent 이식 (`gmail_calendar` v0.2.0)

멀티채널 공통 소스 컨텍스트: `source_provider` ∈ `gmail|slack|telegram`,
`source_id`, `thread_id`, `source_url`, `message_text`.

단계: `extract(LLM) → validate(결정적) → conflict_check(Calendar 검색) →
register(멱등) → notify`

- Slack: `POST /api/v1/webhooks/slack` — `X-Slack-Signature` HMAC 검증,
  5분 타임스탬프 윈도우, `url_verification` 챌린지, 채널 allowlist
- Telegram: `POST /api/v1/webhooks/telegram` — secret-token 헤더 검증, 봇 메시지 무시
- 수신함: `message_extractions` 테이블, `(provider, source_id)` 멱등,
  `processing_status` pending/processed/failed + 재시도 백오프(최대 5회)
- 워커(`_automation_loop`, `JOBMATE_WORKER_INTERVAL_SECONDS`):
  pending 메시지 → run 생성·동기 실행, due `notification_jobs` 발송,
  `gmail_calendar` 자동화 활성 시 주기적 Gmail 폴링, KST 06시 이후 radar 일일 수집
- `scheduled_events`: provider-aware event_key, status, version
- Calendar 충돌/자기중복은 `CalendarClient.search_events` 사전 검색으로 판별.
  타임아웃 후 불확실 쓰기는 marker 검색으로 복구(이벤트 재생성 없음).
- 알림 실패해도 캘린더 링크 보존, 사전 알림은 `notification_jobs`에 예약.

신규 엔드포인트: `/webhooks/slack`, `/webhooks/telegram`, `/messages`,
`/messages/{provider}/{id}/retry`, `/listeners/status`, `/events`,
`/events/{id}/review`, `/notification-jobs`, `/gmail-calendar/poll`(어댑터 필요)

- **needs_review 검토 흐름**: `gmail_validate`가 검증 실패 후보를
  `scheduled_events(status="needs_review")`로 영속화. 대시보드 Calendar 뷰 상단에
  "검토 필요" 카드(제목/시작/종료 수정 입력 + 승인·등록/거부)를 표시.
  `POST /api/v1/events/{id}/review` — `reject`는 `rejected` 전이,
  `approve`는 수정값 병합 → `validate_event` 재검증 → 통과 시
  `find_by_marker("review:{id}")` 중복 확인 후 `create_event` →
  `registered` + `calendar_event_id` 저장. 재검증 실패 시 422 + 사유 갱신,
  캘린더 어댑터 없으면 503.

### 3. skillRadar 이식 (`skill_radar` v0.1.0)

단계: `collect → dedupe → summarize(LLM, default 티어) → rank → approve(사람) → publish`

- `radar_collect`: `queries.json`의 플랫폼별 GitHub Search 쿼리,
  `GitHubClient` 프로토콜(GitHubAPI 실구현 + FakeGitHub). README는
  `Accept: application/vnd.github.raw`로 fetch, base64 폴백.
- `radar_dedupe`: `full_name` 중복, fork, archived 제외.
- `radar_summarize`: `RepoSummary`(en/zh/ko 요약, taxonomy+confidence,
  summary_status). content_hash 캐시로 재호출 방지, 실패 시 메타데이터 폴백.
  LLM 실패는 audit 기록 후 계속 진행.
- `radar_rank`: stars + 일일 증가량 + 라이선스 + taxonomy 신뢰도 점수.
- `radar_publish`: 승인 전 reject면 스냅샷 미작성. `radar_snapshots`/
  `radar_items`에 일별 플랫폼 스냅샷 저장(같은 날 재실행 시 갱신).

엔드포인트: `GET /radar/trending?platform&date&lang`, `GET /radar/dates`,
`POST /radar/refresh {platforms, force}` (플랫폼당 run 생성)

Web Push: `GET /push/vapid-key`, `POST /push/subscribe|unsubscribe`,
`GET /sw.js` — gmail_calendar notify 단계에서 `webpush` 어댑터가
저장된 구독 전체로 발송(VAPID_PRIVATE_KEY 필요, 404/410 구독 자동 삭제).
푸시 클릭(`notificationclick`)은 payload의 `url`로 이동 — gmail 유래
알림은 `https://mail.google.com/mail/u/0/#all/{message_id}` 원문 링크가
들어간다(`sensors/gmail_url.build_gmail_url` + `is_safe_source_url` 검증).
알림 예약 발송(`_process_due_notification_jobs`)도 gmail 이벤트면 동일
링크를 source_url로 전달한다.

### 5. 상용 전환(Django) 시 이관 대상

- `api/` 계층(routers/ + appctx.py)의 엔드포인트/워커 → Django views + Celery/RQ 태스크
- `store/` 계층(db.py Store + schema_sqlite/schema_pg + migrations) → Django ORM/PostgreSQL (스키마는 그대로 이관 가능)
- LangGraph 체크포인터 → PostgresSaver
- 워크플로/함수/센서는 프레임워크 비의존이라 그대로 재사용

### 6. Vercel 배포 / PostgreSQL

- `app.py`(루트)가 Vercel Python entrypoint — `src/`를 sys.path에 추가 후
  `jobmate.api.serverless:app`(`create_app()` 인스턴스)을 노출.
- DB: `Store`는 인자가 `postgres://`/`postgresql://` DSN이면 psycopg3 +
  `schema_pg.py`의 `SCHEMA_PG`로 PostgreSQL을, 아니면 `schema_sqlite.py`의 `SCHEMA`+SQLite 파일을 사용.
  `JOBMATE_DATABASE_URL` 또는 Vercel Postgres의 `POSTGRES_URL`/
  `POSTGRES_PRISMA_URL`(자동 인식)이 있으면 PG 사용. PG DSN이 없으면
  `JOBMATE_DB_PATH` SQLite, Vercel에서는 `/tmp/jobmate.db`(인스턴스 임시 —
  WARNING 로그 발생, 영속성 없음).
  SQL은 `?`→`%s`, `INSERT OR IGNORE`→`ON CONFLICT DO NOTHING`으로 번역되는
  단일 코드베이스.
- 서버리스에서는 lifespan의 자동화 스레드를 띄우지 않음(`VERCEL` env 감지).
  대신 `GET|POST /api/v1/cron/tick`이 `_automation_loop` 1사이클을 실행 —
  `vercel.json`의 cron이 주기 호출. `CRON_SECRET` env가 있으면
  `Authorization: Bearer <CRON_SECRET>` 검증(Vercel Cron이 자동 부착).
- 주의: Vercel Hobby 플랜 cron은 하루 1회 제한 — 분 단위 폴링이 필요하면
  외부 스케줄러(GitHub Actions 등)로 tick을 호출하거나 Pro 플랜 필요.
- Google 토큰: 로컬은 `JOBMATE_{GMAIL,CALENDAR}_TOKEN_PATH` 파일.
  Vercel처럼 파일이 없는 환경은 `JOBMATE_{GMAIL,CALENDAR}_TOKEN_JSON` env에
  토큰 JSON 전체를 넣으면 부팅 시 임시 파일(0600)로 materialize해 어댑터에
  주입한다. 토큰 경로만 설정되고 파일이 없으면 해당 어댑터는 생성되지 않고
  WARNING 로그를 남긴다(앱 크래시 없음).

### 7. 이메일 3줄 요약 카드 (`/api/v1/email/check`)

- 외부 스케줄러(cron-job.org 등)가 30분마다 `POST /api/v1/email/check` 호출.
  본문 `{"limit": 5, "query": "in:inbox"}` — limit 최대 20.
- `adapters["gmail"]`(GoogleGmail)로 최근 메일을 읽고 메시지별 LLM 3줄 요약을
  생성해 `email_summaries` 테이블에 upsert. 결과는 `GET /api/v1/email/summaries`
  로 조회하며 Gmail Checker 뷰가 우선 표시(없으면 message_extractions 폴백).
- 인증: `Authorization: Bearer {CRON_SECRET|JOBMATE_CRON_SECRET}` 또는 lead
  이상 세션/권한 — 둘 다 없으면 403 (`?secret=` 쿼리 파라미터는 폐기 —
  로그/히스토리 노출 방지).
- `GET /api/v1/email/summaries` — 복호화된 메일 제목·발신자·요약을 반환하므로
  lead 이상 게이트 적용(member는 403). `messages.source_text` 마스킹과
  동일한 민감도 기준.
- Gmail API 오류 시 502 + `{"ok": false, "error": ...}` 반환.

### 8. LangSmith 관측성

- `langsmith>=0.15` 명시 의존성. `LANGSMITH_API_KEY` env가 있고
  `JOBMATE_LANGSMITH_TRACING`(기본 true)이면 `configure_langsmith()`가
  `LANGCHAIN_TRACING_V2`/`LANGCHAIN_API_KEY`/`LANGCHAIN_PROJECT`
  (`JOBMATE_LANGSMITH_PROJECT`, 기본 `jobmate`)를 설정 — app/cli 시작 시 호출.
- LangGraph 워크플로 실행은 langsmith 내장 연동으로 자동 트레이스.
- `CompositeLLM.complete`는 tracing env 감지 시 `langsmith.traceable`
  (`run_type="llm"`, name `jobmate.llm.complete`)로 래핑되어 OpenAI-compat/
  Codex 모든 LLM 호출이 별도 run으로 기록됨. 키 없으면 래핑하지 않음.
- `engine/trace.py`의 `job_traceable`(백그라운드 잡 8개 계측)은
  `JOBMATE_LANGSMITH_SAMPLE_RATE`(0~1, 기본 1.0)로 호출당 샘플링 —
  LangSmith 비용/저장량 관리용. 민감 키(토큰/이메일 원문 등)는
  `_REDACT_KEY_RE`로 `***REDACTED***` 마스킹.

#### Agent Insights (`GET /api/v1/llm-monitor/stats?days=30`)

`store.llm_stats(monthly_budget=)` 집계 — runs+stage_runs 조인. v2 사이드바
"Agent Insights" 뷰(구 LLM 모니터)가 소비. 응답:
`{runs_total, by_status, terminal_runs, failed_runs, error_rate_pct,
latency_s{p50,p95,p99,avg,max,samples}, stage_latency_s, tokens{in,out,
total,avg_per_run,runs_with_tokens}, models[], prompt_versions[],
prompt_version_stats[], stage_model_matrix[], by_stage[], by_workflow[],
stage_calls, stage_failures, stage_failure_rate_pct,
retry{calls,tokens,token_pct,failed_stage_tokens,attempts_hist},
tokens_ratio{input_pct,output_pct},
budget{month,monthly_tokens,budget_max,used_pct,alert}|null,
approval_backlog{waiting,oldest_wait_s,total_wait_s},
daily[{date,runs,tokens,errors}], recent_failures[{...,trace_id}],
langsmith{enabled,project,sample_rate}}`.
- 지연시간: 종료 상태 run의 `updated_at-created_at` 백분위(최근접 순위법)
- `by_stage`: stage_key별 호출/실패율/토큰/p50·p95·avg 지연/주요 모델 — p95 내림차순(병목)
- `stage_model_matrix`: stage×model별 호출/토큰/실패율 — 모델 다운그레이드 판단용
- `prompt_version_stats`: 프롬프트 버전별 비용·실패율 비교
- `retry`: attempt>1 재시도가 태운 토큰(비용 낭비) + attempts_hist 분포
- `by_workflow`: 워크플로별 runs/실패/평균시간/총토큰/run당 토큰(단가)
- `budget`: `monthly_budget`(settings.budget_max_tokens) 전달 시 당월 stage 토큰
  합계와 사용률 — used_pct≥80이면 `alert=true` + 인박스 `budget_alert` 등록
  (dedupe_key `llm_budget_{YYYY-MM}`으로 월 1회)

### 9. Agent-Office 뷰 (`dev_review` 스테이지 시각화)

- 대시보드 사이드바 "Agent Command" 메뉴(뷰 키 `office`): `dev_review`
  workflow의 run을 선택해 단계 스테이지를 3D 보드 노드로 표시한다.
- 노드 상태는 `stage_runs.status`(`pending`/`running`/`succeeded`/`failed`/
  `skipped`)에서 매핑하고, run 단위 상태(`queued`/`running`/
  `waiting_approval`/`waiting_review`/`needs_human`/`completed`/`failed`/
  `rejected`/`budget_exhausted`/`cancelled`)는 ORCH(오케스트레이터) 노드
  테두리와 활성 run 선택에 사용한다. 실행 중 스테이지에는 진행 애니메이션,
  attempt>1에는 재시도 표시(×N)를 붙인다.
- 데이터는 기존 runs API를 재사용한다 — `GET /api/v1/runs?workflow=dev_review&limit=50`
  (`workflow` 쿼리 파라미터로 workflow_key 필터, 미지정 시 전체 workflow 대상
  기본 limit=50 동작 유지)으로 dev_review run 목록을 고르고
  `GET /api/v1/runs/{id}`로 stages(전체 stage_runs)·토큰 사용량·
  이벤트 로그를 주기 폴링한다. run 상태가 바뀌면 선택 중인 상세 패널도
  다시 렌더링한다.
- `waiting_approval` run에서 승인 단계(사람 승인) 노드를 선택하면
  승인/거절 버튼을 표시 — `POST /api/v1/runs/{id}/approve`
  `{decision: "approve"|"reject"}` 호출. run이 waiting_approval을 벗어나면
  버튼은 자동으로 숨겨지고, 클릭 즉시 비활성화해 더블클릭 중복 발사를 막는다.
- 노드 클릭 시 우측 상세 패널에 스테이지 설명·상태·소요시간·토큰 합계와
  해당 run의 이벤트 로그를 표시한다. 헤더에는 진행률·총 토큰·경과 시간을
  요약한다(토큰은 모든 시도 attempt를 합산).
- 별도 코딩 job 큐/워커/SSE는 없다 — 코딩 에이전트 기능은 제거됐고,
  dev_review run 실행은 API 서버의 run 실행 경로(`_automation_loop`/tick 또는
  동기 `jobmate run`)가 담당한다.
- **모드 전환**: Agent-Office 뷰 상단에 `워크플로 | 세션` 탭과
  `3D 보드 | 스프라이트 사무실` 토글이 있다.
  - 스프라이트 사무실: `claude-3d-frog-office`(MIT) 포팅 아이소메트릭
    캔버스 — `src/jobmate/api/static/legacy/office/`의 JS/CSS/webp (레거시 UI 전용, v2는 `v2/src/features/office/sprites/`). 최초 선택 시
    lazy 로드. `jobmate-bridge.js`가 `officeState`를 people 계약으로 변환
    (stage running→working, waiting_approval→decision, 그 외→rest).
  - 세션 탭: 스프라이트 엔진을 재사용하되 provider를
    `GET /api/v1/agent-sessions`로 교체 — 로컬 `jobmate agent-bridge`가
    push한 Claude/Codex/Gemini/Devin 세션이 캐릭터로 표시된다.

#### 9.1 에이전트 세션 (`agent_sessions` + `agent-bridge`)

- `agent_sessions` 테이블: tool/session_key UNIQUE, status
  (`working`/`decision`/`rest`/`ended`), doing/ask 요약(≤80자),
  project/title, machine, tokens_in/tokens_out(누적, MAX 갱신),
  last_event_at. 대화 본문은 저장하지 않는다.
- `POST /api/v1/agent-sessions` — 머신 push 전용. `JOBMATE_API_KEY`가
  설정된 경우 API 키 인증 필수(세션 쿠키만으로는 403). body:
  `{tool, session_key, status, project?, title?, doing?, ask?, event_at?,
  machine?, tokens_in?, tokens_out?, ended_summary?, artifacts?}`.
  `machine`은 브릿지가 보내는 짧은 호스트명, `tokens_*`는 세션 누적
  토큰 카운터(서버는 MAX로만 갱신 — 역행 push는 무시).
- `GET /api/v1/agent-sessions?limit=50&include_ended=&machine=` —
  `ended` 제외(기본), last_event_at 내림차순. `machine` 지정 시 해당
  머신 세션만 정확 일치 필터. 각 항목에 계산 필드가 붙는다:
  - `health`: `ended`(status=ended) / `stale`(working·decision인데
    last_event_at‖updated_at이 300초 초과) / `long_idle`(rest인데
    43200초=12h 초과) / `active`(그 외). Python 계산.
  - `est_cost_usd`: tokens_in/out을 1M 토큰당 가격표로 환산한 USD
    추정치. tool별 오버라이드(codex 저가, claude/gemini 등) + default
    {input:3.0, output:15.0}. 토큰이 둘 다 없으면 null.
    세션별 비용은 로깅하지 않는다.
- `GET /api/v1/agent-sessions/stats?since=YYYY-MM-DD` — 응답
  `{tools: {...}, hourly: [{hour:0..23, working_seconds:int}]}`.
  `since`는 로컬 날짜(기본 오늘, 형식 오류 시 422). `hourly`은
  agent_session_events의 working/decision 이벤트 간격(event_at →
  다음 이벤트 created_at, 로컬 날짜로 클립, 시간 경계 분할 합산)을
  로컬 시간 버킷에 합산한 값.
- `GET /api/v1/agent-sessions/{tool}/{session_key}/history` — 상태 전이
  이벤트 시간순(최대 500).
- `jobmate agent-bridge [--url URL] [--interval 15] [--once]` — 로컬
  수집기. `~/.claude/projects`, `~/.codex/sessions`(jsonl.zst),
  `~/.gemini/antigravity-cli/conversations`(sqlite),
  `~/.local/share/devin/cli`(transcripts+locks)를 스캔해 상태를 계산,
  변경분/60초 하트비트만 push. 모든 push에 `machine`(짧은 호스트명)을
  포함한다. 토큰 누적치는 claude(assistant usage 합산)와
  codex(token_count의 total_token_usage 최신값)에서만 수집하고
  gemini/devin은 null로 둔다 — 스캔 실패는 세션 수집을 깨지 않는다.
  인증은 `JOBMATE_API_KEY` env, 서버 주소는 `--url` 또는 `JOBMATE_URL`
  env(기본 `http://127.0.0.1:8000`). 상태 판정은 파일 mtime+마지막
  이벤트 휴리스틱이며, 미완료 일반 도구 호출은 `working`,
  `request_user_input`/`ask_user_question`만 `decision`으로 판정한다.
- **알림 규칙(`notify_rules`)**: 세션 attention 웹푸시( decision 진입
  또는 ask 설정 전이 시 1회, 10분 레이트리밋)에 적용되는 prefs 필터.
  `automation_state`의 `prefs` 키 JSON 안 `notify_rules` 리스트:
  `[{"tool": str|null, "project": str|null, "statuses": [str]}]`.
  - 비어 있거나 없으면 모든 세션에 푸시(기존 동작).
  - 규칙이 있으면 규칙 중 하나라도 `tool`(null=전체)·`project`
    (null=전체) 일치 AND `statuses`에 세션의 유효 상태가 포함될 때만
    푸시. 유효 상태는 `ask`가 비어 있지 않으면 `"ask"`, 아니면
    `status`(working/decision/rest/ended). 매칭 안 되는 세션은
    조용히 스킵(debug 로그만).
  - `GET/POST /api/v1/settings`로 왕복 가능 — POST body에
    `notify_rules`를 포함하면 검증 후 저장(최대 100개 규칙,
    statuses는 문자열 리스트 필수).

### 9.5 워크플로 변형·스케줄·통계·diff/감사 조회

#### 워크플로 템플릿 (`GET /api/v1/workflows`)

`dev_review` 파이프라인의 단계 부분집합 변형 4종이 `WORKFLOWS`에 등록됐다
(`workflows/code_pipelines.py`). 모두 `analysis→implement→auto_checks` 이후
리뷰 단계만 다르며 `implement` stage key는 동일해 diff 미리보기가 공통 동작한다.

| key | 단계 |
|---|---|
| `dev_review` | analysis→implement→auto_checks→security→code_review→qa→approval |
| `bugfix` | analysis→implement→auto_checks→security→approval |
| `refactor` | analysis→implement→auto_checks→code_review→approval |
| `docs_update` | analysis→implement→auto_checks→approval |
| `dependency_update` | analysis→implement→auto_checks→security→code_review→approval |
| `gmail_calendar` / `skill_radar` | 기존 워크플로 (변경 없음) |

`GET /api/v1/workflows` 응답 항목: `{key, version, description, stages:[{key,kind,description,agent,function}]}`.
`POST /api/v1/runs`는 `WORKFLOWS`에 등록된 모든 key를 그대로 받는다.

#### 에이전트/스테이지 모델 오버라이드 (`JOBMATE_AGENT_MODELS`)

JSON 객체로 agent 키(`analysis|implementer|security|reviewer|qa|extractor`) 또는
stage 키(`analysis|implement|auto_checks|security|code_review|qa|approval` 등)를
모델명에 매핑한다. 예: `{"security":"gpt-5","qa":"claude-sonnet"}`.
`build_registry`가 `agent.model.model`만 교체하고 `ModelConfig`의 나머지
필드(base_url/api_key_env/provider/temperature 등)는 유지한다. 잘못된 JSON은
경고 후 무시.

#### Run 통계 (`GET /api/v1/runs/stats?workflow=&days=30`)

`runs`+`stage_runs` 조인 집계(SQLite/PostgreSQL 공용 SQL). 응답:
`{workflow, days, runs, succeeded, failed, running, waiting_approval,
avg_duration_s, total_tokens_in, total_tokens_out, stage_failures, daily}`.
- `succeeded`=completed, `failed`=failed/rejected/budget_exhausted/needs_human/cancelled,
  `running`=queued+running, `waiting_approval`=waiting_approval (나머지 상태는 runs에만 포함)
- `avg_duration_s`: 종료 상태 run의 `updated_at-created_at` 평균(초), 없으면 null
- `stage_failures`: run×stage별 최신 attempt가 failed인 건수를 stage_key별 집계
- `daily`: 윈도우 전 일자(UTC) `{date,runs,tokens}` — runs는 created_at 일자,
  tokens는 stage_runs.started_at 일자 기준 in+out 합

#### Approval diff 미리보기 (`GET /api/v1/runs/{run_id}/diff`)

implement 단계의 succeeded stage_run 출력을 최신 시도 순으로 합쳐
`ChangeProposal.diff`(unified diff)를 파일 단위로 분해한다.
응답 `{files:[{path,status,additions,deletions,diff}], summary}` —
status는 added/deleted/renamed/modified. implement 산출물이 없으면
`files: []`. run이 없으면 404.

#### Run 감사 로그 (`GET /api/v1/runs/{run_id}/audit`)

`audit_events`를 run_id로 조회해 최신순 최대 200건 반환 —
`[{id, actor, action, object_ref, detail, created_at}]` (detail은 본문/토큰 없는
메타데이터만). `run_detail`의 `audit` 필드와 동일 데이터의 역순 뷰.

#### 주기적 workflow 실행 (`/api/v1/schedules`)

`workflow_schedules` 테이블(SQLite/PostgreSQL 양쪽 스키마):
`id, workflow, input(JSON), interval_minutes, enabled, last_run_at, next_run_at, created_at`.

- `GET /api/v1/schedules` — 전체 목록 (input은 파싱된 객체, enabled는 bool)
- `POST /api/v1/schedules` — `{workflow, input?, interval_minutes}`.
  workflow는 `WORKFLOWS` 등록 key만 허용(아니면 404), `interval_minutes>=5`
  (미만 시 422). `next_run_at = now + interval`로 생성, 201 + 스케줄 객체.
- `POST /api/v1/schedules/{id}/toggle` — `{enabled: bool}`.
  활성화 시 `next_run_at`을 `now + interval`로 재계산. 없으면 404.
- `DELETE /api/v1/schedules/{id}` — 삭제, 없으면 404.

발사 경로: `_automation_loop`와 `/api/v1/cron/tick`이 매 사이클
`_process_due_schedules`를 호출 — `enabled=1 AND next_run_at<=now`인
스케줄마다 run을 생성(`store.create_run` → 일반 run과 동일하게 `/runs`에 표시)
하고 `last_run_at`/`next_run_at`을 갱신한다. run audit에 `scheduled_run`
이벤트(object_ref=schedule id)가 남는다. input의 `task`가 없으면
`"scheduled <workflow>"`를 사용한다. 스케줄 CRUD·발사 모두 `audit_events`에
기록되며, 스케줄 입력은 run input으로 그대로 전달된다(비밀값 입력 금지).

#### 승인 메타데이터

`approvals` 테이블에 `created_at` 컬럼 추가(양쪽 스키마 + 기존 DB는
`_ensure_columns` 마이그레이션). `GET /api/v1/runs/{id}`의 approvals 항목에
`created_at`이 포함된다(구 행은 `decided_at`으로 폴백). 승인 "대기" 시작
시각은 approval stage의 `stage_runs.started_at`(RUNNING 유지) 또는
`/audit`의 `waiting_approval` 이벤트로 확인한다.

### 10. 대시보드 설정 (`/api/v1/settings`)

- 헤더 ⚙ 버튼 → 설정 다이얼로그. `automation_state` 테이블 `prefs` 키에 JSON 저장.
- 항목: `gmail_check_minutes`(30/60 — `_maybe_poll_gmail` 폴링 간격에 적용,
  email/check 외부 cron 주기는 cron-job.org/Vercel cron에서 별도 설정),
  `radar_interval`(daily/weekly — `_maybe_daily_radar`가 마지막 수집 후
  7일 미만이면 스킵),
  `notify_rules`(에이전트 세션 어텐션 푸시 필터 — §9.1 참조).
- GET/POST `/api/v1/settings` — 검증 실패 시 422.
- POST 시 `_sync_cronjob`이 cron-job.org 실제 스케줄도 갱신
  (`adapters/cronjob.py`, `PATCH /jobs/{id}`):
  - `JOBMATE_CRONJOB_JOB_ID` — 이메일 체크 job. `gmail_check_minutes`
    30→`minutes:[0,30]`, 60→`minutes:[0]` (Asia/Seoul).
  - `JOBMATE_CRONJOB_RADAR_JOB_ID` — 레이더 수집 job. daily→매일 06:00,
    weekly→매주 월요일 06:00.
  - **자동 생성**: job id가 없고 `CRONJOB_ORG_API_KEY` +
    `JOBMATE_PUBLIC_BASE_URL`이 설정돼 있으면 `PUT /jobs`로 job을 생성하고
    반환된 id를 prefs(`cronjob_email_job_id`/`cronjob_radar_job_id`)에 저장.
    이후 설정 변경은 기존 job에 `PATCH`만 수행(중복 생성 없음).
    생성되는 job은 `POST {PUBLIC_BASE_URL}/api/v1/email/check`
    (`{"limit":5}`)와 `POST .../api/v1/radar/refresh`(`{"force":true}`)를
    호출하며, `JOBMATE_API_KEY` 설정 시 `X-API-Key` 헤더를 함께 보낸다.
  - `CRONJOB_ORG_API_KEY`는 콘솔 Settings에서 발급. job id/API 키 미설정 시
    `skipped`, API 실패 시 `error:` 상태 문자열을 응답 `cronjob` 필드로
    반환 — 로컬 저장은 항상 성공, UI가 상태를 표시한다.

### 11. 보안 (`security.py` + API 미들웨어)

- **API 키 인증**: `JOBMATE_API_KEY` 설정 시 `/api/*` 전체에
  `X-API-Key` 또는 `Authorization: Bearer` 요구. 예외: `/api/v1/health`,
  `/api/v1/webhooks/*`(자체 서명 검증). 키와 허용 이메일 목록이 모두 없고
  Vercel이 아닐 때만 인증 비활성(로컬 개발).
  프론트는 localStorage `jobmate_api_key`를 자동 첨부하고 401 시 1회 입력
  프롬프트 후 재시도한다.
- **저장 데이터 암호화**: Fernet(`cryptography`). 키 우선순위
  `JOBMATE_ENCRYPTION_KEY` → `JOBMATE_API_KEY` → `CRON_SECRET` →
  `JOBMATE_CRON_SECRET`. 암호문은 `enc:v1:` 접두사, 키 없으면 평문 저장.
  적용 필드: `push_subscriptions.keys_json`, `email_summaries`의
  `subject`/`sender`/`summary` — store 계층에서 저장 시 암호화·조회 시
  복호화해 API 응답 형태는 동일하다.
- **응답 헤더**: 모든 응답에 `X-Content-Type-Options: nosniff`,
  `X-Frame-Options: DENY`, `Referrer-Policy: no-referrer`,
  `Permissions-Policy`(camera/mic/geo 차단) 부여.
- 참고: TLS 종료는 배포 계층(Vercel 등) 책임. Google OAuth 토큰 파일은
  파일 권한(0600)으로 보호되며 DB 암호화 대상이 아니다.

#### 11.1 2026-11-23 보안 수정

- `JOBMATE_ALLOWED_EMAILS`가 설정된 경우에만 비밀번호 가입 시 관리자 API 키를
  요구한다(허용 이메일 입력만으로는 소유권이 검증되지 않음). 미설정 시 공개 가입.
- Google 로그인은 `email_verified=true`가 필요하다. 허용 목록이 설정되면
  목록의 이메일만 로그인 가능. 다른 Google subject가 연결된 기존 계정으로
  로그인할 수 없다. 허용 목록에서 제거한 세션은 즉시 거부한다.
- cron tick은 Vercel 외 환경에서도 설정된 cron secret 또는 API 키를 검증한다.
  Vercel은 전용 cron secret이 필수다.
- Web Push는 HTTPS/443의 FCM, Mozilla, Apple Push, Windows Push 호스트만
  허용한다. 저장 구독도 발송 시 재검증하며 리디렉션을 차단하고 10초 타임아웃을 적용한다.
  실패 로그에는 endpoint가 포함될 수 있는 예외 원문 대신 예외 유형만 남긴다.
- 도구 파일 읽기는 심볼릭 링크를 해석한 실제 경로가 저장소 내부인지 검사한다.
- `deep-translator` 의존성을 제거했다(PYSEC-2022-252). 한국어 번역 폴백은
  기존 HTTPX로 MyMemory API를 호출하고 실패하면 원문을 유지한다.
- Windows의 `chmod(0600)`은 POSIX 권한 보장과 같지 않다. Windows 토큰 파일의
  실제 보호는 NTFS ACL 설정에 달려 있으며 이번 검사에서는 별도 검증하지 않았다.

### 12. 통합 인박스·비용·리포트·메신저·세션 활동 (2026-11-23 추가)

#### 12.1 알림 센터 (`inbox_items`)

- 테이블: `id, kind, title, body, link, read, dedupe_key, created_at`
  (SQLite/PostgreSQL 양쪽 스키마). kind ∈
  `notification|session_attention|approval|schedule|report`.
- `notifications` 테이블은 그대로 유지 — `GET /inbox` 호출 시
  `dedupe_key=notif:{id}`로 `inbox_items`에 **지연 미러링**(멱등,
  읽음 상태는 인박스 항목 기준). 나머지 kind는 이벤트 발생 시 직접 insert.
- dedupe: `upsert_inbox_item(dedupe_key=...)` — 같은 키가 있으면
  title/body/link만 갱신하고 created_at·read는 유지. `reset_read=True`면
  미읽음으로 리셋(승인 재대기용).
- 발생 지점: 세션 decision/ask 전이 → `session:{tool}:{session_key}`,
  run waiting_approval 전이 → `approval:{run_id}`, 스케줄 발사/실패 →
  `schedule:{run_id}`/`schedule-fail:{sid}:{ts}`, 리포트 생성 →
  `report:{id}`.
- 엔드포인트:
  - `GET /api/v1/inbox?limit=50&unread_only=` → `[{id,kind,title,body,link,read,created_at}]`
    최신순 (`read`는 bool).
  - `POST /api/v1/inbox/{id}/read`, `POST /api/v1/inbox/read-all`
    (`{ok,updated}`), `GET /api/v1/inbox/unread-count` → `{count}`.
  - 승인 결정(`POST /runs/{id}/approve` 또는 메신저 `승인해`) 시 해당
    `approval:{run_id}` 인박스 항목을 자동 read 처리.

#### 12.2 비용 대시보드

- `GET /api/v1/usage/summary?days=30` →
  `{total_cost_usd,total_tokens_in,total_tokens_out,by_model:[{model,cost_usd,tokens}],
  by_day:[{date,cost_usd,tokens}],top_sessions:[{tool,session_key,cost_usd}],
  budget_usd,budget_exceeded}`.
- 비용은 `llm_usage` 행에 `jobmate/pricing.py`의 모델별 가격표
  (1M 토큰당 USD, 패밀리 키워드 매칭: claude/codex/gemini/default)를 적용한
  **추정치**다. `top_sessions`는 `agent_sessions.tokens_*`의
  `est_cost_usd` 상위 10개(토큰 없으면 제외).
- `budget_usd`는 prefs `monthly_budget_usd`(POST /settings로 설정,
  GET /settings에도 반환). `budget_exceeded` = UTC 월초 이후 llm_usage
  추정 비용 > 예산.

#### 12.3 자연어 쿼리 (`POST /api/v1/ask`)

- body `{question}`(≤2000자) → `{answer}` (한국어).
- 컨텍스트: run_stats(7d)·agent_session_stats·llm_usage_summary 집계만
  JSON으로 주입(비밀값/원문 없음). `settings.model_for("_ask","default")`
  모델로 `llm.complete` 호출 — MeteredLLM 경유로 사용량 자동 계측.
- 타임아웃 30초. LLM 실패/타임아웃 시 **503** `{"answer":"","error":"llm_unavailable"}`.
- 레이트리밋: 세션 사용자 또는 IP당 UTC 일 20회(인메모리).

#### 12.4 리포트 (`jobmate/reports.py` + `reports` 테이블)

- `build_report(store, kind, settings)` — kind `daily`(1일)/`weekly`(7일)
  + `exec_daily`/`exec_weekly` 임원 리포트(§15.8).
  섹션: `period, runs(집계+daily), sessions(tool별), llm(토큰/비용/모델별),
  approvals.pending, radar.new_items, notable_failures(stage_failures 상위)`.
- 엔드포인트:
  - `GET /api/v1/reports?kind=daily|weekly` — 온디맨드 생성(비저장).
  - `GET /api/v1/reports/latest?kind=` — 저장본 우선, 없으면 온디맨드 생성.
  - `POST /api/v1/reports/generate {kind}` — **admin 전용**, 저장 +
    인박스 `report` + 메신저 알림.
- 자동 생성: `_automation_loop`과 `/cron/tick`이 매 사이클
  `_maybe_generate_reports` 호출 — 최신 리포트가 20h(daily)/7d(weekly)
  이상 지났거나 없으면 생성·저장·인박스·메신저 알림. 실패는 warning 로그.

- 첫 가입 사용자는 자동 admin 승격(`_maybe_first_user_admin`).

#### 12.6 메신저 커맨드 (`jobmate/messenger.py`)

- `parse_command(text)`: `승인해|approve [run_id]`(최신 waiting_approval),

- `notify(text)`: `JOBMATE_SLACK_WEBHOOK_URL` +
  `JOBMATE_TELEGRAM_BOT_TOKEN`/`JOBMATE_TELEGRAM_CHAT_ID` 설정 채널 전체로
  best-effort 발송. waiting_approval 전이와 리포트 생성 시 호출.
- 신규 env: `JOBMATE_SLACK_WEBHOOK_URL`, `JOBMATE_TELEGRAM_BOT_TOKEN`,
  `JOBMATE_TELEGRAM_CHAT_ID`, `JOBMATE_ADMIN_EMAILS` (.env.example 참조).

### 13. 사이드바 뷰 집계 API (읽기 전용, `jobmate/insights.py`)

새 대시보드 사이드바 뷰용 GET 엔드포인트 4개. 모두 `/api/*` 인증 미들웨어와
동일하게 세션 사용자 또는 API 키를 요구하며, 상태를 변경하지 않는다.
집계 로직은 `src/jobmate/insights.py`의 순수 함수에 두고 app.py는 얇게 감싼다.
비용 센터 뷰는 기존 `GET /usage/summary`+`GET /agent-sessions`, 시스템
모니터링은 `GET /health/detail`을 재사용하므로 신규 엔드포인트가 없다.

#### 13.1 인사이트 (`GET /api/v1/insights?days=30`)

- 응답: `{days, sessions:{by_tool,by_project,total_sessions,
  total_working_seconds}, runs:{total,succeeded,failed,running,
  success_rate,avg_duration_s,by_workflow}, cost:{total_cost_usd,
  llm_tokens_in,llm_tokens_out}, top_failures}`.
- `sessions`는 신규 Store 메서드 `session_work_seconds(since_iso)` 기반 —
  `agent_session_events`를 (tool, session_key) 시간순으로 훑어
  `agent_session_stats`와 동일한 간격 추정(working 이벤트→다음 이벤트,
  최대 1시간 캡, 마지막 working은 현재까지)으로 tool/project별
  `sessions`(윈도우 내 고유 session_key 수)·`working_seconds`·
  `decisions`(tool만)를 계산. project는 이벤트 값→`agent_sessions.project`
  →`"(no project)"` 순. 윈도우 이전 이벤트는 로드하지 않아 경계 구간은
  누락될 수 있다(단순화, 문서화된 한계).
- `runs`는 `store.run_stats` 재사용. `success_rate` =
  succeeded/(succeeded+failed), 종료 run 0이면 null. `by_workflow`는
  workflow별 `run_stats` 재호출. `top_failures`는 stage_failures 상위
  (stage_key,count) 정렬 목록.
- `cost`는 `llm_usage_rows(cutoff)` + `pricing.cost_usd` 합계 —
  `/usage/summary`와 동일한 추정 방식.

#### 13.2 자동화 허브 (`GET /api/v1/automation/overview`)

- 응답: `{schedules:[{id,workflow,interval_minutes,enabled,last_run_at,
  next_run_at,input}], notify_rules, cron:{last_tick_at},
  messenger:{slack,telegram}, reports:{last_daily,last_weekly},
  generated_at}`.
- schedules는 `store.list_schedules()` 투영. notify_rules는 prefs 원본.
- `cron.last_tick_at`은 `/health/detail`과 같은 `_last_cron_tick_at()`
  모듈 변수(`_automation_loop`/`cron/tick` 진입 시 갱신).
- `messenger` configured는 env 존재 여부(bool)만 —
  slack=`JOBMATE_SLACK_WEBHOOK_URL`, telegram=`JOBMATE_TELEGRAM_BOT_TOKEN`
  +`JOBMATE_TELEGRAM_CHAT_ID` 모두 설정 시 true. 값 자체는 반환하지 않는다.
- `reports.last_*`는 `store.list_reports` 최신순 첫 daily/weekly의
  created_at.

#### 13.3 아카이브 검색 (`GET /api/v1/archive?q=&kind=&limit=50`)

- 3개 소스를 Python 필터로 통합(데이터셋이 작아 DB 방언 차이 회피):
  - `kind="report"`: `list_reports` → title `일일|주간 리포트 YYYY-MM-DD`,
    snippet `kind · 생성 시각`, link `"reports"`.
  - `kind="run"`: `list_runs` → title `workflow: task 앞 60자`,
    snippet `status · created_at`, link `"runs"`.
  - `kind="session"`: `list_agent_sessions(include_ended=True)` 중
    status=ended이고 ended_summary/artifacts가 있는 행 → title
    `tool · project(또는 session_key 앞 12자)`, snippet=ended_summary
    (없으면 artifacts), link `"office"`.
- `q`는 title+snippet 대소문자 무시 부분 문자열. `kind`는
  report|run|session, 빈 값=전체, 그 외 값은 422.
- 응답 `{items:[{kind,id,title,snippet,created_at,link}], query}` —
  created_at 내림차순, limit 최대 200.

#### 13.4 개발자 상태 (`GET /api/v1/developer/status`)

- 응답 `{integrations:[{name,configured,note}], auth:{google,password,
  api_key,admin_emails_configured}, generated_at}`.
- integrations: gmail/calendar(어댑터 주입 여부), github_radar
  (`settings.github_token_env`이 가리키는 env, 기본 `GITHUB_TOKEN`), slack/telegram(env 존재),
  llm_default(`settings.llm_api_key_env`, 기본 `GEMINI_API_KEY`가 가리키는 env)/llm_codex
  (codex api key env 또는 `~/.codex/auth.json` 존재), codex_bridge
  (`agent_sessions_bridge_info().last_push_at` 존재).
- auth: google=`GOOGLE_CLIENT_ID` 설정, password=항상 true(내장 기능),
  api_key=`JOBMATE_API_KEY` 설정, admin_emails_configured=
  `JOBMATE_ADMIN_EMAILS` 설정. **모든 값은 bool/짧은 설명만 — 비밀값
  원문·토큰·URL은 절대 반환하지 않는다.**

### 14. 대시보드 확장 기능 (2026-11-23 추가)

모두 세션 인증 필요(공개 share 조회 제외). 신규 테이블:
`playbooks`, `run_comments`, `connectors`, `custom_workflows`, `triggers`,
`trigger_fires`, `share_links`, `dashboard_cards`. `runs`에 `created_by` 컬럼 추가.

#### 14.1 플레이북 (`/api/v1/playbooks`)

- `GET` → `{items:[{id,name,workflow,input,created_by,created_at}]}`.
- `POST {name,workflow,input?}` → 201. workflow는 내장+커스텀 모두 허용
  (미등록 시 404). name 공백 불가.
- `DELETE /{id}` → 204.
- `POST /{id}/run` → 202 `{run_id,...}`. `POST /runs`와 동일한 백그라운드
  실행 경로(`_start_run`)를 사용하며 `created_by`에 실행자를 기록한다.

#### 14.2 Run 코멘트 (`/api/v1/runs/{run_id}/comments`)

- `GET` → `{items:[{id,run_id,user_id,user_email,body,created_at}]}` (최신순).
- `POST {body}` → 201. run 존재 확인, body trim 후 1~4000자만 허용(그 외 422).
  `user_email`·`user_id`를 함께 저장한다.

#### 14.3 커넥터 (`/api/v1/connectors`)

- 타입: `github|jira|notion|linear|webhook|json`.
- `POST {type,name,config,enabled?}` → 201. `config`의 token/secret/password/
  api_key 등 민감 키는 Fernet(`enc:v1:`)로 암호화해 저장한다.
  **응답·목록에는 `config`를 포함하지 않고 `has_token`만 노출한다.**
- `GET` → `{items:[{id,type,name,enabled,has_token,last_fetch_at,last_error,created_at}]}`.
- `DELETE /{id}`, `POST /{id}/toggle {enabled}`.
- `GET /{id}/items?limit=50` → 외부 fetch 후 정규화된
  `{items:[{id,title,url,state,updated_at,author}]}`.
  - 60초 인메모리 캐시(`_CONNECTOR_CACHE`), 실패 시 `last_error` 기록 + 경고 로그.
  - github: `api.github.com` + 선택적 token(Bearer). webhook/json: config.url을
    GET하고 `config.json_path`(dot-path, 기본 배열 루트)로 배열 추출,
    `config.fields`로 출력 필드 매핑 가능. jira/notion/linear은 config.url
    + json_path/fields 규칙을 그대로 사용한다.
  - 외부 호출 성공/실패는 앱 로그에 기록(토큰·URL 민감값 미포함).

#### 14.4 커스텀 워크플로 (`/api/v1/workflows/custom`)

- `GET` → `{items:[{name,spec,created_at,updated_at}]}`.
- `POST {name,spec}` → 201. spec는 `WorkflowSpec`로 검증하고 `spec.key==name`이어야 한다.
- `DELETE /{name}`.
- 저장된 spec는 앱 시작 시와 변경 직후 `_sync_custom_workflows()`가 모듈
  `WORKFLOWS` dict에 동기화한다. `build_registry()`가 `WORKFLOWS`를 순회하므로
  `/runs`, 플레이북, 스케줄, 트리거에서 별도 코드 없이 그대로 해석된다
  (프로세스 재시작 후에도 DB에서 복원).

#### 14.5 트리거 (`/api/v1/triggers`)

- `match`: `{tool?, project?, state?}` (state ∈ 세션 라이프사이클 상태).
  `action.type`: `run_workflow{workflow,input?}` | `run_playbook{playbook_id}` |
  `report{report_kind=daily|weekly}`.
- `POST {match,action}` → 201(검증 실패 422/404), `GET`, `DELETE /{id}`,
  `POST /{id}/toggle {enabled}`.
- `_automation_loop`/cron tick에서 세션 스냅샷을 주기적으로(≥45s) 비교해
  **상태 전이**를 감지한다. 동일 `(trigger_id, tool, session_key, state, fingerprint)`는
  `trigger_fires`의 UNIQUE 제약으로 1회만 발화(재시작·중복 tick에도 dedupe).
  발화 시 `last_fired_at`/`last_error` 갱신, 성공·실패 앱 로그 기록
  (세션 본문 미로깅).

#### 14.6 팀 뷰 (`GET /api/v1/team`)

- `{items:[{id,email,name,role,run_count,last_active_at,session_count}]}`.
  `runs.created_by`(email 또는 user id) 기준 집계 + auth_sessions 활동 병합.
  첫 사용자/`JOBMATE_ADMIN_EMAILS` 기준 effective admin 반영.

#### 14.7 감사 뷰 (`GET /api/v1/audit?limit=200`)

- **admin 전용**(비관리자 403). `{items:[{id,created_at,actor,action,target,detail}]}`
  최신순. `audit_events` 테이블 재사용. 로그인 성공/실패·승인/거절·설정 변경·
  playbook/connector/workflow/trigger/card/share 변경·role 변경이 기록된다.
  비밀값은 detail에 넣지 않는다.

#### 14.8 내보내기/공유

- `GET /api/v1/export?kind=runs|sessions|usage|reports&format=csv|json&days=30`
  → `text/csv` 또는 `application/json` attachment. 비밀 필드 제외.
- `POST /api/v1/share {kind:run|report|insights, ref_id}` → 201 `{token,url,expires_at}`
  (30일). `GET /api/v1/share/{token}` 및 공개 페이지 `GET /share/{token}`은
  세션 없이 안전한 스냅샷만 반환. 만료 시 410, 미존재 404.

#### 14.9 대시보드 카드 (`/api/v1/cards`)

- `GET/POST {title,url,json_path?}/DELETE /{id}/POST /{id}/toggle`.
- `GET /{id}/data` → 서버가 URL을 GET(8s 타임아웃, ~256KB 상한)해 `json_path`
  dot-path로 값을 추출해 `{value}` 반환(빈 path=전체 JSON).
- SSRF 방지: http/https만 허용, localhost·loopback·private/링크로컬 IP 리터럴
  차단 + DNS 이름 해석 결과 전부 공인 IP 검사(`webutil.is_safe_fetch_url`,
  §17.2). 생성·fetch 양쪽에서 422 `url_not_allowed`. 실패 시 `last_error`+경고 로그.

#### 14.10 모바일 요약

- 신규 백엔드 없음 — 기존 `/api/v1/insights`, `/api/v1/automation/overview` 등
  읽기 전용 집계 API로 충분.

### 15. 팀장(lead) 기능 — 역할·프로젝트·리스크·리포트 (2026-11-23 추가)

`jobmate/lead.py` — insights.py와 같은 읽기 전용 집계 모듈(Store 조회 + 순수 함수).
집계 로직은 여기, HTTP 라우트는 `api/routers/`+`api/routers/core.py`, 리포트 본문은 `reports.py`.

#### 15.1 역할 체계 `member|lead|admin`

- `users.role`은 `member|lead|admin` 3단계. 레거시 `'user'`는 읽기 시
  `member`로 정규화(`Store._norm_role`, `_user_json`/`list_users`/`team_activity`),
  쓰기 시에도 `'user'` 별칭을 `member`로 받는다. 알 수 없는 값은 `member`.
- 유효 role 판정(`_effective_role`): 저장 role 우선, `JOBMATE_ADMIN_EMAILS`는
  admin, 신규 `JOBMATE_LEAD_EMAILS`(쉼표)는 lead 부여 — admin env가 lead보다 우선.
- `_lead_user`: 세션 role이 lead/admin, 유효 API 키(머신), 인증 비활성 로컬
  모드일 때 허용. `_admin_user`는 기존과 동일(admin만).
- `PATCH /api/v1/users/{id}/role {role}` — **admin 전용**. 마지막 admin 강등
  시 409 `last_admin` — admin 수 확인과 role 변경을 `Store.exclusive()`
  (store 락) 안에서 원자 처리해 동시 요청 TOCTOU를 방지(프로세스 내 기준,
  멀티 인스턴스는 한계). `DELETE /auth/account`의 마지막 admin 삭제 차단도
  동일 임계구역으로 보호된다. 변경 시 `store.audit` + `_audit_api`(`user_role`) +
  로그. 첫 가입 사용자 자동 admin 승격은 유지(응답 dict도 동기화).
- `GET /api/v1/auth/me` 응답은 기존 `{user:{id,email,display_name,role}}`
  형태 유지, role은 정규화된 값.

#### 15.2 프로젝트 마스터 + 태깅

- `projects` 테이블: `id,name UNIQUE(ci),color,description,goal,target_count,
  created_by,created_at` — SQLite/PG 양쪽 + `lower(name)` 유니크 인덱스.
- `runs.project` 컬럼 추가(`_migrate_run_columns` ALTER). `create_run`은
  `input.project`를 컬럼에도 복사. `agent_sessions.project`는 기존 컬럼 재사용.
- 프로젝트 이름 매칭은 trim + case-insensitive. 미등록 이름도 자유 태그로 허용.
- 엔드포인트(전부 **lead 이상**):
  - `GET/POST /api/v1/projects`, `PATCH|DELETE /api/v1/projects/{id}`
    (name/color/description/goal/target_count). 변경·삭제 시 감사 로그.
  - `PATCH /api/v1/runs/{run_id} {project}` — 태그 설정/해제(`""`/null).
  - `PATCH /api/v1/agent-sessions/{session_key} {project}` — tool 미지정,
    session_key 최신 세션 우선. 변경 시 `agent_session_events`에 전이 1건 기록.

#### 15.3 프로젝트 개요/상세

#### 15.5 리스크 (`GET /api/v1/risks`, 라이브 계산)

### 16. 에이전트 플랫폼 확장 (2026-11-24 추가)

#### 16.1 네이티브 function calling + 도구 스키마 레지스트리

- `LLMClient.complete()`에 선택적 `tools`/`tool_choice` kwargs 추가.
  반환 계약: `(output, usage)` 유지 — 모델이 tool_calls를 반환하면
  `output == {"tool_calls": [{"id","name","arguments"}], "content": str|None}`
  (arguments는 JSON 문자열 또는 dict, OpenAI 중첩 `function.*` 형태도 정규화).
  `schema` 검증은 tool_calls 턴에서는 바이패스.
- `OpenAICompatLLM`은 chat/completions `tools` 파라미터 전송 + `message.tool_calls`
  파싱. `CodexResponsesLLM`은 Responses API `function_call` output item을
  SSE 이벤트에서 수집. `MeteredLLM`은 kwargs 그대로 전달(사용량 계측 유지).
- `src/jobmate/tools/schemas.py`: `register_tool_schema(name, description, parameters)`
  / `openai_tools()` / `has_schema(name)` — OpenAI tools 형식 레지스트리.
  builtin `read_file`/`run_tests`/`read_diff` 스키마 사전 등록.
- `ToolExecutor(tools, repo_root, extra_tools)`: `extra_tools`는 builtin과 병합,
  **builtin 이름은 절대 덮어쓸 수 없다**. `openai_schemas_for(allowed)`로
  allowlist 필터링된 스키마 조회.
- `engine/runner.py::_run_llm_stage`: `agent.tools`가 비어있지 않으면
  `_tool_loop` 실행 — 최대 `_MAX_TOOL_ROUNDS=5`라운드 + `budget_max_tool_calls`
  상태 카운터(실행된 호출만 집계, denied는 미집계). `ToolDeniedError`/실행 오류는
  `ERROR: …` 문자열로 모델에 반환해 복구 유도. 5라운드 후 tools 없는 최종
  `complete`로 답변 강제. 감사 로그는 `{tool, arg_keys}`만 기록(인자 원문 금지).
  `tools=[]` 에이전트는 기존과 동일한 단일 호출.

#### 16.2 프롬프트 인젝션 방어 (`engine/guards.py`)

#### 16.3 MCP 연동 (`src/jobmate/mcp/`)

### 17. 이메일 인증·SSRF 가드·메시지 마스킹 (2026-11-25 추가)

#### 17.1 이메일 인증 (`users.email_verified` + `email_verifications`)

- 스키마: `users.email_verified` 컬럼 — 기존 행은 1로 보강
  (`_ensure_columns` ALTER, 이미 로그인 중인 계정은 검증 완료로 간주).
  `email_verifications` 테이블: `id, email, token_hash, expires_at,
  used_at, created_at` — 토큰 원문은 메일 링크에만 포함하고 DB에는
  SHA-256 해시만 저장(주석 "원문 금지"). TTL 기본 24h(`ttl_hours`).
- 인증 강제 여부 `_email_verification_required()`: 로컬 개발 모드
  (API 키·허용 이메일 목록·VERCEL 모두 없음)만 면제 — 그 외에는 항상 적용.
  Google OAuth 로그인은 `email_verified=true` 계정만 허용하고,
  이메일로 매칭/신규 생성되는 계정은 자동 verified 처리
  (`create_user(..., email_verified=True)`).
- 엔드포인트:
  - `POST /api/v1/auth/signup` — 인증 필요 모드에서 비밀번호 가입 후 인증
    메일 발송. 응답 201 `{user, verify_email_sent, email_verification_pending}`.
    인증 불필요 모드(로컬)는 즉시 세션 쿠키 발급하고 pending=false.
  - `POST /api/v1/auth/login` — 비밀번호는 맞지만 `email_verified=0`이면
    403 `email_not_verified`. 실패 카운트(10분 10회 스로틀)는 비밀번호
    오류에만 적용하고 미인증 차단은 별도 audit(`auth_login_unverified`)로
    기록한다.
  - `GET /api/v1/auth/verify?token=` — 토큰 해시 조회 → 유효하면
    `email_verified=1` + 세션 쿠키 발급 후 완료 HTML 반환. 소비는
    `consume_email_verification` 원자적 UPDATE(used_at/expires_at 조건)
    로 판정해 동시 요청 중복 소비를 차단하고, 재발송 시 같은 이메일의
    기존 미사용 토큰은 전부 무효화된다. 만료/사용/미존재 시 실패 HTML(400).
    `/auth/*`는 미들웨어 인증 예외.
  - `POST /api/v1/auth/verify/resend {email}` — 미인증 계정에만 재발송,
    같은 이메일 10분에 1회(`_VERIFY_RESEND_MIN_INTERVAL=600`) 초과 시
    429 `resend_too_soon`. 미가입/이미 인증 이메일에도 동일 응답
    (`{"sent":false}`)으로 계정 열거를 방지한다.
  - 무키 원격 오픈 모드(API 키·허용 목록·VERCEL 모두 없음 + 비-loopback
    요청)에서는 `signup`/`login` 외에 `verify`·`verify/resend`·`google`·
    `google/callback`도 진입부에서 403 — 원격 토큰 소비·계정 생성·첫
    사용자 admin 선점을 차단한다. `is_loopback_request`는
    `X-Forwarded-For`/`Forwarded` 외에 `X-Real-IP`/`CF-Connecting-IP`/
    `True-Client-IP` 프록시 헤더가 있으면 비-loopback으로 판정한다.
  - `POST /api/v1/auth/password {current_password, new_password}` — 현재
    비밀번호 확인 후 해시 교체 + **전체 세션 폐기**(`revoke_user_sessions`),
    현재 쿠키도 삭제해 재로그인 요구.
  - `GET /api/v1/auth/sessions` / `DELETE /api/v1/auth/sessions/{id}` —
    본인 세션 목록/개별 폐기(타인 세션 404).
  - 인증 링크 베이스 URL: `JOBMATE_PUBLIC_BASE_URL` 우선, 미설정 시 요청
    Host 사용. `JOBMATE_PUBLIC_HOSTS`(쉼표 구분 허용 호스트) 설정 시 불일치
    Host로의 발송은 거부(`auth_verify_send_blocked` 감사로그) — Host-header
    인젝션 방지. PUBLIC_HOSTS 미설정 + `VERCEL=1`이면 Vercel 엣지의 Host
    라우팅 검증에 의존해 허용한다(커스텀 도메인 지원 — `*.vercel.app`만
    허용하면 커스텀 도메인 인증 메일이 전부 차단된다). 그 외 비로컬
    프로덕션 기동에서 두 설정 모두 없으면 경고 로그를 남긴다.
  - Google OAuth: 기존 계정이 `email_verified` 미인증이면(공격자의 사전
    비밀번호 가입 가능 상태) Google이 이메일 소유권을 증명한 것으로 보고
    심어둔 비밀번호 해시를 비우고 `google_sub`를 연결한다
    (`auth_google_claim_unverified` 감사) — 미인증 사전가입으로 피해자의
    Google 로그인이 영구 차단되는 DoS를 방지. 인증 완료된 비밀번호 계정과
    이메일이 같으면 `google_sub` 자동 연결을 거부하고
    `/?auth_error=google_account_conflict`로 리다이렉트(계정 선점 방지).
    `password_hash`가 빈 Google-only 계정만 자동 연결된다.
- 발송 백엔드(`src/jobmate/mailer.py` — stdlib smtplib, 새 의존성 없음):
  `JOBMATE_SMTP_HOST` 설정 시 SMTP 우선. `JOBMATE_SMTP_PORT`(기본 587)/
  `USER`/`PASS`/`FROM`(기본 USER, 없으면 `jobmate@localhost`)/
  `TLS`(`starttls` 기본 | `ssl` | `none`). SMTP 미설정 시 Gmail 어댑터
  (`adapters["gmail"]`, `GoogleGmail.send_message`)로 폴백 — Gmail 토큰에
  `gmail.send` scope 필요. 둘 다 없으면 발송 실패: Vercel은 warning 로그만,
  로컬은 인증 링크 URL을 info 로그에 출력(개발 편의). 발송 실패는 가입
  플로우를 깨지 않고 `verify_email_sent=false`로 응답한다.
- **주의**: `gmail.send`는 `gmail.readonly`와 별도 scope — 기존 readonly
  토큰으로는 발송 불가. `jobmate google-auth gmail`을 재실행해 새 scope로
  토큰을 재발급해야 한다(§4 Google 연동 — 발급 시 readonly+send를 함께
  요청한다). 비밀번호·수신자 원문 등 민감값은 로그에 남기지 않는다.

#### 17.2 SSRF 가드 강화 (`webutil.is_safe_fetch_url`)

- IP 리터럴 차단에 더해 DNS 이름은 `socket.getaddrinfo(host,443,TCP)`로
  해석해 결과 IP 전부가 공인인지 검사 — `is_global` 필수 +
  `is_private`/`loopback`/`link_local`/`multicast`/`reserved`/`unspecified`
  모두 아님. RFC 6598 CGNAT(100.64.0.0/10)·6to4/터널드·NAT64 내장 IPv4
  (Python 3.12.0~3.12.3 ipaddress 테이블 미수정 대응)도 차단 —
  `localtest.me`/`nip.io`/`lvh.me` 같은 공개 DNS 이름의 사설 IP 해석을
  차단한다. `*.localhost`는 DNS 해석 결과가 전부 loopback일 때만
  loopback으로 인정한다(사내 DNS 임의 해석 fail-closed). 해석 실패·
  검증 불가는 거부(false positive 허용, 명확한 일시적 DNS 장애로 간주).
- 해석 결과는 60초 TTL 인메모리 캐시(최대 512 호스트)로 반복 조회 비용을
  줄인다. `getaddrinfo`에 적용 가능한 타임아웃이 없어 느린 DNS는 OS
  resolver 타임아웃까지 호출을 블로킹할 수 있다(docstring 트레이드오프).
- 적용 경로: 대시보드 카드 생성(`POST /cards`)·fetch(`GET /cards/{id}/data`)
  — 위반 시 422 `url_not_allowed`. 커넥터의 `config.url`을 fetch하는
  jira/notion/linear/webhook·json generic 경로(`webutil.fetch_json` 경유).
  github 커넥터는 `api.github.com` 고정 URL이라 대상 아님.
- DNS 리바인딩(TOCTOU) 대응: 검증에 사용한 IP를 커스텀 httpcore 백엔드로
  connect 단계에 고정(pin)해 재해석 우회를 차단한다. SNI/Host 헤더는 원래
  도메인을 유지한다.
- 포트 제한: `80`/`443`만 허용(`_ALLOWED_PORTS`) — 공인 IP의 임의 TCP
  포트 스캔/응답 읽기 방지. 검증(`is_safe_fetch_url`)과 핀 고정
  (`_pinned_ip_for`) 양쪽에 동일 적용.
- `normalize_items`의 `url` 필드도 http/https/상대경로만 통과 —
  `javascript:` 등 위험 스킴은 빈 문자열로 정규화(프론트 `safeUrl`과 중복 방어).
- `assert_safe_fetch_url`/`fetch_bytes`/`fetch_json`이 공용 fetch 진입점 —
  신규 외부 fetch 경로는 이 함수를 경유해야 한다.

### 18. 스코프드 예산 + wakeup 코얼레싱 (Phase-1 백엔드)

#### 18.1 스코프드 예산 (`budget_policies`/`budget_incidents`, `jobmate/budget_scope.py`)

> 2차(§24)에서 지출 권위가 정수 microusd로 이관됐다 — 아래 USD 서술은
> `*_microusd` 필드의 파생 표시값 기준으로 읽는다. 스코프에 `task`가
> 추가됐고 reservation/unpriced/window_kind 정책이 생겼다.

- 월간 USD 예산을 `global`/`project`/`workflow`/`agent` 스코프로 관리한다
  (Paperclip budget_policies 단순 포팅). 지출은 `stage_runs×runs` 조인의
  토큰×모델 단가(`pricing.cost_usd`)로 환산하고, 스코프 귀속은
  workflow→`runs.workflow_key`, project→`runs.project`, agent→
  `runs.agent_id`, global→전체. 월간 지출은 60초 인메모리 캐시
  (`budget_scope._spend_cache`).
- `evaluate_admission(store, workflow_key, project, agent_id="")` — run 생성
  전 심사. 관련 정책(global+매칭 workflow+매칭 project+매칭 agent, 즉
  `scope_id=agent_id`)의 warn%/hard 임계를 넘으면 `budget_incidents`에
  open 인시던트를 멱등 생성하고 인박스 `kind='budget'`로 알린다.
  `hard_stop_enabled`이고 `month_spend >= amount_usd`이면 blocking 목록을
  반환한다. `agent_id`를 아는 호출 지점(POST /runs, deferred promote)만
  agent 스코프를 심사한다 — 스케줄/트리거/메시지 intake는 agent 태그를
  만들지 않으므로 `agent_id=""`로 호출해 agent 정책이 적용되지 않는다.
- `agents.monthly_budget_usd`도 동일 윈도우·agent 스코프 지출로 집행된다 —
  정책 행 없이 에이전트 레지스트리에 직접 설정하는 월간 상한으로,
  `month_spend >= monthly_budget_usd`이면 hard block만 적용한다
  (인시던트/인박스는 정책 전용이라 생성하지 않는다).
- 집행 지점: `POST /api/v1/runs`(429 `budget_exceeded`, 레거시
  `prefs.monthly_budget_usd`와 병행), `POST /playbooks/{id}/run`,
  workflow schedule 발사(`_process_due_schedules` — 해당 발사만 스킵),
  trigger `run_workflow`/`run_playbook`(`_fire_trigger_action._launch`),
  메시지/radar intake(`_create_and_run` — 차단 시 예외).
- API (전부 lead 이상):
  - `GET /api/v1/budgets/overview` → `{policies:[{...,month_spend_usd,
    used_pct,status,open_incidents}], month}`
  - `PUT|DELETE /api/v1/budgets/policies/{scope_type}[/{scope_id}]`
    — scope_type은 `global|workflow|project|agent`. scope_id 없는 경로는
    global. agent 스코프의 scope_id는 agents.id. `amount_usd` null/<=0 또는
    DELETE는 `is_active=0` 비활성화(이력 보존).
  - `GET /api/v1/budget-incidents?status=open`
  - `POST /api/v1/budget-incidents/{id}/resolve`
    `{action: keep_paused|raise_budget_and_resume|dismiss, amount_usd?, note?}`
    — `raise_budget_and_resume`은 `amount_usd > amount_observed` 필수,
    정책 금액 갱신 + 해당 정책 open 인시던트 전부 resolved + 감사 로그.

#### 18.2 Wakeup 코얼레싱 (`wakeup_requests`, `jobmate/wakeups.py`)

- 모든 run 생성 요청은 `wakeup_requests` 행을 남긴다(감사).
  `scope_key = {workflow_key}:{sha256(canonical {agent_id,input})[:16]}` —
  agent_id가 다르면 별도 scope라 동일 input·다른 agent 태그 요청은
  coalesce되지 않는다(태그 유실 방지).
- `admit_run(...)` — 동일 scope의 queued/running run이 있으면 새 run 없이
  `coalesced`(기존 run_id 반환), `force_new`면 `deferred`로 적재.
  `idempotency_key` 재생은 기존 wakeup의 run을 반환(`replayed`/`coalesced`).
- run 종결(`_execute_run_job`/`_create_and_run`/`_do_approve` resume 경로의
  `on_run_finished`) 시 연결 wakeup을 completed/failed로 마감하고,
  같은 scope의 최 deferred 1건을 promote해 run을 생성·실행한다
  (스케줄러 콜백으로 `_execute_run_job` 재진입). scope당 활성 run 1개 유지.
- `POST /api/v1/runs` 요청 바디에 `force_new: bool`,
  `idempotency_key: string` 추가. 응답은 기존 `{id,status}` 유지 +
  coalesced/deferred 시 `action` 필드 추가.
- 조회: `GET /api/v1/wakeups?run_id=&status=&source=` (lead 이상),
  `GET /api/v1/runs/{id}` 응답에 `wakeups` 요약 포함.
- 미적용 경로: `jobmate/cli.py run`(로컬 CLI, 직접 create_run —
  wakeup/예산 admission 우회, 로컬 전용 도구로 간주),
  `fail_stale_runs` 리퍼 경로(스토어 계층이라 스케줄러 없음 — wakeup은
  queued로 잔류 가능, 다음 동일 scope 종결 이벤트 때 정리되지 않음).

#### 18.3 알려진 한계 (accepted residual risks)

- **check-then-act 레이스**: `evaluate_admission`(지출 조회→판정)과 run
  생성, `admit_run`의 active-run 스캔→wakeup INSERT는 원자적이지 않다.
  단일 프로세스+스레드풀 구성에서는 창이 극히 좁고, `idempotency_key`
  부분 UNIQUE 인덱스(`idx_wakeup_idem_uniq`)와 `budget_incidents` open
  부분 UNIQUE가 동시 삽입의 최악 케이스(이중 run/중복 인시던트)를 막는다.
  다중 인스턴스 배포 시에는 예산 hard_stop이 최종 강제가 아니므로
  외부 결제/수집 단계의 별도 한도가 필요하다.
- **cli.py 면제**: `jobmate/cli.py run`은 wakeup coalescing과 스코프드
  예산 심사를 거치지 않는다(로컬 개발 도구). 운영 API 경로만 집행된다.
- **function 단계 토큰**: function stage가 내부 LLM을 호출하고 예외로
  죽으면 그 시점까지 소비된 토큰은 `stage_runs`에 기록되지 않는다
  (성공 시 반환 dict의 tokens_in/out로만 집계). LLM stage는 실패 시에도
  누적 usage를 기록한다.
- **function 단계 모델 단가**: function 내부 LLM 호출의 `cost_usd`는
  함수가 명시 반환할 때만 state에 합산된다 — 미반환 시 토큰은 기록돼도
  USD 환산은 단가표 기본값 추정에 의존한다.
- **PATCH /runs/{id} project 재태깅**: lead 이상이 run의 project를 바꾸면
  `runs.project` 컬럼 기준 과거 지출의 스코프 귀속도 함께 이동한다
  (`input.project`/`run.input`은 변경되지 않아 코얼레싱 scope_key는 유지).
  월간 집계의 소급 재분류를 허용하는 트레이드오프다.

### 19. 에이전트 레지스트리 + 조직도 (Phase-2 백엔드)

Paperclip `agents` 테이블의 개념 포팅 — 코딩 에이전트 어댑터(claude/codex/
gemini/devin/custom)를 조직도(reports_to)로 등록·관리한다. 스키마는
`store/schema_sqlite.py`/`store/schema_pg.py` 양쪽에 `agents` 테이블 + `runs.agent_id`
컬럼으로 추가됐고, 기존 DB는 `_migrate_run_columns`의 `_ensure_columns`가
`agent_id`를 ALTER로 보강한다(agents 테이블은 CREATE TABLE IF NOT EXISTS로
자동 생성).

#### 19.1 데이터 모델 (`agents` 테이블)

- `id` TEXT PK, `name` TEXT NOT NULL UNIQUE(코드 레벨에서 lower() 기준
  중복도 차단 — projects와 동일 규칙) + `idx_agents_name_lower`
  UNIQUE 인덱스(`lower(name)`)로 DB 레벨에서도 ci 중복을 강제한다.
  인덱스는 `_migrate_agent_name_index`가 생성 — 기존 DB의 ci 중복은
  최신 행만 이름을 유지하고 나머지에 `·dup·{id}` 접미를 붙여 보존한다
  (id 참조 무결성 유지). `adapter_type` TEXT NOT NULL
  (`claude|codex|gemini|devin|custom` — agent_bridge 스캐너 tool 값 + 수동
  custom), `role`/`description` TEXT NULL, `capabilities` TEXT(JSON 배열),
  `reports_to` TEXT NULL → agents(id) 자기참조 FK, `status` TEXT NOT NULL
  DEFAULT 'active'(`active|paused|archived`), `monthly_budget_usd` REAL NULL,
  `created_by`/`created_at`/`updated_at`.
- `runs.agent_id` TEXT NULL — run을 에이전트에 귀속시키는 태그.
  `Run.agent_id` 모델 필드, `run_detail` 응답에도 포함.
- store: `store/agents.py` AgentStoreMixin — CRUD + `reports_to_would_cycle`
  (체인 워크, 방문 집합 방어) + `agent_run_stats`/`agent_spend_rows`
  (30일 runs_30d/last_run_at 원시 집계). `create_agent`/`update_agent`는
  쓰기 경로에서 reports_to 대상 존재·자기참조를 재검증한다 — SQLite는
  `PRAGMA foreign_keys`가 커넥션별로 꺼져 있을 수 있어 FK가 강제되지
  않으므로 방어 심화 차원이다(순환 참조는 앱 계층 전용 — 검사~쓰기 사이
  TOCTOU는 잔존 한계).
- 서비스: `jobmate/agents.py` — enum 검증, reports_to 규칙(존재·비archived·
  자기참조·사이클 금지), capabilities 정규화, AgentOut 조립
  (cost_30d_usd는 stage_runs×runs 조인 행을 `pricing.cost_usd`로 환산).
  reports_to 규칙 예외: PATCH가 기존 reports_to 값을 그대로 재전송하는
  no-op은 archived 상위여도 허용한다 — 프론트가 현재값을 항상 함께
  보내므로, archived 상위를 가진 기존 행의 다른 필드 수정이 422로
  막히지 않게 하기 위함이다. 새로 archived를 상위로 지정하는 것은 거부.

#### 19.2 API

- `GET /api/v1/agents?status=` — `{"items": [AgentOut]}`. **lead 이상**
  (AgentOut에 monthly_budget_usd/cost_30d_usd 등 예산·비용 집계가 포함돼
  member에게 노출하지 않는다 — 조직도 nav/페이지도 lead 전용).
  status 필터는 active|paused|archived, 빈 문자열은 미지정과 동일.
  AgentOut = {id, name, adapter_type, role, description, capabilities(list[str]),
  reports_to(id|null), status, monthly_budget_usd, created_at, updated_at,
  runs_30d, cost_30d_usd, last_run_at}. 조직도는 프론트가 reports_to로 트리 구성
  (별도 엔드포인트 없음).
- `POST /api/v1/agents` (lead+) — {name, adapter_type, role?, description?,
  capabilities?, reports_to?, status?, monthly_budget_usd?} → 201 AgentOut.
  name 중복(대소문자 무시, 앱 검사 + `idx_agents_name_lower` UNIQUE 인덱스
  이중 방어) → 409, 그 외 검증 실패 → 422.
- `PATCH /api/v1/agents/{id}` (lead+) — model_fields_set 기준 부분 갱신,
  reports_to=null/""는 상위 해제, monthly_budget_usd=null은 한도 해제.
  미존재 → 404, name 중복(사전 검사 통과 후 인덱스 충돌 포함) → 409.
- `DELETE /api/v1/agents/{id}` (lead+) — 소프트 삭제(status='archived').
  runs.agent_id 참조 이력을 보존하기 위해 하드 삭제하지 않는다.
- 모든 변경은 `_audit_api`(agent_create/agent_update/agent_archive) +
  logger.info로 감사 로그를 남긴다.

#### 19.3 runs.agent_id 태깅

- `POST /api/v1/runs` 바디에 `agent_id` 추가 — 존재하는
  active/paused 에이전트 id만 허용(미존재·archived 시 422).
  `wakeups.admit_run(agent_id=...)` → `create_run` 컬럼 기록.
  deferred wakeup은 payload에 agent_id를 실어 promote 시에도 태그 유지 —
  promote 시점에 에이전트가 archived됐으면 해당 wakeup은 failed로 마감하고
  run을 만들지 않는다. agent_id는 예산 심사(`evaluate_admission`)와
  코얼레싱 scope_key에도 포함된다(§18.1/§18.2).
- **알려진 한계**: bridge 세션(agent_sessions.tool)→agents 행의 자동 추론은
  하지 않는다 — 세션 push 경로는 run을 만들지 않고, run 생성은 명시 태깅만
  지원한다. `reports_to` 순환 검사는 앱 계층 check-then-act라 검사~쓰기
  사이 TOCTOU가 남는다(동시 PATCH로 일시적 순환이 생길 수 있으나
  `reports_to_would_cycle`의 방문 집합이 무한 루프는 막는다).
  function stage가 호출하는 내부 LLM 토큰은 이 경로의 agent 스코프
  지출 집계 대상이 아니다(§18.3 function 단계 항목과 동일 제약).
  `agent-scope`/`monthly_budget_usd` 집행은 agent_id를 아는 경로
  (POST /runs, deferred promote)에만 적용된다 — agent 태그 없이 생성되는
  스케줄/트리거/메시지 run에는 agent 예산이 귀속되지 않는다(§18.1).

#### 19.4 에이전트별 예산

- `budget_policies`에 `scope_type='agent'`, `scope_id=agents.id`로
  월간 USD 정책을 둘 수 있다(§18.1 — PUT/DELETE
  `/api/v1/budgets/policies/agent/{agent_id}`). 지출은
  `budget_spend_rows`의 `runs.agent_id` 조인으로 집계한다.
- `agents.monthly_budget_usd`는 정책 행 없이 직접 설정하는 월간 상한 —
  `evaluate_admission`이 agent 스코프 지출 >= 한도이면 hard block한다
  (인시던트/인박스 알림은 budget_policies 경로만 생성).

### 20. 목표 계층 goals + run/project 연동 (Phase-3 백엔드)

Paperclip `goals`(self-ref 트리) 포팅 — 조직·프로젝트 상위 목표를
`parent_id` 자기참조 트리로 등록하고, 프로젝트와 run에 `goal_id`로 귀속시킨다.
스키마는 `store/schema_sqlite.py`/`store/schema_pg.py` 양쪽에 `goals` 테이블 +
`runs.goal_id`/`projects.goal_id` 컬럼으로 추가됐고, 기존 DB는
`_migrate_goal_columns`의 `_ensure_columns`가 ALTER로 보강한다.

#### 20.1 데이터 모델 (`goals` 테이블)

- `id` TEXT PK, `title` TEXT NOT NULL(≤200), `description` TEXT DEFAULT '',
  `parent_id` TEXT NULL 자기참조(FK 없음 — agents.reports_to와 동일하게
  앱 계층이 존재/사이클 검증), `status` TEXT NOT NULL DEFAULT 'active'
  (`active|done|archived`), `created_by`/`created_at`/`updated_at`.
  `idx_goals_parent`, `idx_goals_status` 인덱스.
- `projects.goal_id` TEXT NULL — 프로젝트가 상위 목표에 연결.
  `runs.goal_id` TEXT NULL — run의 목표 태그. `Run.goal_id` 모델 필드,
  `run_detail`/`GET /runs` 응답에 포함.
- store: `store/goals.py` GoalStoreMixin — CRUD + `parent_would_cycle`
  (parent_id 체인 워크, 방문 집합 방어 — agents와 방향만 반대) +
  `list_goals`의 children_count(직계 자식 수 GROUP BY 1회 집계).
  `create_goal`/`update_goal`은 존재하지 않는 parent·자기참조를 방어
  (SQLite FK 미강제 대비). 서비스: `jobmate/goals.py` — status enum,
  parent 규칙(존재·비archived·자기참조·사이클 금지), GoalOut 조립.
  agents와 동일하게 PATCH가 기존 parent_id를 그대로 재전송하는 no-op은
  archived 부모여도 허용한다.

#### 20.2 API

- `GET /api/v1/goals?status=` — `{"items": [GoalOut]}`. **member+**
  (목표는 민감 정보가 아니며 runs/projects가 참조 — agents와 달리
  예산/비용 집계가 없어 member 읽기를 허용). status 필터는
  active|done|archived, 빈 문자열은 미지정과 동일.
  GoalOut = {id, title, description, parent_id(id|null), status,
  created_at, updated_at, children_count}.
- `POST /api/v1/goals` (lead+) — {title, description?, parent_id?,
  status?} → 201 GoalOut. title 필수·공백 불가·≤200, parent는 존재·
  비archived·무사이클이어야 한다(위반 시 422).
- `PATCH /api/v1/goals/{id}` (lead+) — model_fields_set 기준 부분 갱신,
  parent_id=null/""는 루트 해제. 미존재 → 404.
- `DELETE /api/v1/goals/{id}` (lead+) — 소프트 삭제(status='archived').
  runs.goal_id/projects.goal_id 참조 이력을 보존한다. **자식 목표는
  parent_id를 유지**한다 — archived 부모 아래 자식의 표시 방법은
  프론트엔드가 트리 렌더링 시 결정한다(계약상 허용, 차단하지 않음).
- 모든 변경은 `_audit_api`(goal_create/goal_update/goal_archive) +
  logger.info.

#### 20.3 runs/projects의 goal_id 해석

- `POST /api/v1/runs` 바디에 `goal_id` 추가 — 존재하는 비archived 목표만
  허용(미존재·archived 시 422). 해석 순서는 `store.create_run`이 담당:
  **명시 goal_id 파라미터 → input_data.goal_id → 프로젝트(project 태그를
  projects.name ci로 매칭)의 goal_id → NULL**. input의 `goal_id` 키는
  컬럼/컨텍스트로 흡수하고 저장 input에서는 제거한다 — 코얼레싱
  canonical input이 (요청 input, runs.goal_id) 양쪽에서 같은 형태가
  되도록 하기 위함.
- goal_id가 해석되면 `run.input["goal"] = {"id", "title"}` 컨텍스트를
  주입한다 — 워크플로 stage가 run.input을 읽어 목표 맥락을 프롬프트에
  반영할 수 있다. `"goal"` 키는 `wakeups.scope_key_for`의 canonical
  계산에서 제외된다(저장된 run.input과 요청 input_data의 scope 일치
  유지). `"goal_id"`/`"goal"`은 예약 키로 취급한다.
- goal_id는 `wakeups.admit_run`/`scope_key_for`/`_payload_json`/
  `_active_run_for_scope`/deferred promote 전 경로에 agent_id와 동일하게
  스레딩된다 — 동일 input·다른 goal_id는 coalesce되지 않는다.
- **scope 일관성(H1 수정)**: goal_id 해석은 `store.resolve_run_goal_id`
  단일 경로 — admit_run이 scope_key/payload 계산 **전에** 호출해
  프로젝트 폴백 goal까지 scope·wakeup payload·생성 run이 일치한다.
  이전에는 admit_run이 goal_id=""로 scope를 계산하고 create_run이
  폴백 해석해 coalescing이 깨지고 deferred wakeup이 고착됐다.
- **goal 검증(M1/M2)**: admit_run은 명시 goal_id(파라미터 또는
  input_data.goal_id — 스케줄/플레이북 JSON 경유 포함)를 존재+비archived로
  검증하고 무효 시 `action="invalid_goal"`을 반환한다(호출자가 422/스킵/
  ""로 매핑). 프로젝트 **폴백**의 무효 goal은 태그를 strip하고 진행한다.
  create_run도 동일 규칙으로 방어 — missing/archived goal은 태깅하지 않고
  `input["goal"]`/`input["goal_id"]` 예약 키는 항상 제거 후 재주입한다.
  deferred promote 시점에 goal이 archived됐으면 wakeup을 failed로 마감
  (agent archived 재검사와 동일 패턴).
- **scope_key 마이그레이션(H2)**: `_migrate_deferred_wakeup_scopes`가
  Store 오픈 시 status='deferred' 행의 scope_key를 payload의
  (input, agent_id, goal_id)로 재계산한다 — goal_id 도입으로 digest
  형식이 바뀌기 전의 행이 영구 고착되는 것을 방지. payload에 goal_id가
  없으면 프로젝트 폴백 규칙으로 보정해 payload에도 기록한다.
  파싱 불가 행은 failed로 마감. 행 단위 best-effort(경고만).
- 프로젝트 API: archived goal_id는 create/patch 모두 422로 거부 —
  archived 목표를 새로 프로젝트에 연결할 수 없다(기존 연결은 보존).
- `PATCH /api/v1/runs/{id}` (lead+) — `goal_id` 필드 추가. null/""는
  해제, 존재하지 않는/archived 목표는 422. project와 함께 model_fields_set
  기준 부분 갱신으로 변경됐고, **모든 검증을 먼저 수행한 뒤 mutate**한다
  (goal_id 422가 project 변경을 부분 적용하지 않음 — M4 수정).
- 프로젝트 API: `POST/PATCH /api/v1/projects`의 `goal_id`(존재+비archived
  검증 — archived는 422, null/""=해제), 목록/상세 응답에 `goal_id` 포함 —
  `_project_json`이 `SELECT *`를 그대로 반환하므로 컬럼 추가만으로
  노출된다.
- 알려진 한계: goal 컨텍스트는 run 생성 시점 스냅샷 — 이후 목표
  title/parent 변경은 기존 run.input["goal"]에 반영되지 않는다.
  archived/done 목표를 참조하는 기존 run/project는 그대로 둔다(이력 보존).
  `export_runs`에 goal_id 컬럼 포함.

### 21. 커스텀 워크플로 spec 버전닝 (Phase-3 백엔드)

Paperclip document versioning 포팅 — `custom_workflows.spec`은 항상 최신
리비전의 사본이고, 실제 이력은 `workflow_revisions` 테이블의
append-only 리비전 행이 담당한다. 리비전 행은 절대 재작성하지 않으며,
복원은 새 리비전 추가(restore-as-new-revision)다.

#### 21.1 데이터 모델

- `workflow_revisions`: `id` TEXT PK, `name` TEXT NOT NULL,
  `revision` INTEGER NOT NULL, `spec` TEXT NOT NULL(JSON),
  `note` TEXT DEFAULT '', `created_by` TEXT DEFAULT '', `created_at`
  TEXT, `UNIQUE(name, revision)` + `idx_workflow_revisions_name`.
- `custom_workflows`에 `latest_revision` INTEGER NOT NULL DEFAULT 0,
  `updated_at` TEXT 컬럼 추가 — `_migrate_workflow_version_columns`의
  `_ensure_columns`가 기존 DB를 ALTER로 보강한다.
- **백필**: `_backfill_workflow_revisions`가 Store 오픈 시 리비전 이력이
  없는 custom_workflows 행에 현재 spec을 revision 1(note='backfill')로
  복원하고 latest_revision을 동기화한다. 관용적 — 실패해도 경고만
  남기고 기동한다. 리비전은 있으나 latest_revision이 뒤처진 행도
  MAX(revision)으로 보정한다.
- store: `store/builder.py` — `save_custom_workflow(name, spec,
  base_revision=?, note=?, created_by=?)`가 CAS+append를 한 tx로 수행
  (SELECT latest → 불일치 시 conflict 반환 → upsert spec + INSERT
  revision). `list/get_custom_workflow_revisions`,
  `get_custom_workflow_revision`, `restore_custom_workflow_revision`
  (rev spec을 latest+1로 복제, note 기본값 'restore revision N').
  `upsert_custom_workflow`은 save_custom_workflow에 위임하는 레거시
  래퍼 — 리비전 없는 spec 갱신 경로를 없앴다.
  `delete_custom_workflow`는 리비전 행도 함께 삭제한다(cascade —
  리비전은 spec의 파생 이력이라 워크플로 없이 보존 가치가 없고,
  고아 리비전이 복원 경로를 오염시키는 것을 막는다).
  `list_custom_workflows`/`get_custom_workflow` 응답에
  `latest_revision`/`updated_at` 포함. `_sync_workflow_registry`는
  `list_custom_workflows`의 최신 spec만 읽으므로 변경 없이 동작한다.

#### 21.2 API (모두 lead+)

- `POST /api/v1/workflows/custom` — 바디에 `base_revision`(int|null),
  `note`(≤500) 추가. spec 검증은 기존과 동일(WorkflowSpec +
  spec.key==name). `base_revision`이 주어지고 현재 latest_revision과
  다르면 **409 표준 err() 엔벨로프** `{"error": {"code":
  "revision_conflict", ...}, "current_revision": N}` — 프론트는
  `error.code`로 판별한다(레거시 플랫 형태도 폴백 수용). 성공 시
  append-only 리비전 추가 + custom_workflows 갱신, 응답에
  `revision` 포함. base_revision 생략 시 항상 latest+1 append —
  첫 저장은 revision 1. **첫 저장(신규 name)은 base_revision을
  검사하지 않고 무시한다** — row가 없으면 latest=0으로 취급해 어떤
  base_revision이든 revision 1이 생성된다(클라이언트는 신규 저장에
  base_revision을 보내지 않는 것이 계약).
- `GET /api/v1/workflows/custom` 목록 항목에 `latest_revision` 포함 —
  프론트가 revisions fetch 실패 시에도 CAS 기준 리비전을 알 수 있다.
- `GET /api/v1/workflows/custom/{name}/revisions` — `{"items":
  [{id, name, revision, note, created_by, created_at, spec_preview}]}`
  최신순. spec은 200자 미리보기만(전문은 상세 엔드포인트). 미존재
  워크플로 → 404.
- `GET /api/v1/workflows/custom/{name}/revisions/{rev}` —
  `{id, name, revision, spec(전체 dict), note, created_by, created_at}`.
- `POST /api/v1/workflows/custom/{name}/revisions/{rev}/restore` —
  해당 리비전 spec을 최신+1 리비전으로 복사 → `{"name", "revision":
  new_rev}`. 복원 대상 spec은 WorkflowSpec으로 재검증하고
  spec.key==name을 요구한다 — 무효/키 불일치 spec은 **422
  invalid_spec**(최신 리비전 오염 방지). 저장 경합은 **409
  revision_conflict**, 미존재 워크플로/리비전은 404. 복원 후
  `_sync_workflow_registry` 재동기화.
- 모든 저장/복원/삭제는 `_audit_api`(custom_workflow_save/_restore/_delete)
  + logger.info. CAS 경합(UNIQUE(name,revision) 충돌)도 store가
  conflict로 변환해 같은 409 계약을 반환한다.

#### 21.3 알려진 한계

- CAS는 check-then-act — 동시 저장 2건이 같은 latest를 읽으면 한쪽이
  UNIQUE 충돌로 conflict 처리된다(데이터 손상은 없으나 클라이언트 재시도
  필요). SELECT~INSERT가 단일 tx라 sqlite 직렬화로 대부분 방어된다.
- 리비전 목록의 spec_preview는 저장된 JSON 문자열 앞 200자 — 의미
  단위 truncate가 아니다.
- revision 번호는 name별 단조 증가 — 삭제 후 재생성하면 1부터 다시
  시작한다(UNIQUE(name,revision) 덕에 충돌 없음 — 삭제 시 리비전도
  cascade로 제거되므로).

### 22. Eval 하니스 — 저장 입력 + 결정적 체크 채점 (Phase-4 백엔드)

Paperclip pillar-3 포팅 — eval은 "입력 픽스처 + 결정적 체크" 묶음이고,
`POST /evals/{id}/run`이 이를 일반 run 파이프라인으로 실행한 뒤 완료된
run을 체크로 채점한다. LLM judge는 v1에서 제외 — results 항목이
`{check_type, check, passed, detail}` 형태라 judge 타입을 나중에 추가할
수 있다(check_type은 표시용 타입 문자열, check는 원본 체크 객체 —
프론트는 check_type으로 라벨을 달고 check를 툴팁에 직렬화한다).

#### 22.1 데이터 모델

- `evals`: `id` TEXT PK, `name` TEXT NOT NULL, `workflow_key` TEXT NOT NULL,
  `input` TEXT(JSON 객체 — `task` 필수), `checks` TEXT(JSON 배열),
  `status` TEXT NOT NULL DEFAULT 'active'(`active|archived`),
  `created_by`/`created_at`/`updated_at`.
  `idx_evals_name_lower` UNIQUE 인덱스(`lower(name)`)로 대소문자 무시
  중복을 DB 레벨에서도 차단 — agents/goals의 앱 검사 + 인덱스 이중
  방어와 동일 패턴. `idx_evals_status`.
- `eval_runs`: `id` TEXT PK, `eval_id` TEXT NOT NULL, `run_id` TEXT NOT NULL,
  `status` TEXT NOT NULL DEFAULT 'pending'(`pending|scored|error`),
  `score` REAL NULL, `results` TEXT JSON 배열, `error` TEXT,
  `created_at`, `scored_at` NULL. `idx_eval_runs_eval`, `idx_eval_runs_run`.
- store: `store/evals.py` EvalStoreMixin — CRUD + `find_eval_by_name`
  (ci) + `latest_eval_runs`(목록 집계용 eval별 최신 행 1회 스캔).
  서비스: `jobmate/evals.py` — 필드/체크 검증, `eval_out`/`eval_run_out`
  조립, 채점 엔진(아래).

#### 22.2 API

- `GET /api/v1/evals?status=` — **lead+**(픽스처가 민감 정보를 담을 수
  있고 UI 뷰도 lead 전용). `{"items": [EvalOut]}`,
  EvalOut = {id, name, workflow_key, input, checks, status, created_by,
  created_at, updated_at, last_score?, last_run_at?}. last_run_at은 가장
  최근 eval_run의 created_at, last_score는 score가 null이 아닌 가장 최근
  eval_run의 score — 방금 트리거한 pending run이 최신이어도 이전 점수가
  유지된다.
- `POST /api/v1/evals` (lead+) — {name, workflow_key, input, checks?,
  status?} → 201 EvalOut. workflow_key는 WORKFLOWS(내장+custom 동기화
  포함)에 존재해야 하고, input.task는 비어있지 않은 문자열, checks 각
  항목은 type+필수 필드가 유효해야 한다(위반 시 422, name 중복 409).
- `GET /api/v1/evals/{id}` — lead+, EvalOut.
- `PATCH /api/v1/evals/{id}` (lead+) — 부분 갱신(name/workflow_key/
  input/checks/status). name 중복 409, 나머지 검증 실패 422.
- `DELETE /api/v1/evals/{id}` (lead+) — 소프트 삭제(status='archived').
  eval_runs 채점 이력 보존.
- `POST /api/v1/evals/{id}/run` (lead+) — eval_run + 실제 run을 만들고
  `{"eval_run_id", "run_id", "status": "pending"}` 201을 반환한다.
  - **코얼레싱 우회**: `wakeups.admit_run` 대신 `store.create_run`을
    직접 호출 — eval run은 매번 별개 실행이어야 하므로 동일 input의
    활성 run과 합류/지연되지 않는다(wakeup_requests 행 없음).
  - **예산 심사**: POST /runs와 동일한 두 단계 — prefs.monthly_budget_usd
    MTD 초과 시 429 budget_exceeded, budget_scope.evaluate_admission의
    스코프드 hard_stop도 동일하게 차단(실제 비용을 쓰므로).
    run 생성 버스트 레이트리밋(_run_rate_limited)도 동일 적용.
  - run.metadata에 `eval_id`/`eval_run_id`를 기록 — run detail의
    metadata로 run→eval 역추적 가능.
  - eval_runs 행은 run과 함께 생성되고, run이 이미 terminal이면
    생성 시점에 즉시 채점한다(거의 없는 경로 — 방어).
- `GET /api/v1/evals/{id}/runs?limit=` — **lead+**,
  `{"items": [EvalRunOut]}` 최신순(최대 200). EvalRunOut = {id, eval_id,
  run_id, status, score, results:[{check_type, check, passed, detail}],
  error, created_at, scored_at}.

#### 22.3 채점 — lazy + 결정적

- run이 terminal(completed/failed/rejected/cancelled/budget_exhausted/
  needs_human — waiting_*는 비종결)이면 `GET /evals/{id}/runs` 조회
  시점에 pending 행을 채점한다(`evals.maybe_score_eval_run`, 멱등 —
  `WHERE status='pending'` 조건부 UPDATE). 실패한 run도 채점한다 —
  체크가 대부분 실패해 낮은 점수가 되는 것이 올바른 신호.
- run이 없거나 eval이 삭제된 경우는 status='error'로 마감(재시도 없음).
- 개별 체크 예외는 해당 체크 실패로 기록하고 채점은 계속 — 크래시가
  전체 채점을 죽이지 않는다. checks가 비어 있으면 score=NULL,
  status='scored', results=[].
- score = passed/total*100 (소수 1자리).

#### 22.4 체크 타입 (`jobmate/evals.py`)

공통 출력 뷰: `run_output_doc` = `{stage_key: 최신 attempt의 output}`
(dict), `run_output_text` = stage_key 루트의 `path: value` 렌더링 +
`run.error` 1행(output_contains/regex가 검색). json_path는 doc에 대해
`a.b[0].c` 형태 단순 경로를 해석한다(jsonpath 라이브러리 없음 —
dict 키/list 인덱스만). 경로가 가리키는 값이 JSON 문자열이면 파싱 후
비교한다.

- `stage_completed` {stage, status?} — 해당 stage의 최신 attempt
  상태가 status(기본 'succeeded' — StageStatus 어휘)와 일치.
- `output_contains`/`output_not_contains` {value} — 출력 텍스트에
  부분문자열 포함/미포함.
- `output_regex` {pattern} — re.search. 잘못된 regex는 422로 저장 단계에서
  차단하고, 검증 우회 저장분도 채점 시 체크 실패로 처리(크래시 없음).
- `json_path` {path, equals?, contains?} — 최소 하나 필요. equals는
  == 비교, contains는 str() 포함 검사. path는 선행 `$`/`$.`를 벗겨
  해석한다(`$.a.b` ≡ `a.b` — 프론트 placeholder 관용).
- `max_cost_usd` {value} — stage_runs 토큰×모델 단가 합계
  (pricing.cost_usd — budget spend와 동일 기준)가 value 이하.

검증 상한(생성/PATCH 공통, `validate_eval_fields`): input.task ≤ 20000자
(RunCreateRequest와 동일), check 문자열 필드(stage/value/pattern/path/
contains/문자열 equals) ≤ 1000자, 비문자열 equals 직렬화 ≤ 10000자,
input+checks 직렬화 합계 ≤ 200KB. output_contains/output_not_contains의
value와 json_path의 contains는 비어있을 수 없다(빈 문자열은 모든 출력에
trivially 매칭). output_regex는 `(a+)+` 류 중첩 정량자 패턴을 휴리스틱으로
거부한다 — 완전한 ReDoS 판별은 아니므로 길이 캡과 병행하는 best-effort
방어이며 잔여 위험은 문서화된 한계로 남는다.

#### 22.5 알려진 한계

- eval_runs는 `retention_sweep`에서 status<>'pending'이고 created_at이
  365일 경과하면 삭제된다(pending = lazy 채점 대기 중이므로 보존).
  evals 픽스처 자체는 삭제하지 않는다.
- 채점은 eval의 **현재** checks/input 정의를 사용한다 — run 생성 후
  eval을 PATCH하면 이후 채점은 새 정의로 매겨진다(스냅샷 아님).
- eval run은 wakeup_requests를 남기지 않는다 — wakeups 감사 뷰에는
  나타나지 않고 runs 목록에는 일반 run으로 보인다(metadata.eval_id로
  구분).
- run.metadata는 eval_id/eval_run_id 마커만 — run 목록 API에는 별도
  eval 필드를 추가하지 않았다(계약상 metadata로 충분).

### 23. Agent 관리 1차 — 레지스트리·task·checkout·wake (paperclip spec)

`docs/paperclip-agent-management-spec.md` 1차 구현. 기존 `/api/v1/agents`,
`/api/v1/runs`와 공존하며 관리(task) 계층을 추가한다. 비용 원장·microusd
예산은 §24(2차), approvals 인박스·watchdog·goals/projects·routines·
Paperclip 커넥터는 후속.

#### 23.1 데이터 모델

- `agents` 신규 컬럼: `kind`(workflow|external), `adapter_config`(JSON,
  secret류 키는 API 응답에서 `REDACTED` 마스킹), `last_seen_at`,
  `title`, `monthly_budget_microusd`(2차부터 `monthly_budget_usd`보다
  우선하는 월간 상한으로 집행 — §24.3).
- `tasks`: `identifier`(`WMB-<n>` UNIQUE), title/description, status 8종,
  priority 4종, `assignee_agent_id`, `reviewer_agent_id`, `parent_id`,
  `current_run_id`, `checkout_agent_id`/`checkout_at`, `created_by`.
- `task_runs`: (task_id, run_id) PK + `attempt` — 한 task의 run 이력.
- `agent_events`: 통합 이벤트 로그. `idempotency_key` UNIQUE로 멱등 append,
  `event_type` 13종(`task_checkout_released` 포함), agent/task/run nullable
  참조, `occurred_at`. retention_sweep이 `created_at` 90일 경과분을 삭제한다
  (tasks/task_runs는 업무 이력이라 별도 정책 없이 보존).

#### 23.2 상태 어휘·전이

- Agent status 7종: `pending_approval, active, idle, running, paused, error,
  terminated`. 레거시 `archived`는 `canonical_agent_status`로 terminated에
  매핑(읽기/전이 모두 별칭 허용, 저장값은 신규 어휘 권장).
- Task status 8종: `backlog, todo, in_progress, in_review, waiting_approval,
  blocked, done, cancelled`.
- 전이 allowlist는 `models/management.py`(`_AGENT_TRANSITIONS`,
  `_TASK_TRANSITIONS`, `can_transition_*`)가 단일 기준 — 위반 시 409.
  terminal(task done/cancelled, agent terminated)에서 출발하는 전이는 없다.

#### 23.3 API (`/api/v1/management`, `api/routers/management.py`)

- 에이전트: `GET/POST /agents`, `GET/PATCH /agents/{id}`,
  `POST /agents/{id}/transition`, `POST /agents/{id}/wake`,
  `POST /agents/{id}/heartbeat`. 목록의 `status`/`kind` 필터는 허용 어휘
  밖 값이면 빈 목록이 아니라 422.
- 태스크: `GET/POST /tasks`, `GET/PATCH /tasks/{id}`(id 또는 `WMB-n`),
  `POST /tasks/{id}/assign`, `POST /tasks/{id}/checkout`,
  `POST /tasks/{id}/release`.
- 이벤트: `GET /events` — `agent_id/task_id/run_id/event_type/after/limit` 필터.
- 읽기 권한: `/agents`, `/events`는 lead 이상(heartbeat detail 등 임의 JSON
  포함). `/tasks` 목록/단건은 member도 읽기 가능 — task는 작업 항목이라
  멤버가 참조해야 하며 민감 집계(budget/cost)가 없어 노출 위험이 낮다는
  제품 결정. 모든 쓰기는 lead 이상.
- 쓰기는 lead 이상(기존 `_lead_gate`), **heartbeat와 external kind checkout은
  머신 전용 — `security.authorized`(API 키)만 허용, 세션 쿠키만 있으면 403**.
- wake는 `Idempotency-Key` 헤더 또는 body `idempotency_key` 필수(없으면 422,
  body 키는 150자 상한 — 서비스가 `wake:{agent_id}:{key}` 복합키를 만들어
  저장 계층 200자 상한 안에 들어가게 한다). wake replay 판정은
  `agent_events`의 `wake_requested` 키로 먼저 수행하고, 기록된 결과가
  있으면 예산/레이트리밋 검사 **이전**에 그대로 재생한다(`replayed: true`) —
  예산 소진 후 재시도도 429가 아니라 기록된 결과를 받는다. agent_events
  유실(크래시/retention) 후 동일 키 재시도는 `admit_run`의
  `wakeup_requests.idempotency_key` replay로 수렴하며, terminal run의
  replay는 task/agent를 active로 되돌리지 않고 `project_run_status`로
  종결 상태를 복원한다. 동일 키+다른 task는 409 `idempotency_conflict`.
  workflow kind는 `wakeups.admit_run`으로 run을 만들어 `task_runs`에 링크하고
  task 상태(in_progress)·`current_run_id`·`wake_requested` 이벤트 등 모든
  bookkeeping을 **`schedule()` 호출 이전**에 완료한다 — run이 예약 직후
  즉시 종결돼도 투영 대상이 준비된 상태다. 백그라운드 실행은 POST /runs와
  동일하게 버스트 레이트리밋·월간 예산·스코프드 예산
  (`budget_scope.evaluate_admission`, 해석된 adapter_config.workflow 기준)을
  통과해야 하며 차단 시 429 `budget_exceeded` + 감사 로그. external kind는
  run을 만들지 않고 202 + 이벤트만 기록(예산 검사 대상 아님).
- checkout은 `UPDATE ... WHERE checkout_agent_id IS NULL OR =?` CAS +
  `status NOT IN ('done','cancelled')` — 동시 요청 중 정확히 하나만 성공,
  충돌/terminal task는 409. assignee가 다른 agent로 명시 배정된 task도 409.
  checkout 성공 시 todo→in_progress로 진행한다. `release`는 checkout을
  해제해 stranded checkout의 탈출 경로를 제공 — lead/관리자 세션
  (`_explicit_lead_user`, 머신 API 키 제외)이거나 머신 키+checkout 소유
  agent_id 일치 시에만 허용한다. 머신 API 키는 `_lead_user`상 admin-equivalent지만
  holder 검사를 우회하지 않는다.
- `PATCH /tasks/{id}`의 `parent_id`는 uuid 외에 `WMB-n` identifier도 받으며
  uuid로 정규화해 저장한다. 자기참조·조상 체인 순환(해석된 uuid 기준)은 422.
  `assignee_agent_id` 변경이 checkout 보유자와 어긋나면 checkout을 자동
  해제하고 `task_checkout_released` 이벤트를 남긴다. `title`/`status`/
  `priority`의 명시 `null`은 NULL 상태가 없는 필드라 422로 거부하고,
  nullable 필드(assignee 등)의 `null`은 비우기로 동작한다.
- terminal task(done/cancelled) 진입 시 `_finalize_terminal_task`가
  checkout 해제 + `current_run_id` 클리어 + `task_completed`/`task_cancelled`
  lifecycle 이벤트(`term:{task}:{status}` 멱등 키)를 남긴다 — 수동 PATCH,
  heartbeat, run 투영 세 경로가 공유하며 이미 terminal인 task의 stale
  잔여도 회수한다. `create_task`도 `patch_task`와 동일하게 assignee/
  reviewer agent 존재·종결 여부를 검증한다.
- 레거시 `PATCH /api/v1/agents/{id}`의 `status`도 전이 allowlist를 거친다 —
  canonical 7값 + `archived` 별칭만 허용, 불법 전이/terminal 출발은 409,
  변경 시 `agent_status_changed` 이벤트를 남긴다. status 변경은 다른 필드
  쓰기 전에 검증해 부분 적용을 막는다. `GET /agents?status=`도 동일 통합
  어휘를 받는다.

#### 23.4 run→task/agent 투영 (`services/run_projection.py`; facade `agent_management.py`로 re-export)

- `project_run_status(store, run_id)`가 run 상태를 연결된 task/agent에 투영:
  `running→in_progress`, `waiting_approval→waiting_approval`,
  `completed→done`(+`_finalize_terminal_task` 정리), `failed/cancelled→blocked`.
  task_runs에 링크되지 않은 run은 투영하지 않는다(일반 `/runs` 실행과 분리).
  agent 상태 투영은 run-aware다 — 한 agent에 다른 활성 run이 남아 있으면
  idle로 내리지 않는다. agent status 전이는
  `Store.transition_agent_status(from_status→to_status)` CAS로 수행해 동시
  갱신과의 lost-update를 막는다(레거시 PATCH 경로도 동일 CAS 사용, 경합 시 409).
- hook 위치: `engine/runner.py::_finalize`·`_approval_stage`,
  `api/jobs.py` 실패 경로, `api/appctx.py`의 `_do_approve`, `api/support.py`
  reaper — run terminal/waiting 전이 지점마다 호출. 투영 실패는 run 결과를
  망가뜨리지 않도록 내부에서 삼키고 warning 로그만 남긴다.
- `heartbeat`는 머신 어휘(`working/idle/error` 등)를 canonical 상태로
  매핑해 `last_seen_at`을 갱신한다. terminated agent는 heartbeat/wake 거부(409).

#### 23.5 UI

- v2 Agent Office에 `ManagementRoster` 추가 — `/management/agents`를 폴링해
  실제 agent status/kind/last_seen을 표시(3D 보드와 별개 그리드). 현재
  task의 status와 priority(low/medium/high/urgent) 배지도 함께 표시한다.
- `/agents` 화면은 기존 status 어휘를 유지하되 신규 상태 라벨/톤을 표시.

### 24. 비용 원장 cost_events + microusd 예산 (paperclip spec 2차)

`docs/paperclip-agent-management-spec.md` 2차 A/B/C 구현. 기존 float USD
집계(llm_usage·stage_runs×가격표)는 호환용으로 유지하고, 신규 비용 권위는
정수 microusd(1 USD = 1,000,000 microusd)다 — **금액 계산에 float 금지**
(spec Global Constraint). 모든 `*_usd` 필드는 microusd/1e6 파생 표시값.

#### 24.1 가격표 (`jobmate/pricing.py`)

- `MODEL_TOKEN_PRICES_MICROUSD`: (input, output) microusd/1M 토큰 정수 단가 —
  `MODEL_TOKEN_PRICES`와 같은 모델 패밀리 키워드 매칭(default/claude/codex/
  gemini). 단가 변경 시 `PRICING_VERSION`을 올리고 cost_events의
  `pricing_version`에 기록된다.
- `cost_microusd(model, tokens_in, tokens_out, cached_input_tokens=0)` —
  `(tokens*rate)//1_000_000` 순수 정수 연산. 캐시 토큰은 할인 단가가 없어
  input 요금에 포함(보수적 상한). `cost_usd`는 microusd/1e6 파생 래퍼.

#### 24.2 cost_events 원장 (`store/costs.py`, `cost_ledger.py`)

- stage_run 1건당 cost_events 1행 — `idempotency_key` UNIQUE
  (`cost:{stage_run_id}` 라이브, `backfill:stage:{id}` 소급)로 재시도/
  재전송 중복 청구를 막는다. `(row, created)` 반환 — 재생은 created=False.
- `cost_status`: `reported|estimated|unpriced`. **NULL iff unpriced**
  불변식을 `record_cost_event`가 양방향 강제 — 가격을 모르는 사용량을
  0으로 대체 기록하지 않는다. `billing_type`: `metered_api|
  subscription_included|subscription_overage|credits|fixed|unknown`.
- 입력 검증: 토큰 수·cost_microusd는 bool/float/str/음수 거부(정수만).
  API 계층은 `CostEventCreateRequest`의 `StrictInt`가 먼저 차단한다.
- emission: `engine/runner.py`가 LLM stage 성공·실패(누적 usage)·function
  stage 성공 3지점에서 `_emit_cost_event` 호출 — 실패해도 run을 깨지
  않도록 예외를 삼키고 warning만 남긴다. model 있으면 `estimated`+
  rate card microusd, 없으면 `unpriced`(cost_microusd=NULL).
  MeteredLLM의 llm_usage 계측과는 별개 경로(이중 계상 아님).
- 백필: `cost_ledger.maybe_backfill_cost_events`가 automation loop 매 tick
  `automation_state['cost_ledger_backfill_v1']` 가드로 프로세스당 1회 실행
  (배치 500×최대 20). `stage_runs_missing_cost_events`는 토큰 0 stage_run을
  제외(emit이 기록하지 않으므로 영구 미커버 방지). 남은 대상이 없을 때만
  done 기록 — 실패 시 다음 tick 재시도.

#### 24.3 microusd 예산 (`budget_scope.py`, `store/budgets.py`)

- `budget_policies` 신규 컬럼: `amount_microusd`(권위 한도 — >0이면
  `amount_usd`보다 우선, 둘 다 오면 microusd가 한도이고 usd는 파생 표시),
  `reservation_microusd`(admission 차단에만 반영 — spend+reservation>=amount
  이면 차단, 실제 지출 아님), `unpriced_usage_policy`(`block|allow`,
  기본 allow), `window_kind`(`calendar_month_utc|lifetime`).
  `budget_incidents`에 `observed_spend_microusd`/`unpriced_event_count`/
  `reason_code`(`limit_exceeded|unpriced_usage`) 추가. 기존 amount_usd>0
  행은 기동 시 `ROUND(amount_usd*1e6)`로 1회 백필(`_migrate_cost_ledger_columns`).
- 스코프에 `task` 추가 — `SCOPE_TYPES = global|workflow|project|agent|task`.
  task 귀속은 `cost_events.task_id`(run→task_runs 첫 링크).
- 지출 = `cost_events.cost_microusd` 합계(NULL=unpriced 제외) +
  **미커버 stage_runs**(cost_events에 stage_run_id 연결 행이 없는 것)를
  rate card로 환산한 합 — 원장 이벤트와 stage_run_id로 연결돼 이중 계상
  없음. workflow/project/agent 귀속은 runs 조인, agent는 `ce.agent_id`
  우선·`runs.agent_id` 폴백.
- `unpriced_usage_policy='block'`이고 윈도우 내 unpriced 이벤트가 있으면
  지출 한도와 무관하게 hard_stop(`reason_code='unpriced_usage'`).
- `evaluate_admission(..., task_id="")` — 모든 비교 microusd 정수.
  `agents.monthly_budget_microusd`는 `monthly_budget_usd`보다 우선하는
  월간 상한(2차 집행 경로).
- 인시던트 해결 `raise_budget_and_resume`도 `amount_microusd` 우선 —
  새 한도는 `observed_spend_microusd`(없으면 amount_observed 파생)보다
  커야 한다.

#### 24.4 API

- `POST /api/v1/management/cost-events` — **머신 API 키 전용**(세션 쿠키
  불가). 외부 runner의 비용 보고. 201 생성 / 동일 idempotency_key 재전송은
  200 기존 행 재생. 검증 실패 422. 수용 시 `cost event accepted` INFO 로그
  (ids/provider/model/cost_status — credential 없음) + 감사.
  `stage_run_id`만 태그되고 `run_id`가 없으면 서버가 `sr.run_id`를 유도해
  저장하고, `agent_id` 미지정 시 run.agent_id(실존 agent일 때),
  `task_id` 미지정 시 run이 단일 task에만 귀속될 때 그 task_id를 유도한다
  — stage_run 단독 태그 이벤트가 workflow/project/agent/task 스코프
  집계에서 누락되지 않게 하기 위함(M6).
- `GET /api/v1/management/cost-events` — lead 이상. agent/task/run/
  stage_run/provider/model/cost_status/billing_type/occurred_from/to
  필터, occurred_at DESC, limit 최대 500.
- `GET /api/v1/management/costs/summary?scope=&scope_id=&from=&to=` —
  lead 이상. scope는 `global` 또는 `type:id`(agent:X 등). total_microusd는
  priced만 합산, unpriced는 별도 카운트 — '모름'을 0원으로 뭉개지 않는다.
- `PUT /api/v1/budgets/policies/{scope_type}[/{scope_id}]` —
  `amount_microusd`/`reservation_microusd`(StrictInt, ≥0)/
  `unpriced_usage_policy`/`window_kind` 필드 추가. 명시 null은 미전송과
  동일하게 기존 값 유지(무음 비활성화 방지), `amount_usd` 명시 null만
  기존 의미대로 비활성화.
- `POST /api/v1/budget-incidents/{id}/resolve` — `amount_microusd` 추가
  (amount_usd보다 우선).

### 25. 범용 승인 approval_requests + watchdog recovery (paperclip spec 2차 D/E)

`docs/paperclip-agent-management-spec.md` 2차 D/E 구현. 기존 run 승인
(`approvals` 테이블 + `POST /runs/{id}/approve`)은 그대로 두고, 도메인
무관 durable 승인함 `approval_requests`와 watchdog 복구 추적
`recovery_actions`를 추가했다. 상태 전이·CAS·도메인 규칙은 서비스 계층
(`services/approvals.py`, `services/watchdog.py`), 원자적 쓰기는
`store/governance.py`(`GovernanceStoreMixin`)가 담당한다.

#### 25.1 approval_requests (`store/governance.py`, `services/approvals.py`)

- 필드: id, action_type, risk_level, status, requested_by_agent_id,
  requested_by, task_id, run_id, resource_type, resource_id, summary(≤300),
  safe_payload(JSON TEXT), expires_at, decided_by, decision_comment,
  decided_at, created_at, updated_at.
- enum: `ApprovalStatus` pending|approved|rejected|expired|cancelled,
  `ApprovalRisk` low|medium|high|critical, `ApprovalActionType`
  run_resume|budget_raise|agent_hire|agent_terminate|external_send|
  deploy|destructive_tool|recovery (`models/enums.py`).
- **safe_payload secret 거부**: `_SECRET_KEY_RE`(agent_management과 동일
  규칙 — token/secret/password/api_key/credential/bearer/dsn/auth 등)를
  재귀 키 순회로 검사해 매칭되면 저장 전에 422 `secret_payload`. 값이
  아니라 키 이름 기준이며 중첩 dict/list 안 키도 잡는다. safe 키 아래
  URL 문자열의 userinfo credential(`https://user:pass@host`)도
  `redact_adapter_config`로 스크럽해 저장한다. 직렬화 결과가 8000자를
  넘으면 422 — 잘린 JSON은 파싱 실패로 `{}`가 돼 부수효과 필드를
  조용히 잃으므로 절대 저장하지 않는다(store도 동일 한도로 방어).
- **action_type별 최소 risk(C1)**: `ACTION_MIN_RISK` —
  agent_terminate|budget_raise|external_send|deploy|destructive_tool은
  최소 `high`, agent_hire|run_resume은 `medium`, recovery는 `low`.
  요청 risk_level이 최솟값보다 낮으면 생성 시 상향 보정되고, 결정
  게이트도 `effective_risk_level`(저장값과 최솟값 중 높은 쪽)로 판정해
  보정 이전의 낮은 risk row도 머신 결정이 불가하다.
- **resource↔payload 바인딩(H1)**: agent_terminate는
  `resource_type='agent'`+`resource_id` 필수이고 payload.agent_id는
  있으면 resource_id와 일치해야 한다 — 부수효과 대상은 resource_id
  단일 기준. recovery는 payload.recovery_id와 resource_id가 둘 다
  있으면 일치 필수. run_resume은 payload.run_id/row.run_id/resource_id
  상호 일치. budget_raise는 incident_id가 있으면 실존 incident,
  없으면 유효 scope_type+amount 필수. 요청 생성 시점과 결정
  pre-validation(`_prevalidate_decision`) 양쪽에서 강제한다.
- **참조 무결성(L3)**: requested_by_agent_id/task_id/run_id는 생성 시
  실존해야 한다(없으면 422) — cost-events와 같은 규칙.
- **결정 CAS**: `decide_approval_request`는 `WHERE status='pending' AND
  (expires_at IS NULL OR expires_at >= now)` 조건부 UPDATE — 동시
  approve/reject 중 정확히 하나만 rowcount>0. 만료는 lazy — 읽기 경로가
  `expires_at` 경과 pending을 'expired'로 해석하고, list/decide 전
  `expire_stale_approval_requests`가 DB 상태를 확정한다. `expires_at`은
  `datetime.fromisoformat` 검증 + UTC 정규화(`+00:00`) — 사전식 비교가
  어긋나지 않게 하고, 과거 시각은 허용(즉시 expired).
- **부수효과 사전 검증(H2)**: approve 결정은 CAS **이전**에
  `_prevalidate_decision`이 대상 실존·오픈 상태·바인딩 일치를 확인한다
  — 대부분의 실패는 승인을 pending으로 남긴 채 404/409/422로 끝난다.
  CAS 이후에야 알 수 있는 실패(resume 충돌, budget resolve 규칙 위반
  등)만 커밋 후 부수효과 단계로 넘어가며, 그 경우도 결정을 되돌리지
  않고 `approval_side_effect_error` 감사 + error agent_event로 보상한다.
  **잔여 비원자성**: spec의 '결정+대상 상태 변경+감사를 같은
  transaction'는 resume_fn·budget_scope 같은 트랜잭션 외부 호출 때문에
  완전히 보장되지 않는다 — 결정 CAS와 부수효과 사이의 프로세스 크래시
  시 승인은 committed인데 부수효과가 누락될 수 있다. 완화: pre-validation
  + 실패 감사/이벤트 + watchdog missing_cost/failed_resume 감지.
- **high/critical 권한**: 라우터가 `_explicit_lead_user`(세션 lead/admin
  또는 로컬 개발 admin — 유효 API 키 제외)로 검증, 미충족 시 403
  `explicit_lead_required`. 머신 키 하나가 고위험 결정을 내리지 못한다.
- **부수효과**(결정 커밋 이후, 실패해도 승인 유지 — spec D):
  - `run_resume`: `ctx._do_approve`를 resume_fn으로 주입해 기존
    claim/resume/audit/wakeup 경로 재사용. approve→resume,
    reject→run reject.
  - `budget_raise`: payload `incident_id` → `budget_scope.resolve_incident
    (raise_budget_and_resume)`, 아니면 `scope_type/scope_id/amount_*` →
    `upsert_policy`.
  - `agent_terminate`: `transition_agent(..., terminate_authorized=True)`로
    terminated 전이 — 승인 row 자체가 권한.
  - `recovery`: payload `recovery_id`의 recovery_action을 resolved로.
  - `agent_hire`/`external_send`/`deploy`/`destructive_tool`: 결정 기록 +
    감사만 — 실제 실행은 각 도메인의 명시적 API가 담당한다.
- 부수효과 실패는 결정을 되돌리지 않고 `approval_side_effect_error`
  감사 + error agent_event를 남긴다(spec D 준수).
- **agent terminate 가드**: `transition_agent`와 legacy
  `PATCH /api/v1/agents/{id}`의 status→terminated 전이는 승인된
  agent_terminate approval_request(agent/<id>)가 없으면 409
  `approval_required`. `DELETE /agents`(archive=terminated 별칭)와
  서비스 내부 직접 호출은 별도 경로 — 승인 우회가 필요하면
  `terminate_authorized=True`를 명시한다.

#### 25.2 recovery_actions (`store/governance.py`, `services/watchdog.py`)

- 필드: id, source_type(agent|task|run), source_id, kind, status,
  attempt_count, max_attempts, next_attempt_at, timeout_at, owner_type,
  outcome, resolution_note, created_at, updated_at, resolved_at.
- `RecoveryKind`: stale_heartbeat|stranded_task|stuck_run|missing_cost|
  failed_resume. `RecoveryStatus`: active|escalated|resolved|cancelled.
  `RecoveryOwnerType`: system|agent|human.
- **source당 open 1건**: `create_recovery_action`이 사전 조회 +
  부분 UNIQUE 인덱스 `idx_recovery_actions_open`
  (`_migrate_recovery_actions_index`, `_migrate_budget_incident_index`와
  동일 패턴 — 더티 DB 중복 행은 cancelled로 정리 후 인덱스 생성, 실패해도
  기동 지속)로 이중 방어한다.
- 상태 전이: `set_recovery_status`는 open→resolved|cancelled|escalated만
  허용('active'는 시작 상태). `record_recovery_attempt`는 open 상태에서만
  attempt_count+1/outcome/next_attempt_at 갱신.

#### 25.3 watchdog cycle (`services/watchdog.py`)

- `_automation_loop`(jobs.py)와 `POST /api/v1/cron/tick`(messaging.py)
  모두 `_check_waiting_approvals` 직후 `run_cycle(store)` 호출 — 운영
  cron과 `POST /management/watchdog/run`(admin)이 같은 service를 쓴다.
- env: `JOBMATE_WATCHDOG_BATCH`(기본 25, cycle 처리 상한),
  `JOBMATE_WATCHDOG_HEARTBEAT_MINUTES`(기본 30),
  `JOBMATE_WATCHDOG_STUCK_HOURS`(기본 24).
- **중복 실행 방지**: module-level non-blocking lock — automation loop과
  cron tick·`watchdog/run`이 겹쳐도 cycle은 1개만 돌고 후발 호출은
  `skipped`를 반환한다.
- **예산 규칙(BLOCK-2 수정)**: detector 생성은 `was_created`만 소비하고
  dedupe hit는 무료 — 만성 소스가 batch를 잠식하지 않는다. detector별
  쿼터(ceil(batch/5))로 한 detector 폭주가 다른 detector를 굶기지 않는다.
  복구 단계는 detection backlog과 무관하게 항상 실행 — 건강 재검사는
  attempt 예산 무관하게 모든 open row를 보고, due 재시도만 batch 상한을
  공유한다. `list_open_recovery_actions`는 active→escalated 순으로
  정렬해 escalated 누적이 스캔 슬롯을 잠식하지 않게 한다(열린 row가
  clamp 한도를 넘는 극단적 경우 최신 행이 밀릴 수 있는 잔여 한계 있음).
  due 재시도는 `next_attempt_at`이 잡힌 예약 건을 미시도(NULL) 건보다
  먼저 처리한다.
- detector(각각 store의 전용 쿼리):
  - `stale_heartbeat`: kind='external' + active|idle|running agent 중
    `last_seen_at`이 cutoff보다 오래된 것(NULL=미연결 제외, workflow
    kind 제외 — 서버 heartbeat가 없다).
  - `stranded_task`: in_progress + checkout 없음 + current_run/task_runs에
    queued|running|waiting_* run 없음.
  - `stuck_run`: waiting_approval|waiting_review|queued로 stuck cutoff보다
    오래 updated_at — `_reap_stale_runs`(30분)의 queued/running fail과
    별개로 더 긴 꼬리만 본다. needs_human은 사람 알림 경로가 있어 제외.
  - `missing_cost`: terminal run 중 토큰 사용 finished stage_run이
    있으나 cost_events(run_id)가 하나도 없는 것 — 토큰 0 stage_run만
    있는 run은 emit이 기록하지 않으므로 제외(영구 오탐 방지).
  - `failed_resume`: `run_resume_error` audit 이후 run_approve/reject
    결정 없이 waiting_approval에 남은 run(72h 창).
- 복구 규칙: 매 cycle open recovery의 건강을 먼저 재검사해 회복됐으면
  resolved. due(`next_attempt_at` 경과) active만 재시도 — escalated는
  사람 결정 대기라 자동 재시도하지 않는다(건강 재검사로 resolved만 가능).
  안전한 자동 복구만: `missing_cost`→`cost_ledger.backfill_cost_events`
  (멱등 `backfill:` 키), `failed_resume`/`stuck_run`(waiting_approval)→
  run_resume approval_request 생성(dedupe). 그 외는 알림
  (agent_event)만 — 외부 전송/파괴 작업 자동 재시도 없음.
- 재시도는 지수 백오프(15m×2^n, 상한 6h), `attempt_count >= max_attempts`
  이면 escalated + owner_type=human + inbox `kind='recovery'` 알림 +
  source가 task면 in_progress→blocked 전이(`_advance_task_status`).
- cycle 시작 시 `expire_stale_approval_requests` sweep으로 만료 pending을
  확정한다. 반환 counts{scanned,detected,created,retried,escalated,
  resolved,expired_approvals,batch_limit}는 spec H watchdog cycle 로그로
  INFO 기록된다.

### 26. Paperclip 브리지 — 외부 오케스트레이터 projection (paperclip spec 3차 E/F)

`docs/paperclip-agent-management-spec.md` 3차 E/F 구현. Workmateboard는
Paperclip을 재구현하지 않고, 로컬/상주 브리지가 Paperclip API를 polling해
변경분을 machine endpoint로 push하면 서버가 읽기 전용 projection
(`external_agents`/`external_tasks`/`external_runs`)에 upsert한다.
Vercel은 Paperclip/Codex를 실행하지 않는다.

#### 26.1 구성 요소

- `src/jobmate/paperclip/` 패키지 (`paperclip_client.py`는 호환 shim)
  - `client.py`: `OrchestratorClient` 프로토콜 — `get_dashboard/list_agents/
    list_tasks/list_runs/get_cost_summary`. 테스트는 fake를 주입한다.
  - `PaperclipClient` — httpx REST 클라이언트. base URL은
    `validate_paperclip_url`로 검증: http/https + (loopback 호스트 또는
    webutil SSRF 가드 통과 공인 호스트)만 허용, userinfo 자격증명 포함
    URL 거부. 공인 호스트는 `_PinnedTransport`로 검증 IP에 connect 고정
    (DNS 리바인딩 차단), 리다이렉트 비추적(3xx도 오류), 응답 8MB 상한,
    429/5xx/타임아웃은 지수 백오프+지터 최대 3회 재시도, 401/403은
    즉시 실패. `Authorization: Bearer` 헤더는 로그/예외에 남기지 않는다.
  - 엔드포인트(스펙이 정확한 경로를 정의하지 않아 아래로 가정):
    `GET /api/companies/{company_id}/agents|tasks|runs|dashboard|
    cost-summary`, 페이지네이션 `?limit=&cursor=`, 응답의
    `next_cursor/cursor/next_page/page_token/after`를 따른다.
    `next`가 절대 URL/경로면 무시한다(임의 호스트 요청 방지).
  - `PaperclipBridge.sync_once()` — `collect_snapshot`으로 3종 엔티티를
    조회·정규화(external_id/status/title/assignee/token_cost_summary)하고
    `POST /api/v1/management/integrations/paperclip/snapshot`으로 push.
    push 대상 `jobmate_url`도 `validate_jobmate_url`로 paperclip과 동일
    정책 검증을 거친다 — X-API-Key가 실리므로 공인 호스트는 https 필수,
    http는 loopback에서만 허용.
    멱등키는 canonical payload의 sha256(`pc-<hash40>`) — 동일 페이로드
    재시도는 서버 replay, 변경 시 새 키로 false conflict 없음.
    entity별 `updated_after` 커서를 메모리에 유지해 루프에서 증분 조회.
- `src/jobmate/store/external_sync.py` (`ExternalSyncStoreMixin`)
  - upsert: `UNIQUE(provider, company_id, external_id)` 기준
    `ON CONFLICT DO UPDATE` — 회사 간 external_id 충돌 없이 각자 행을
    유지한다(agents/tasks/runs 3종 공통). snapshot에 없는 기존 행은
    삭제하지 않는다 — 끊긴 외부 연결에서도 마지막 정상 snapshot이
    stale 배지와 함께 유지된다(spec F).
  - `ingest_external_snapshot` — upsert + 커서 갱신 + 멱등키 기록을
    하나의 tx로 처리. 중간 실패 시 아무것도 반영되지 않아 커서가
    오전진하지 않는다(spec G).
  - **stale snapshot 방어**: entity별 저장 커서를 watermark로 써서
    `item.updated_at`이 watermark보다 오래된 행은 upsert하지 않고,
    커서도 단조 전진만 허용한다 — 늦게 도착한 오래된 snapshot이
    최신 상태를 되돌리지 못한다.
  - **커서 값 계약**: `cursors` 값은 ISO-8601 파싱 가능 타임스탬프만
    허용한다(`_cursor_value_ok`) — malformed 값("zzz" 등)은 저장하지
    않는다. malformed가 저장되면 이후 모든 정상 타임스탬프가 문자열
    비교에서 밀려 watermark가 영구 정지하기 때문. `_cursor_newer`도
    parse-aware 우선순위(파싱 가능 > 불가)로 깨진 기존 값을 복구한다.
  - `PaperclipBridge`의 push client도 `_PinnedTransport`로 공인
    jobmate_url의 connect IP를 고정한다(DNS 리바인딩으로 X-API-Key가
    새지 않게 — PaperclipClient와 동일 정책). `agent_bridge.Bridge`도
    생성 시 `validate_jobmate_url`로 동일 egress 정책을 적용하고,
    push client에 동일 pinning을 사용한다 — 둘 다 http는 loopback만
    허용, 공인은 https 필수, userinfo 금지.
  - 스키마 마이그레이션(`Store._migrate_external_company_columns`):
    구 스키마 `UNIQUE(provider, external_id)` DB는 external_agents/
    tasks/runs 3종을 (provider, company_id, external_id) UNIQUE로
    재작성한다(SQLite 테이블 rebuild, PG는 제약 교체 + company_id
    백필). company_id 인덱스는 컬럼 보강 이후
    `_ensure_external_company_indexes`가 생성한다 — SCHEMA 문자열에
    두면 구 DB에서 executescript가 깨진다. 마이그레이션 실패는
    `logger.critical` + `_external_company_schema_broken` 플래그로
    표면화하고 ingest가 명시적 RuntimeError로 조기 실패한다 —
    3컬럼 ON CONFLICT의 sqlite OperationalError로 이어지는 것을 막는다.
  - 커서: 스키마에 entity 컬럼이 없어
    `external_sync_cursors.cursor` JSON에 `{"agents":..,"tasks":..,
    "runs":..}` 형태로 병합 저장한다.
  - 멱등: `external_snapshot_keys` 테이블을 최초 ingest 시 lazy 생성
    (스키마 파일 변경 없이). 동일 키+동일 payload 해시 → replayed,
    동일 키+다른 해시 → `SnapshotConflictError` → API 409.
    키는 최근 100개/7일로 prune.
  - 비밀 제거: `sanitize_external_payload`가 secret-like 키(token/
    secret/password/api_key/credential/session/cookie 등)와
    transcript/prompt/messages/adapter_config/env 서브트리를 재귀
    제거한다. `token_cost_summary`는 allowlist 스칼라 키만 저장.
    브리지 측에서도 동일 정제를 적용한다(심층 방어).
  - `external_sync_status(provider?)` — (provider, company_id)별
    엔티티 카운트, entity별 커서, last_synced_at, last_error_code,
    stale 판정(기본 15분 초과 시 stale).
- `src/jobmate/api/routers/paperclip.py`
  - `POST /api/v1/management/integrations/paperclip/snapshot` —
    machine gate(`authorized()` — 세션 쿠키만으로는 403), Idempotency-Key
    헤더 또는 body.idempotency_key 필수. 항목 수 상한
    (agents 1000/tasks·runs 5000). 201 생성 / 200 replay / 409 충돌.
  - `GET /api/v1/management/integrations/paperclip/status` — 머신 키
    또는 lead 세션. 읽기 전용 카운트/커서만 반환.
- `src/jobmate/cli.py` — `jobmate paperclip-bridge` 서브커맨드.

#### 26.3 보안·운영 노트

- external_* 행은 native agents/tasks/runs와 ID 네임스페이스를 섞지
  않는다(별도 테이블). 외부 task를 native run으로 자동 생성/재실행하지
  않는다. 상세 prompt/transcript/adapter env/credential은 동기화하지
  않는다 — 서버가 저장 전 재차 제거한다.
- snapshot POST는 machine 전용 — 세션 쿠키만으로는 403. status GET은
  머신 키 또는 lead 세션.
- 서버 로그: `paperclip snapshot accepted|replayed provider= company=
  agents= tasks= runs= replayed= <ms>` — payload·URL·키 없음.
  감사 로그(`paperclip_snapshot`)에도 건수/키 앞부분만 기록.
- 브리지 로그: provider/company 없이 건수와 replayed 여부, 실패 시
  예외 클래스+HTTP 상태만.
- topology(17_운영_보안_가이드_v1.0.1.md 부록 A 참고): Vercel=UI/API, 로컬/VPS=Paperclip +
  paperclip-bridge, PostgreSQL=native+external projection.

### 27. Routines — 반복 업무 루틴 스케줄러 (paperclip spec 3차 C/F/G)

routines 테이블은 반복 업무를 정의하고, routine_runs는 1회 스케줄
발사의 감사/멱등 기록이다. 스케줄 실행은 기존 automation loop과
`/api/v1/cron/tick`이 담당한다 — 신규 데몬 없음.

#### 27.1 데이터 모델 (`store/routines.py` RoutineStoreMixin)

routines 컬럼: id, name, description, project_id, task_template(JSON),
assignee_agent_id, schedule_kind, schedule(JSON), timezone(IANA),
max_concurrent(기본 1), enabled(INTEGER), next_run_at, last_run_at,
created_by, created_at, updated_at. routines.status 컬럼은 없고
enabled의 파생값(active|paused)으로 API 응답에 포함한다.

routine_runs 컬럼: id, routine_id, scheduled_for, task_id,
status(pending|created|skipped|failed), idempotency_key UNIQUE,
error_code, created_at, finished_at. routine 삭제 시 runs 이력은 보존.

#### 27.2 스케줄 종류와 next-run 계산 (`services/routine_schedule.py`; `routines.py`가 re-export)

schedule_kind는 3종만 지원(croniter 의존 없음):

- `interval`: `{"minutes": int}` — anchor(routines.next_run_at) 격자.
  timezone 미사용. 생성/재활성화 시 첫 발생은 now+minutes.
- `cron_daily`: `{"time": "HH:MM"}` — routine.timezone 로컬 시각.
- `cron_weekly`: `{"weekday": 0-6 (Mon=0), "time": "HH:MM"}`.

모든 next_run_at/last_run_at/scheduled_for는 UTC ISO-8601.

DST 정책(명시, `resolve_local`):

- ambiguous(fall-back 중복 로컬 시각): 첫 번째 발생(fold=0, 더 이른 UTC).
- nonexistent(spring-forward gap): 같은 날 최대 180분 forward-scan해
  첫 유효 로컬 시각으로 이동(예: 02:30 → 03:00). 없으면 그 슬롯 생략.
- interval은 timezone을 쓰지 않는다.

missed schedule: catch-up 루프 없이 now 이하 가장 최근 1회만 발사
(scheduled_for=최신 발생, next_run_at=now 이후 첫 발생).

#### 27.3 발사 경로

- `_process_due_routines` (api/jobs.py): `_process_due_schedules`와 동일
  구조. `due_routines(limit=JOBMATE_ROUTINE_BATCH, 기본 10)` → routine별
  try/except. `_automation_loop`에서 `_process_due_schedules` 직후 호출,
  `cron_tick`(routers/messaging.py)에서는 defer list → `_schedule_run_jobs`
  (BackgroundTasks) 경로로 실행 job을 넘긴다.
- `fire_due_routine` (services/routines.py):
  1. `claim_routine_fire_with_run` — next_run_at CAS(compare-and-swap)와
     pending routine_run INSERT를 **한 tx**로 처리한다. loop/tick 동시
     실행·다중 인스턴스의 중복 발사를 원자적으로 차단하고, claim 성공
     시점에 routine_run 행이 이미 존재해 claim~task 생성 사이 크래시로
     run 기록이 유실되지 않는다. claim_lost/duplicate(동일
     idempotency_key)로 수렴한다.
  2. `max_concurrent` — routine_inflight_count(이 routine이 만든 task 중
     done/cancelled가 아닌 수) >= max_concurrent이면 run을 skipped로
     기록하고 다음 발생으로 진행(중복 task 없음).
  3. task 생성 — `agent_management.create_task` 재사용. task_template의
     title/description/status(기본 todo)/priority만 허용. routine의
     project_id는 생성 task의 project_id/goal_id(project.goal_id)로 전파.
     생성 직후 routine_run.task_id를 즉시 연결한다.
  4. assignee_agent_id가 있으면 `agent_management.wake_agent` 재사용 —
     idempotency_key `routine:{routine_run_id}`, schedule 콜백으로 run
     실행을 defer/thread에 위임. 예산 admission은 wakeups.admit_run
     내부에서 수행된다. wake 실패는 routine_run.error_code에만 기록하고
     status는 created 유지(task는 생성됨).
  - task 생성 이후 단계(task_id 연결→wake→created 마감+audit)는 보호
    블록으로 묶여 mark/audit 실패 시 routine_run을 failed로 best-effort
    마감한다(task_id 보존 → inflight 추적 유지). 그래도 pending으로
    남은 행은 `sweep_stale_pending_runs`(TTL 1h,
    `_process_due_routines`이 매 주기 호출)가 failed('interrupted')로
    회수한다 — claim~task 생성 사이 크래시의 잔여도 정리된다.

### 29. Agent Permissions — capability allow/deny 모델 (paperclip spec 3차 D/F/G)

`agent_permissions` 테이블(agent_id, capability, effect allow|deny,
scope_type global|project|task, scope_id NOT NULL DEFAULT '',
UNIQUE(agent_id,capability,scope_type,scope_id,effect)) 위에 구축된
에이전트 capability 권한 계층. 스키마는 schema_sqlite.py/schema_pg.py 양쪽에
이미 정의돼 있다.

#### 29.1 Capability 어휘 (`models.AgentCapability`)

spec D 최소 집합 16종: `task:read|create|assign|update`,
`agent:read|manage|wake`, `run:execute|approve`, `cost:read`,
`budget:manage`, `artifact:create`, `external:send`, `deploy:execute`,
`destructive:execute`, `integration:manage`.

#### 29.2 판정 규칙 (`services/permissions.py`)

- `evaluate_permission(store, agent_id, capability, scope_type, scope_id,
  task_id, project_id)` → `{decision: allow|deny|needs_approval, ...}`.
- 매칭 규칙: global은 항상, project는 컨텍스트 project_id와,
  task는 컨텍스트 task_id와 scope_id가 같을 때 매칭. task_id만 주면
  서버가 task의 project_id를 해석해 project 규칙도 함께 평가한다
  ('WMB-n' identifier도 canonical uuid로 정규화).
- **task의 project가 정본**: task_id가 해석되면 그 task의 project_id가
  컨텍스트 project로 우선한다. 명시적 project_id가 task의 project와
  다르면 `evaluate_permission`은 task 측을 평가하고
  `conflict_project_id`를 결과에 남기며, `require_permission`은
  `ManagementError(422,'validation')`를 던진다 — 다른 project 컨텍스트로
  project deny를 우회할 수 없다.
- **deny 우선**: 매칭 scope 전체에서 deny 1건이면 deny — scope 무관.
- 규칙이 allow뿐이면 allow. 단 `external:send`/`deploy:execute`/
  `destructive:execute`는 spec D대로 **명시적 allow + 2차 approval을
  모두 요구** → `needs_approval`. 규칙이 없으면 이 3종은 기본 deny,
  나머지 capability는 기본 allow(permissions는 opt-in 제한 계층).
- needs_approval 판정 시 `CAPABILITY_APPROVAL_ACTION`으로 기존
  `approval_requests.action_type`(external_send/deploy/destructive_tool)에
  매핑하고 `store.has_decided_approval(action, 'agent', agent_id)`를
  확인한다. 이 action들은 `ACTION_MIN_RISK`가 high를 강제해 로그인된
  lead/admin만 승인 결정을 내릴 수 있다(2차 D와 동일 메커니즘).
- **승인은 standing grant**: `(action_type, agent_id)`에 대해 과거에
  approved된 approval이 하나라도 있으면 이후 모든 호출에 유효하다 —
  만료·소비되지 않는다. spec D는 승인 단위를 정의하지 않아 가장 단순한
  해석을 택했다. scope별 승인(예: 특정 project의 deploy만)이 필요해지면
  approval_requests의 resource/safe_payload에 scope를 싣는 확장이 필요하다.

#### 29.3 Identity 모델 — 누가 검사받는가

- `agent_permissions`는 **agent_id에 귀속**된다. 기계 API 키는 agent가
  아니라 공유 자격이므로, 검사는 **agent가 행위자로 등장하는 경로**에만
  적용한다 — 대상/행위 agent의 permission 행을 평가한다.
- 사람(세션 lead/member)의 management 쓰기는 agent permission과 무관하게
  기존 lead/member 모델을 따른다.
- `agent_id` 없이 생성되는 run(POST /runs, 내부 trigger/schedule 경로)은
  agent 행위자가 아니므로 run:execute 검사를 적용하지 않는다.

#### 29.4 강제 지점 (서버 재검증 — spec "서버가 반드시 다시 검증")

`services/permissions.require_permission`이 판정 후 deny→
`ManagementError(403,'permission_denied')`, needs_approval(미승인)→
`(409,'approval_required')`를 던진다. denial 로그는
actor/capability/scope/resource id만 남기고 payload 원문은 기록하지
않는다(spec H).

| 경로 | 검사 내용 |
|---|---|
| `wake_agent` (services/agent_management) | wake 대상 agent의 `agent:wake` 항상 + workflow kind는 `run:execute` + task-bound wake는 `task:assign`(task 스코프). idempotent replay는 부수효과가 없어 검사 이전에 반환 |
| `create_task` / `patch_task`(assignee 변경) / `assign_task`(경유) | assignee agent의 `task:assign` — create는 project 스코프까지, patch/assign은 task 스코프. **patch_task가 project_id와 assignee_agent_id를 동시에 바꾸면 assignee의 task:assign을 '대상' project 스코프에서도 재검증**한다(현재 project 기준 판정만으로는 이동 후 deny 우회 가능 — task 스코프 규칙은 첫 호출이 커버) |
| deferred wakeup promote (`wakeups.py`) | defer 이후 agent permission 회수에 대비해 promote 시 `run:execute` 재검증 — task_id(`input.meta.task_id`)와 **project_id(`input.project` → canonical project uuid 해석, 이름/id 모두 허용)**를 함께 넘긴다. task project와 run project가 충돌하면 422 의미론으로 wakeup failed 마감 |
| `checkout_task` | checkout하는 agent 본인의 `task:update`(task 스코프) + **assignee가 비어 checkout이 자기 배정을 수반하면 `task:assign`(task 스코프)도 요구**. 단 **명시적 lead 세션/로컬 admin의 대리 checkout은 면제**(`human_actor` — 라우터가 `_explicit_lead_user`로 판정). 머신 API 키 등 비-명시 호출은 agent-actor로 간주해 검사한다 |
| `heartbeat` (task_id + 상태 전이 시) | heartbeat agent 본인의 `task:update`(task 스코프) |
| `POST /api/v1/runs` | `agent_id` 태깅된 run 생성 시 해당 agent의 `run:execute`(project/task 스코프 — metadata.task_id·project 해석). **run 수준 검사만 한다** — metadata.task_id가 있어도 task 생명주기 capability는 검사하지 않으며, task 측 강제는 task 엔드포인트와 wake 경로에서 수행한다(의도적 결정) |

미적용(의도적): `release_task`(lead의 stranded checkout 회수 경로를 막지
않기 위해), `transition_agent`/`run approve` 등 사람 lead 행위,
`cost:read`/`budget:manage`/`artifact:create`/`integration:manage`/
`agent:read|manage`/`run:approve`/`task:read|create` — 현재 agent-actor
전용 엔드포인트가 없으므로 규칙 저장·effective 판정만 지원한다. 해당
행동을 여는 신규 경로는 `require_permission`을 호출해야 한다.

#### 29.5 API (spec F)

- `GET /api/v1/management/agents/{id}/permissions` — 규칙 목록(member+,
  `/api/*` 미들웨어 인증). 응답 `{"agent_id", "permissions":[...]}`.
- `PUT /api/v1/management/agents/{id}/permissions` — 규칙 전체 교체
  (**명시적 lead 전용 `_explicit_lead_user`** — 머신 API 키는 403.

  이 엔드포인트에는 세션 lead/admin 또는 로컬 admin만 허용한다).
  body `{"permissions":[{capability,effect,
  scope_type,scope_id}]}` — 프론트엔드 계약과 동일. 검증:
  capability/effect/scope_type enum, scope_id 필수(project/task) +
